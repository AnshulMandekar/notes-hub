What is a data warehouse?

In one line: a data warehouse is the one central place where a company keeps all its data (sales, transactions, budget, marketing, HR) so people can analyse it.

Simple analogy

Think of the suitcase you pack for a holiday. Formal clothes, casual clothes, shoes and socks all go into one bag. A data warehouse is that bag for a company's data. Everything is in one place, so you always know where to look.

Why it matters

  • Almost every data engineering job description asks for "experience building data warehouses".
  • Many people know the tools (Azure, AWS, GCP, Databricks) but get stuck when asked about data warehousing and data modelling. That's the gap this video fills.
  • Tools can speed up the work, but every warehouse design depends on the business. You can't automate that thinking, which makes it a skill AI won't easily replace.

Database vs data warehouse

MySQL, PostgreSQL and SQL Server are DBMS (database management systems). You can keep a normal database or a data warehouse inside them. So the difference isn't the software. The difference is how data arrives and how it's stored.

Why not just report from the database?

The database's SQL engine is busy inserting new transactions every few milliseconds. If you also run heavy report queries on it (joins, window functions, aggregations), both jobs slow down. A dashboard could take an hour to refresh. So we copy the data to a warehouse and run the reports there.

But doesn't copying the data also put load on the database?

Very little, because ETL only does a plain bulk read with no transformations at the source. Something like "give me everything up to 9 PM", once a day. The next day it asks "give me everything after yesterday 9 PM". The warehouse is like a big brother that keeps collecting new data from the database.

DatabaseData warehouse
Data arrivesConstantly, in small transactionsIn bulk batches (e.g. daily)
FreshnessNear real timeUp to the last load ("static")
Main jobRecord transactions fastAnswer analytical queries
Who queries itThe applicationAnalysts, BI, data scientists

Data warehousing (the verb)

Data warehousing is the process of pulling data from databases and storing it in the warehouse in the right shape. Anyone can run ETL with drag-and-drop tools these days. The real value of a data engineer is knowing how to structure the data. That's the architecture and the fundamentals.

Interview

"Is a data warehouse a different software from a database?" No. Both store tables of rows and columns, and both can live in the same DBMS. The difference is the workload: OLTP databases take small writes all the time, while a warehouse takes bulk loads and serves analytical reads.

ETL and the warehouse layers: staging, core, data marts

ETL = Extract → Transform → Load. We don't copy the database straight into the final tables. The warehouse has two layers inside it:

Staging layer

A raw, as-is copy of the source with no transformation. We read the source quickly and leave it alone so the busy database isn't loaded.

Core layer

Curated (transformed) data. This is the layer analysts, data scientists and BI developers actually query.

Data mart

A subset of the warehouse for one business area, like Finance or HR. The Finance team doesn't need access to the whole company's data, only its own slice.

Incremental loading and CDC

The problem: on day 1 you load all the rows (the initial load). On day 2 the source has 3 new rows. Do you reprocess everything? No, the old rows are already in the warehouse. Incremental loading means you only load the new rows.

How: with CDC (Change Data Capture). After each load, save the maximum date you've seen (often called the watermark). On the next run, only read the rows after it.

CDC idea · SQLKey idea
-- Day 1 (initial load)
SELECT * FROM source_table;                    -- then store MAX(date) somewhere

-- Day 2+ (incremental load)
SELECT * FROM source_table
WHERE  date_col > '<last saved max date>';      -- only new rows

Truncate the staging layer on every run

If staging still holds yesterday's rows, the next step will reprocess them. So we usually empty (truncate) staging before every load. That gives two kinds of staging:

Transient staging (~90% of cases)

Truncated on every run. It holds only the current batch.

Persistent staging (rare)

Keeps the history. Use it when the business needs a raw history of every load.

Interview

"How do you load only new data?" Incremental loading with CDC. Keep a watermark (the max timestamp or ID loaded so far), filter the source with WHERE col > watermark, then move the watermark forward after a successful load.

Hands-on: an incremental pipeline in Spark SQL

Setup: Databricks Community Edition (free). Search "Databricks Community Edition", sign up, then go to Workspace → Create → Notebook. Click Connect → Create, attach and run to start a free cluster. It shuts down after about 20 idle minutes, and recreating it wipes your databases. Set the default cell language to SQL (or type %sql at the top of a cell), and use %md for headings.

Spark SQL is just SQL. You don't need to know Spark. The Catalog tab works like the table tree in MySQL Workbench: metastore → catalog → database → table.

Step 1: source database and warehouse database

Spark SQL · DatabricksNot run
CREATE DATABASE sales;              -- pretend OLTP source
-- sales.orders: order_id, order_date, customer_id, customer_name, customer_email,
--   product_id, product_name, product_category, region_id, region_name, country,
--   quantity, unit_price, total_amount   (10 rows, one per day)

CREATE DATABASE sales_dwh;          -- the warehouse

Step 2: staging, transformation view, core

Spark SQL · initial loadNot run
-- STAGING: raw copy (initial load = everything)
CREATE TABLE sales_dwh.stg_sales AS
SELECT * FROM sales.orders;

-- TRANSFORMATION: a VIEW stores only the query, not the data
CREATE VIEW sales_dwh.trans_sales AS
SELECT * FROM sales_dwh.stg_sales
WHERE  quantity IS NOT NULL;        -- example cleaning rule

-- CORE: the curated table users query
CREATE TABLE sales_dwh.core_sales AS
SELECT * FROM sales_dwh.trans_sales;

Step 3: next day, 5 new rows arrive

Spark SQL · incremental runKey idea
-- STAGING: CREATE OR REPLACE = truncate + reload, only new rows (CDC)
CREATE OR REPLACE TABLE sales_dwh.stg_sales AS
SELECT * FROM sales.orders
WHERE  order_date > '2024-02-10';   -- last max date loaded

-- the view trans_sales now shows just the 5 new rows automatically

-- CORE: never replace it, APPEND to it
INSERT INTO sales_dwh.core_sales
SELECT * FROM sales_dwh.trans_sales;
Gotcha

Truncate the staging table, but never the core table. If you ran CREATE OR REPLACE on core, you'd lose the first 10 rows. Core grows with INSERT INTO (or MERGE).

Extra

The video hard-codes '2024-02-10'. In real pipelines the watermark lives in a small control table, and you read it with WHERE order_date > (SELECT last_date FROM watermark), then update it after the load. The runnable check at the bottom of this page does exactly this.

The core table here is still "one big table". The real serving layer is a dimensional model (facts and dimensions), which comes next.

Data modeling

Why not serve one big table? Real tables can have 200+ columns. They're hard for the business to understand, reports on them are hard to maintain, and they repeat the same data over and over (redundancy), which costs storage. Data modelling is the process of giving the data a structure.

Interview

"Normalization or dimensional modelling?" DBAs normalise OLTP databases (1NF, 2NF, 3NF) to avoid update anomalies. Data engineers building warehouses use dimensional modelling (facts and dimensions), which is a kind of logical data model built for fast, simple analytics.

Dimensional modelling: fact tables and dimension tables

Take the one big table and split it into one fact table in the middle and several dimension tables around it.

Fact table = the numbers

  • Holds the measures, the numbers you can add up: quantity, price, revenue, cost.
  • Holds the foreign keys that point to each dimension.
  • Sits at the most granular level: 1 source row = 1 fact row. No aggregation.

Dimension table = the context

  • Holds descriptive text and context: who, what, where, when.
  • No measures. (Keys are numbers too, but they aren't values you'd add up.)
  • One table per context: dim_customers, dim_products, dim_region, dim_date.

How to read it: "Revenue by customer" means you join the fact to dim_customers. "Revenue by month" means you join it to dim_date. The fact table supplies the number, and the dimension supplies the "by what".

Simple analogy

A shop receipt is a fact: "2 × item #202 for $40". The product catalogue (item #202 = Shirt, Clothing) is a dimension. You don't print the full product description on every receipt line. You print the code and look up the details when you need them.

Interview

"What's the relationship between a fact and a dimension?" Many-to-one. Many fact rows point to one dimension row, because a dimension stores each customer or product only once (distinct), while the fact table repeats them on every order.

Star schema vs snowflake schema

Once you've chosen a dimensional model, you pick a schema (its logical shape).

StarSnowflake
Shape1 fact plus dimensions, all joined directlySome dimensions joined through other dimensions (a hierarchy)
Joins per queryFewerMore
MaintenanceEasyHarder
Usage~90–99% of real projectsOnly when you really need it

Turning a snowflake into a star: join the child dimension into its parent (e.g. copy the category columns into dim_products). Every dimension then links straight to the fact.

Hands-on: building dimensions with surrogate keys

Always build the dimensions first. The fact table needs their keys, so they have to exist before it.

Pick the columns: one context = one dimension

Source columnsDimension
customer_id, customer_name, customer_emaildim_customers
product_id, product_name, product_categorydim_products
region_id, region_name, countrydim_region
order_datedim_date
order_id (nothing else describes it)stays in the fact (a degenerate dimension, see section 12)

What is a surrogate key?

customer_id = 101 means something to the business, so it's a business key. A surrogate key is a meaningless number (1, 2, 3, …) that the warehouse generates and uses for joins. You create it with ROW_NUMBER() in SQL, or monotonically_increasing_id() in PySpark.

Spark SQL · dim_customersKey idea
-- 1) empty table with a proper schema
CREATE TABLE order_dwh.dim_customers (
  customer_id        INT,
  dim_customers_key  INT,      -- surrogate key
  customer_name      STRING,
  customer_email     STRING
);

-- 2) view: DISTINCT first (in a subquery), THEN number the rows
CREATE OR REPLACE VIEW order_dwh.view_dim_customers AS
SELECT t.customer_id,
       ROW_NUMBER() OVER (ORDER BY t.customer_id) AS dim_customers_key,
       t.customer_name,
       t.customer_email
FROM (
  SELECT DISTINCT customer_id, customer_name, customer_email
  FROM order_dwh.trans_sales
) t;

-- 3) load
INSERT INTO order_dwh.dim_customers
SELECT * FROM order_dwh.view_dim_customers;     -- 10 orders → 7 customers
Gotcha (shown live in the video)

Writing SELECT DISTINCT ..., ROW_NUMBER() OVER (...) in a single SELECT gives you 10 rows, not 7. ROW_NUMBER runs first and makes every row unique, so DISTINCT has nothing left to remove. Do the DISTINCT in a subquery, then add ROW_NUMBER outside it.

Repeat the same pattern for the other dimensions:

Spark SQL · other dimensionsNot run
CREATE OR REPLACE VIEW order_dwh.view_dim_products AS
SELECT t.*, ROW_NUMBER() OVER (ORDER BY t.product_id) AS dim_products_key
FROM (SELECT DISTINCT product_id, product_name, product_category
      FROM order_dwh.trans_sales) t;                       -- 9 products

CREATE OR REPLACE VIEW order_dwh.view_dim_region AS
SELECT t.*, ROW_NUMBER() OVER (ORDER BY t.region_id) AS dim_region_key
FROM (SELECT DISTINCT region_id, region_name, country
      FROM order_dwh.trans_sales) t;                       -- 8 rows

CREATE OR REPLACE VIEW order_dwh.view_dim_date AS
SELECT t.*, ROW_NUMBER() OVER (ORDER BY t.order_date) AS dim_date_key
FROM (SELECT DISTINCT order_date FROM order_dwh.trans_sales) t;
-- DISTINCT on dates still matters: tomorrow there may be many orders per day

product_category repeats across products, which makes it a natural snowflake candidate: you could split it into a dim_category table. Keeping it inside dim_products keeps the model a star.

Hands-on: building the fact table (the key lookup)

Keep the order ID and the numeric columns. Replace every block of context columns with that dimension's surrogate key, which you fetch with a LEFT JOIN on the business key.

Spark SQL · fact_salesKey idea
CREATE TABLE order_dwh.fact_sales (
  order_id INT, quantity DECIMAL, unit_price DECIMAL, total_amount DECIMAL,
  dim_customers_key INT, dim_products_key INT, dim_region_key INT, dim_date_key INT
);

INSERT INTO order_dwh.fact_sales
SELECT f.order_id, f.quantity, f.unit_price, f.total_amount,
       dc.dim_customers_key,
       dp.dim_products_key,
       dr.dim_region_key,
       dd.dim_date_key
FROM order_dwh.trans_sales f
LEFT JOIN order_dwh.dim_customers dc ON f.customer_id = dc.customer_id
LEFT JOIN order_dwh.dim_products  dp ON f.product_id  = dp.product_id
LEFT JOIN order_dwh.dim_region    dr ON f.country     = dr.country      -- not region_id!
LEFT JOIN order_dwh.dim_date      dd ON f.order_date  = dd.order_date;
Gotcha (shown live in the video)

Joining dim_region on region_id blew the fact up from 10 rows to 26. Region 301 (North America) holds two countries, USA and Canada, so the dimension has two rows for region 301 and every matching order got duplicated. Join on the column that is unique in the dimension, which here is country, the most granular one.

Rule: after you build a fact, check that COUNT(*) still equals the source row count. If it's higher, a join is fanning out.

Using the model

Spark SQL · a typical report queryNot run
SELECT p.product_category, SUM(f.total_amount) AS revenue
FROM   order_dwh.fact_sales f
JOIN   order_dwh.dim_products p ON f.dim_products_key = p.dim_products_key
GROUP  BY p.product_category;

TypeOne row means…Example

Periodic snapshotMany transactions aggregated over a period (daily, weekly, monthly). Used more now that data is huge.Sales per store per month

CREATE TABLE fact_sales_monthly AS

       SUM(f.total_amount) AS revenue
FROM   fact_sales f JOIN dim_date d ON f.dim_date_key = d.dim_date_key
GROUP  BY 1, 2;          -- one row = one product's month

Types of dimension tables

Don't mix these up with slowly changing dimensions. That's a separate topic (next section).

1. Conformed dimension

One dimension shared by more than one fact table. dim_products is the same whether you're looking at orders or cancellations.

2. Role-playing dimension

One dimension used in several roles by the same fact. dim_date can be the order date (the active relationship) and also the cancel date (an inactive one, in Power BI terms).

SQL · role-playing date via aliasesNot run
SELECT od.order_date, cd.order_date AS cancel_date, f.order_id
FROM   fact_orders f
JOIN   dim_date od ON f.order_date_key  = od.dim_date_key   -- role: order date
LEFT JOIN dim_date cd ON f.cancel_date_key = cd.dim_date_key; -- role: cancel date

3. Junk dimension

The video describes it as a dimension with only a handful of rows (for example 2 countries in 1 continent, or flag-like values).

Extra: Kimball's exact definition

In Kimball's book, a junk dimension gathers several low-cardinality flags (is_gift, payment_type, is_promo…) into one small table, usually every possible combination. That way the fact needs one key instead of lots of tiny dimensions or flag columns. Use this definition in interviews.

4. Degenerate dimension

A key that has no other descriptive columns, such as order_id. A dimension built from it would hold only one column, so it stays in the fact table as is. That's exactly what we did with order_id in section 10.

Interview

A common question: "Role-playing vs junk vs degenerate?" Role-playing means one dimension used in many roles. Junk means many small flags combined into one dimension. Degenerate means a dimension key with no dimension table, kept in the fact.

Slowly Changing Dimensions (SCD)

The problem: dimension values change over time. A product gets renamed or moves to a new category, and new products launch. You can't rebuild the whole dimension every time. SCD types are the standard ways to handle these changes.

Types 4, 5 and 6 exist but are rarely used, much like normal forms beyond 3NF. In practice you need types 0 to 2, plus awareness of type 3.

TypeWhat happens on a changeHistory?
SCD 0Nothing. Values never change.—
SCD 1Upsert (update + insert): overwrite the old value, and insert rows for new IDs.No
SCD 2Expire the old row and insert a new version, tracked with start_date, end_date and is_current.Full
SCD 3Add a previous_value column.Only the last value

Example: product 3 "Comb" moves from Clothing to Hair care.

The far-future end date (3000-12-31) means "still active". The old row is closed, and a new row becomes current.

Interview

"When would you use SCD 2?" When the business needs to report as of a point in time. For example, Finance wants last year's sales under the category the product had last year. SCD 1 would rewrite history into the new category.

Spark SQL / Delta · SCD 2Not run
-- (Extra: the video explains SCD 2 conceptually; this is one standard way to code it)
-- 1) expire current rows whose tracked column changed
MERGE INTO dim_products_scd2 AS t
USING view_dim_products      AS s
ON  t.product_id = s.product_id AND t.is_current = 'Y'
WHEN MATCHED AND t.product_category <> s.product_category THEN
  UPDATE SET t.end_date = current_date(), t.is_current = 'N';

-- 2) insert a new current version for changed rows and brand-new IDs
INSERT INTO dim_products_scd2
SELECT s.product_id, s.product_name, s.product_category,
       current_date() AS start_date, DATE '3000-12-31' AS end_date, 'Y' AS is_current
FROM   view_dim_products s
LEFT JOIN dim_products_scd2 t
       ON t.product_id = s.product_id AND t.is_current = 'Y'
WHERE  t.product_id IS NULL;      -- no current row = new or just expired

Hands-on: SCD Type 1 with MERGE

Rule: if the ID already exists, update it. If it's new, insert it. In Spark SQL (Delta tables), one MERGE statement does both.

Spark SQL · initial loadNot run
CREATE DATABASE sales_scd;
-- sales_scd.orders : same 10-row source as before

CREATE TABLE sales_scd.dim_products (
  product_id INT, product_name STRING, product_category STRING
);

CREATE OR REPLACE VIEW sales_scd.view_dim_products AS
SELECT DISTINCT product_id, product_name, product_category
FROM   sales_scd.orders;

INSERT INTO sales_scd.dim_products
SELECT * FROM sales_scd.view_dim_products;          -- 9 products

Next day, two new orders arrive. One renames product 201 from "Laptop" to "Gaming Laptop", and one is for a brand-new product 230, "Earpods". The view gets the CDC filter so it only reads those two rows:

Spark SQL · MERGE = upsertKey idea
CREATE OR REPLACE VIEW sales_scd.view_dim_products AS
SELECT DISTINCT product_id, product_name, product_category
FROM   sales_scd.orders
WHERE  order_date > '2024-02-10';                  -- incremental (CDC)

MERGE INTO sales_scd.dim_products     AS target
USING      sales_scd.view_dim_products AS source
ON         target.product_id = source.product_id
WHEN MATCHED     THEN UPDATE SET *                  -- existing id → overwrite
WHEN NOT MATCHED THEN INSERT *;                     -- new id → insert

Result: the dimension has 10 rows, not 11. Product 201 now reads "Gaming Laptop", and product 230 was added.

Gotcha

INSERT INTO dim SELECT * FROM orders fails with a column count or "duplicate column" error. Select only the dimension's own columns (through the view), never * from the big source table.

Interview Q&A

Click an answer to reveal it.

Database vs data warehouse?

Same kind of storage (tables). A database is OLTP: small, constant, real-time writes. A warehouse is loaded in bulk batches and serves heavy analytical reads, so reports don't slow down the live system.

What are the staging and core layers?

Staging is a raw, as-is copy of the source (usually transient, truncated each run). Core is the transformed, curated data that users query. Data marts are domain subsets of core.

Transient vs persistent staging?

Transient is truncated every load and holds only the current batch (about 90% of cases). Persistent keeps the history of every load.

What is incremental loading and CDC?

Loading only new or changed rows. Store a watermark (the max date or ID loaded), read WHERE col > watermark, then move the watermark forward.

Conceptual vs logical vs physical model?

Conceptual: which entities exist. Logical: how they relate (keys, attributes; ER, normalisation or dimensional). Physical: actual tables with data types and constraints.

Fact vs dimension?

A fact holds additive measures plus foreign keys, at the finest grain. A dimension holds descriptive context, one table per context, with distinct rows. Fact to dimension is many-to-one.

Which do you build first, dimensions or the fact?

Dimensions. The fact needs their surrogate keys.

What is a surrogate key and why use it?

A meaningless warehouse-generated integer (ROW_NUMBER, an identity column, monotonically_increasing_id). It decouples the model from source business keys and makes SCD 2 possible, because the same business key can have several versions.

Star vs snowflake?

Star: every dimension joins the fact directly (the common choice). Snowflake: dimensions are normalised into hierarchies, so some reach the fact indirectly. That means more joins and harder maintenance.

Your fact table has more rows than the source. Why?

A join is fanning out because the join key isn't unique in the dimension (as with region_id vs country in the video). Join on the dimension's unique grain.

Types of fact tables?

Transactional (1 row = 1 transaction), periodic snapshot (1 row = an aggregate over a period), accumulating snapshot (1 row = one process with many milestone dates).

Conformed, role-playing, junk, degenerate?

Conformed: shared by several facts. Role-playing: one dimension used in several roles (order date, cancel date). Junk: low-cardinality flags grouped into one dimension. Degenerate: a key like order_id kept in the fact with no dimension table.

SCD 1 vs SCD 2 vs SCD 3?

SCD 1 overwrites (upsert, no history). SCD 2 adds a new row version with start date, end date and a current flag (full history). SCD 3 adds a previous-value column (one step of history).

How do you implement SCD 1 in Spark SQL?

MERGE INTO dim USING src ON key WHEN MATCHED THEN UPDATE SET * WHEN NOT MATCHED THEN INSERT *.

Runnable check of all the core logic

Plain Python with the built-in sqlite3 module, so nothing needs installing. It covers incremental loading with a watermark, DISTINCT before ROW_NUMBER, the fact key lookup without fan-out, SCD 1 upsert and SCD 2 versioning. Run it with python check.py. It prints all checks passed.

Python · sqlite3Ran
import sqlite3
db = sqlite3.connect(":memory:")
q = lambda s: db.execute(s).fetchall()
db.executescript("""
CREATE TABLE orders(order_id INT, order_date TEXT, customer_id INT, customer_name TEXT,
  product_id INT, product_name TEXT, category TEXT, region TEXT, country TEXT, quantity INT, total REAL);
INSERT INTO orders VALUES
 (1,'2024-02-01',101,'Asha',201,'Laptop','Electronics','North America','USA',1,900),
 (2,'2024-02-02',102,'Ravi',202,'Shirt','Clothing','North America','Canada',2,40),
 (3,'2024-02-03',101,'Asha',202,'Shirt','Clothing','North America','USA',1,20);

-- watermark table (CDC by date)
CREATE TABLE watermark(last_date TEXT); INSERT INTO watermark VALUES('1900-01-01');
""")

def load_staging():
    db.executescript("""
    DROP TABLE IF EXISTS stg_sales;  -- transient staging: truncate every run
    CREATE TABLE stg_sales AS SELECT * FROM orders
      WHERE order_date > (SELECT last_date FROM watermark);
    UPDATE watermark SET last_date = (SELECT COALESCE(MAX(order_date), last_date) FROM stg_sales);
    """)

load_staging()
assert q("SELECT COUNT(*) FROM stg_sales") == [(3,)]
db.execute("INSERT INTO orders VALUES (4,'2024-02-04',103,'Meena',203,'Honey','Food','Asia','India',3,15)")
load_staging()
assert q("SELECT order_id FROM stg_sales") == [(4,)]          # only the new row

# dimension with surrogate key: DISTINCT first (subquery), ROW_NUMBER after
db.executescript("""
CREATE TABLE dim_customers AS
SELECT t.*, ROW_NUMBER() OVER (ORDER BY customer_id) AS dim_customer_key
FROM (SELECT DISTINCT customer_id, customer_name FROM orders) t;
CREATE TABLE dim_region AS
SELECT t.*, ROW_NUMBER() OVER (ORDER BY country) AS dim_region_key
FROM (SELECT DISTINCT region, country FROM orders) t;
CREATE TABLE fact_sales AS
SELECT f.order_id, f.quantity, f.total, dc.dim_customer_key, dr.dim_region_key
FROM orders f
LEFT JOIN dim_customers dc ON f.customer_id = dc.customer_id
LEFT JOIN dim_region   dr ON f.country = dr.country;
""")
assert q("SELECT COUNT(*) FROM dim_customers") == [(3,)]       # 4 orders, 3 customers
assert q("SELECT COUNT(*) FROM fact_sales") == [(4,)]          # fact keeps grain, no fan-out
assert q("SELECT COUNT(*) FROM fact_sales WHERE dim_customer_key IS NULL OR dim_region_key IS NULL") == [(0,)]

# SCD type 1: upsert
db.executescript("""
CREATE TABLE dim_products(product_id INT PRIMARY KEY, product_name TEXT, category TEXT);
INSERT INTO dim_products SELECT DISTINCT product_id, product_name, category FROM orders;
INSERT INTO dim_products VALUES (201,'Gaming Laptop','Electronics'),(230,'Earpods','Electronics')
  ON CONFLICT(product_id) DO UPDATE SET product_name=excluded.product_name, category=excluded.category;
""")
assert q("SELECT product_name FROM dim_products WHERE product_id=201") == [("Gaming Laptop",)]
assert q("SELECT COUNT(*) FROM dim_products") == [(4,)]

# SCD type 2: expire old row, insert new version
db.executescript("""
CREATE TABLE dim_prod_scd2(product_id INT, category TEXT, start_date TEXT, end_date TEXT, is_current TEXT);
INSERT INTO dim_prod_scd2 VALUES (3,'Clothing','2024-01-01','3000-12-31','Y');
CREATE TABLE src(product_id INT, category TEXT); INSERT INTO src VALUES (3,'Hair care');
UPDATE dim_prod_scd2 SET end_date='2024-01-02', is_current='N'
 WHERE is_current='Y' AND product_id IN
