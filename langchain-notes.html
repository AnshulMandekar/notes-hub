Recap: what LangChain is and why it exists

Interview · definition

LangChain is an open-source framework for building LLM-powered applications. It gives you ready-made building blocks (models, prompts, loaders, splitters, vector stores, retrievers, parsers) and a way to wire them into pipelines.

The "chat with your PDF" app that motivates it

A user uploads a book and asks questions about it. You cannot send a 1,000-page book to the LLM with every question, so you search for the few relevant pages first and send only those.

Why LangChain (benefits)

  • Chains: output of one step automatically becomes input of the next.
  • Model-agnostic: switch OpenAI to Gemini or Claude by changing 1 to 2 lines.
  • Complete ecosystem: dozens of loaders, splitters, embedding models and vector stores behind one interface.
  • Memory and state handling for follow-up questions ("also give interview questions on this algorithm").

What people build with it

  • Conversational chatbots (first line of customer support)
  • AI knowledge assistants that know your data (a course chatbot)
  • AI agents: chatbots that also act (book the cheapest flight)
  • Workflow automation
  • Summarization and research helpers for private or huge documents
Interview · alternatives

LangChain is not the only option. LlamaIndex and Haystack solve similar problems. The choice depends on pricing, team familiarity and fit for the use case.

LangChain components

Six components. Learn what problem each one solves and you understand most of LangChain. You already have a detailed page on this video, LangChain Components, so this is the condensed version.

ComponentProblem it solvesKey idea
ModelsEvery provider's API is differentStandard interface. Two kinds: language models (text to text) and embedding models (text to vector)
PromptsLLM output is very sensitive to the inputTemplates with placeholders, role-based messages, few-shot examples
ChainsManually passing output from step to stepSequential, parallel and conditional pipelines
IndexesThe LLM never saw your private dataLoader, splitter, vector store, retriever
MemoryLLM API calls are statelessSend past context: full buffer, last N turns, a summary, or custom facts
AgentsChatbots can talk but cannot actLLM reasoning plus tools (weather API, calculator)
Interview · memory types
  • Conversation buffer: whole history every call. Full context, cost grows with the chat.
  • Buffer window: last N interactions only. Bounded cost, forgets older turns.
  • Summarizer-based: a running summary instead of raw text. Fewer tokens.
  • Custom: store chosen facts (preferences, key details).
Beyond the video

The memory classes are legacy now. In Video 10 Nitish says memory moved to LangGraph, and that is where your LangGraph notes cover it (checkpointers and threads).

Models

Interview · definition

The Model component is a common interface for talking to different AI models. It supports two kinds: language models (text in, text out, used for chatbots and agents) and embedding models (text in, vector out, used for semantic search and RAG).

LLMs vs chat models

FeatureLLM (base model)Chat model (instruction tuned)
PurposeFree-form text generationMulti-turn conversation
TrainingGeneral text: books, articles, WikipediaSame, then fine-tuned on chat datasets
MemoryNo idea of conversation historyTakes a list of messages, so history can be sent
Role awarenessNoneUnderstands system, user and assistant roles
Input / outputString to stringList of messages to an AIMessage
Base classBaseLLM (e.g. OpenAI)BaseChatModel (e.g. ChatOpenAI)
Use forText generation, summarization, translation, codeChatbots, assistants, support bots, AI tutors, agents
Interview

"Which should a new project use?" Chat models. LangChain is phasing out the plain LLM interface, and almost every app being built today is conversational.

Setup

  1. Make a folder, open it in VS Code, then python -m venv venv and activate it (venv\Scripts\activate on Windows).
  2. Put the libraries in requirements.txt and run pip install -r requirements.txt. Check with import langchain; print(langchain.__version__).
  3. Create a .env file for secret keys and call load_dotenv() in code. Never write keys in the code.

Gotcha · key names

Use these exact variable names. The integration packages look up these names, so a renamed variable means "API key not found". OpenAI also needs a paid balance (about $5 is plenty for the whole playlist).

Model names in the video (gpt-4, claude-3-5-sonnet, gemini-1.5-pro) get retired over time. Copy a current name from each provider's models page.

The two parameters you will tune

temperature

Controls the randomness of the output. Near 0, the same input gives the same output every time. Higher values give a different, more varied answer on each run.

0 to 0.3Factual answers, maths, code
0.5 to 0.7General Q&A, explanations
0.9 to 1.2Stories, poems, jokes
1.5 and upBrainstorming, very diverse ideas

max_completion_tokens

Caps how many tokens come back. Paid APIs charge per token (prices are quoted per million tokens), so this is a cost control. A token is roughly a word, but not exactly.

With max_completion_tokens=10 the poem stops after about 10 tokens.

Gotcha · corrected in Video 4

Video 3 called temperature a "creativity" knob from 0 to 2. Nitish corrected it at the start of Video 4: what it really controls is how repeatable the output is. Temperature 0 gives the same poem on every run for the same prompt; 1.5 gives a noticeably different poem each time.

Open-source models

Freely available models you can download, modify, fine-tune and deploy without a central provider. Famous ones: LLaMA, Mistral, Falcon, BLOOM, DeepSeek, Qwen. Hugging Face is the largest repository of them.

Why open source

  • Cost: no per-token bill when run locally
  • Control: modify, fine-tune, deploy anywhere
  • Data privacy: confidential data never leaves your machine
  • Customization: fine-tune on your own dataset

Downsides

  • Big models need expensive GPUs. TinyLlama (1.1B) took about 10 minutes on an 8 GB laptop and froze it.
  • Setup is more work
  • Less refined answers: less RLHF (fine-tuning on human feedback)
  • Mostly text-only (limited multimodal)

Embedding models

    "Delhi is the capital of India",
    "Kolkata is the capital of West Bengal",
    "Paris is the capital of France",

# Free, local, about 90 MB, returns 384-dimension vectors
hf = HuggingFaceEmbeddings(model_name="sentence-transformers/all-MiniLM-L6-v2")
Interview · dimensions

OpenAI's default size is 1536 (small) or 3072 (large). A bigger vector captures more meaning but costs more to store and compare. Embedding calls are cheap because the output is just numbers, and in Nitish's experience OpenAI's embeddings beat the free ones on quality.

Mini project: document similarity search

Embed five sentences about cricketers once, embed the user's question, and return the sentence whose vector points in the most similar direction (highest cosine similarity).

document_similarity.pyRan · fake embeddings
import numpy as np
from dotenv import load_dotenv
from langchain_openai import OpenAIEmbeddings
from sklearn.metrics.pairwise import cosine_similarity

load_dotenv()
embedding = OpenAIEmbeddings(model="text-embedding-3-large", dimensions=300)

documents = [
    "Virat Kohli is an Indian cricketer known for his aggressive batting and leadership.",
    "MS Dhoni is a former Indian captain famous for his calm demeanor and finishing skills.",
    "Sachin Tendulkar, also known as the 'God of Cricket', holds many batting records.",
    "Rohit Sharma is known for his elegant batting and record-breaking double centuries.",
    "Jasprit Bumrah is an Indian fast bowler known for his unorthodox action and yorkers.",
]
query = "tell me about bumrah"

doc_embeddings = embedding.embed_documents(documents)
query_embedding = embedding.embed_query(query)

scores = cosine_similarity([query_embedding], doc_embeddings)[0]   # both arguments must be 2D
best = int(np.argmax(scores))
print(documents[best], "| similarity:", round(float(scores[best]), 3))
Gotcha

cosine_similarity expects two 2D lists, so wrap the single query vector in [ ]. Also, this code re-embeds the documents on every run. In a real app you embed once and store the vectors in a vector database, then only embed new queries. That lookup step is called retrieval.

Prompts

A prompt is the message you send to an LLM. Prompts can be multimodal (image, audio, video), but this video is about text prompts, which is what you use most of the time. Small wording changes can change the output a lot, which is why a whole job, prompt engineering, grew around them.

Static vs dynamic prompts

Example: a research-paper summarizer built with Streamlit.

PromptTemplate

prompt_template.pyRan
from langchain_core.prompts import PromptTemplate

template = PromptTemplate(
    template="Summarize the paper '{paper}' in a {style} style, {length} long.",
    input_variables=["paper", "style", "length"],
    validate_template=True,        # error at build time if placeholders and input_variables differ
)
prompt = template.invoke({"paper": "Attention Is All You Need", "style": "beginner", "length": "short"})
print(prompt.to_string())

# In the Streamlit app the values come from st.selectbox(...), then:
# result = (template | model).invoke({...}); st.write(result.content)
Interview · why not f-strings?
  1. Validation: with validate_template=True, a missing or extra variable fails during development, not on the server.
  2. Reusability: save a template to JSON once and load it in any file or page.
  3. Ecosystem fit: a template is a LangChain component, so it plugs into chains: template | model, invoked once. An f-string cannot.
save and load a templateRan
# As taught (works, but deprecated since langchain-core 1.2.21):
template.save("template.json")
from langchain_core.prompts import load_prompt
template = load_prompt("template.json")

# Current replacement:
from langchain_core.load import dumps, loads
open("template.json", "w").write(dumps(template, pretty=True))
template = loads(open("template.json").read())

A console chatbot, and why it needs history

First version: loop, read input, model.invoke(user_input). Ask "which is greater, 2 or 0?" then "multiply the bigger number by 10" and it answers "10x": it has no memory. Fix 1: keep a chat_history list and send the whole list. Fix 2: label every message with who said it, otherwise a long history confuses the model.

chatbot.pyRan · fake model
from dotenv import load_dotenv
from langchain_core.messages import AIMessage, HumanMessage, SystemMessage
from langchain_openai import ChatOpenAI

load_dotenv()
model = ChatOpenAI()

chat_history = [SystemMessage(content="You are a helpful AI assistant")]

while True:
    user_input = input("You: ")
    if user_input == "exit":
        break
    chat_history.append(HumanMessage(content=user_input))
    result = model.invoke(chat_history)            # invoke accepts a whole list of messages
    chat_history.append(AIMessage(content=result.content))
    print("AI:", result.content)

SystemMessageYou, once at the start: sets role and behaviour"You are a knowledgeable doctor"
HumanMessageThe user"Tell me about LangChain"
AIMessageThe model's reply"LangChain is a framework..."

The two ways to call invoke

ChatPromptTemplate and MessagesPlaceholder

chat_prompt_template.pyRan
from langchain_core.messages import AIMessage, HumanMessage
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder

# Dynamic system and human messages: use (role, text) tuples
chat_template = ChatPromptTemplate([
    ("system", "You are a helpful {domain} expert"),
    ("human", "Explain in simple terms, what is {topic}"),
])
print(chat_template.invoke({"domain": "cricket", "topic": "Doosra"}))

# Customer support: load yesterday's chat from the DB into the middle of the prompt
support = ChatPromptTemplate([
    ("system", "You are a helpful customer support agent"),
    MessagesPlaceholder(variable_name="chat_history"),
    ("human", "{query}"),
])
chat_history = [
    HumanMessage(content="I want to request a refund for my order #12345."),
    AIMessage(content="Your refund request has been initiated. It will be processed in 3-5 business days."),
]
prompt = support.invoke({"chat_history": chat_history, "query": "Where is my refund?"})
# -> SystemMessage, HumanMessage (old), AIMessage (old), HumanMessage (today)
Gotcha · placeholders not filled

ChatPromptTemplate([SystemMessage(content="You are a {domain} expert")]) does not fill {domain}; the braces come out literally. Use ("system", "...") tuples (or ChatPromptTemplate.from_messages with tuples). Verified on langchain-core 1.5.

Interview
  • PromptTemplate vs ChatPromptTemplate: both fill placeholders at runtime. The first builds one single-turn prompt; the second builds a list of role-tagged messages for chat models.
  • MessagesPlaceholder: a slot inside a ChatPromptTemplate where a whole list of messages (usually stored chat history) is inserted at runtime.

Structured output

Video 4 was about the LLM's input. Videos 5 and 6 are about its output. By default an LLM replies in free text, which is unstructured: fine for a human, useless for a database or an API.

Unstructured

"Here is a suggested itinerary: Morning, visit the Eiffel Tower. Afternoon, a museum. Evening, dinner."

Structured

[{"time": "Morning", "activity": "Visit the Eiffel Tower"},
 {"time": "Afternoon", "activity": "Walk through a museum"},
 {"time": "Evening", "activity": "Dinner at a cafe"}]
Interview · definition

Structured output means making a language model return its answer in a well-defined data format (such as JSON that follows a schema) so programs can parse it. Its big benefit: the LLM can now talk to machines (databases, APIs, tools), not only to humans.

Three use cases from the video

  • Data extraction: a job portal like Naukri pulls name, last company, 10th/12th/college marks out of uploaded resumes and inserts them into a database.
  • API building: turn long Amazon reviews into topics, pros, cons and sentiment, then serve them through FastAPI.
  • Agents: a calculator tool cannot take "find the square root of 2". The agent must extract {"op": "sqrt", "x": 2} first. Every tool call needs structured output.

Two kinds of LLMs

Interview · what happens behind the scenes

with_structured_output turns your schema into instructions for the model (roughly a system prompt like "extract a summary and a sentiment, return JSON in this format", or a tool/function definition) and parses the model's JSON reply into a dict or object. That is why it works even though your prompt never asked for a summary.

Schema option 1: TypedDict

A TypedDict declares which keys a dict should have and their types. It only gives type hints to your editor: Python does not stop you from putting a string in an int field.

with_structured_output_typeddict.pyNeeds OPENAI_API_KEY · not run
from typing import Annotated, Literal, Optional, TypedDict
from dotenv import load_dotenv
from langchain_openai import ChatOpenAI

load_dotenv()
model = ChatOpenAI()

class Review(TypedDict):
    key_themes: Annotated[list[str], "Write down all the key themes discussed in the review in a list"]
    summary: Annotated[str, "A brief summary of the review"]
    sentiment: Annotated[Literal["pos", "neg"], "Return sentiment of the review, either positive or negative"]
    pros: Annotated[Optional[list[str]], "Write down all the pros inside a list"]
    cons: Annotated[Optional[list[str]], "Write down all the cons inside a list"]
    name: Annotated[Optional[str], "Write the name of the reviewer"]

structured_model = model.with_structured_output(Review)
result = structured_model.invoke("""I recently upgraded to the Samsung Galaxy S24 Ultra ... The 200MP camera is stunning,
but the weight makes one-handed use uncomfortable and the $1,300 price is hard to swallow.
Review by Nitish Singh""")
print(result["summary"], result["sentiment"], result["name"])   # a plain dict
  • Annotated[type, "description"]: adds a hint so the LLM knows exactly what to put there.
  • Literal["pos", "neg"]: restrict a field to fixed values (handy when it goes into a database).
  • Optional[...]: the field may be missing, for example when the review names no reviewer.

Schema option 2: Pydantic (the go-to choice)

Pydantic is a data validation and parsing library (FastAPI uses it). Same idea as TypedDict, but it actually checks the data and raises an error when it is wrong.

pydantic_demo.pyRan
from typing import Optional
from pydantic import BaseModel, EmailStr, Field   # EmailStr needs: pip install email-validator

class Student(BaseModel):
    name: str = "nitish"                       # default value
    age: Optional[int] = None                  # optional fields need a default (None)
    email: EmailStr                            # built-in email validation
    cgpa: float = Field(gt=0, lt=10, default=5, description="Decimal value representing the CGPA")

s = Student(age="32", email="abc@gmail.com")
print(s.age, type(s.age))       # 32 int  -> "32" was coerced to int (type coercion)
print(s.model_dump())           # to a Python dict
print(s.model_dump_json())      # to a JSON string

Student(email="abc")            # ValidationError: not a valid email
Student(email="a@b.com", cgpa=12)   # ValidationError: cgpa must be < 10
with_structured_output_pydantic.pyNeeds OPENAI_API_KEY · schema ran
from typing import Literal, Optional
from pydantic import BaseModel, Field

class Review(BaseModel):
    key_themes: list[str] = Field(description="All the key themes discussed in the review")
    summary: str = Field(description="A brief summary of the review")
    sentiment: Literal["pos", "neg"] = Field(description="Sentiment of the review")
    pros: Optional[list[str]] = Field(default=None, description="All the pros in a list")
    cons: Optional[list[str]] = Field(default=None, description="All the cons in a list")
    name: Optional[str] = Field(default=None, description="Name of the reviewer")

result = model.with_structured_output(Review).invoke(review_text)
print(result.name)            # a Pydantic object: use attribute access, not result["name"]
Gotcha · dict vs object

TypedDict and JSON Schema give back a dict (result["name"]). Pydantic gives back an object (result.name, or dict(result) / result.model_dump()). Mixing them up raises "object is not subscriptable".

Schema option 3: JSON Schema

Use it when the schema must be shared across languages, for example a Python backend and a JavaScript frontend. JSON is understood everywhere.

review_schema.json (shortened)
{
  "title": "Review",
  "type": "object",
  "properties": {
    "key_themes": {"type": "array", "items": {"type": "string"}, "description": "All key themes"},
    "summary":    {"type": "string", "description": "A brief summary of the review"},
    "sentiment":  {"type": "string", "enum": ["pos", "neg"], "description": "Sentiment"},
    "name":       {"type": ["string", "null"], "description": "Name of the reviewer"}
  },
  "required": ["key_themes", "summary", "sentiment"]
}

Interview · the method argument

with_structured_output(schema, method=...) chooses how the model is asked:

  • "json_mode": the model is told to answer in JSON.
  • "function_calling": the schema is sent as a tool definition. Natural fit for agents calling tools.

The video's rule of thumb: function calling for OpenAI, JSON mode for Claude and Gemini.

Beyond the video

On current langchain-openai (checked on 1.5.2) the default is a third option, method="json_schema", which uses OpenAI's native Structured Outputs so the reply is constrained to your schema.

Gotcha · not every model can do it

Swap ChatOpenAI for ChatHuggingFace with TinyLlama and with_structured_output throws an error: that model supports neither JSON mode nor function calling. That is exactly the problem output parsers solve.

Output parsers

Interview · definition

Output parsers convert raw LLM text into structured formats (JSON, CSV, Pydantic models...). They give consistency, validation and ease of use, and they work with any model, including ones that cannot do structured output natively.

1. StrOutputParser

Takes the model's reply and returns just the text. That sounds like result.content, and it is, but it matters inside chains: it lets the output of one model flow straight into the next prompt.

str_output_parser.pyRan · fake model
from dotenv import load_dotenv
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import PromptTemplate
from langchain_openai import ChatOpenAI

load_dotenv()
model = ChatOpenAI()
parser = StrOutputParser()

template1 = PromptTemplate(template="Write a detailed report on {topic}", input_variables=["topic"])
template2 = PromptTemplate(template="Write a 5 line summary on the following text.\n{text}", input_variables=["text"])

chain = template1 | model | parser | template2 | model | parser
print(chain.invoke({"topic": "black hole"}))
Beyond the video

Note the template in the CampusX repo writes /n; the newline is \n.

2. JsonOutputParser

json_output_parser.pyRan · fake model
from langchain_core.output_parsers import JsonOutputParser

parser = JsonOutputParser()
template = PromptTemplate(
    template="Give me 5 facts about {topic}\n{format_instruction}",
    input_variables=["topic"],
    partial_variables={"format_instruction": parser.get_format_instructions()},  # filled before runtime
)
chain = template | model | parser
print(chain.invoke({"topic": "black hole"}))      # a dict, e.g. {"facts": [...]}

# Without a chain: parser.parse(model.invoke(template.invoke({...})).content)
Gotcha · two traps
  • If the template has no input variables, still call chain.invoke({}) with an empty dict, or you get "missing 1 required positional argument: input".
  • JsonOutputParser does not enforce a schema. Ask for 5 facts and the LLM decides the shape ({"facts": [...]} one day, something else the next).
Interview · partial variables

partial_variables are placeholders filled when the template is built, not by the user at runtime. The format instructions are a typical example.

3. StructuredOutputParser

Lets you dictate the JSON shape with a list of ResponseSchema objects.

structured_output_parser.pyRan · parse step
# LangChain 1.x: pip install langchain-classic (was: from langchain.output_parsers import ...)
from langchain_classic.output_parsers import ResponseSchema, StructuredOutputParser

schema = [
    ResponseSchema(name="fact_1", description="Fact 1 about the topic"),
    ResponseSchema(name="fact_2", description="Fact 2 about the topic"),
    ResponseSchema(name="fact_3", description="Fact 3 about the topic"),
]
parser = StructuredOutputParser.from_response_schemas(schema)
template = PromptTemplate(
    template="Give 3 facts about {topic}\n{format_instruction}",
    input_variables=["topic"],
    partial_variables={"format_instruction": parser.get_format_instructions()},
)
chain = template | model | parser
print(chain.invoke({"topic": "black hole"}))      # {"fact_1": ..., "fact_2": ..., "fact_3": ...}
Gotcha

It enforces the shape but does no validation: ask for an integer age and "35 years" still comes through. Also, it was never in langchain_core (not reused enough) and on LangChain 1.x it moved to langchain_classic.

4. PydanticOutputParser

pydantic_output_parser.pyRan · fake model
from langchain_core.output_parsers import PydanticOutputParser
from pydantic import BaseModel, Field

class Person(BaseModel):
    name: str = Field(description="Name of the person")
    age: int = Field(gt=18, description="Age of the person")
    city: str = Field(description="Name of the city the person belongs to")

parser = PydanticOutputParser(pydantic_object=Person)
template = PromptTemplate(
    template="Generate the name, age and city of a fictional {place} person\n{format_instruction}",
    input_variables=["place"],
    partial_variables={"format_instruction": parser.get_format_instructions()},
)
chain = template | model | parser
print(chain.invoke({"place": "Sri Lankan"}))   # Person(name='...', age=32, city='Kandy')

Chains

Every LLM app is a set of small steps: take input, build the prompt, call the LLM, process the reply. Doing each step by hand means calling invoke on each piece and copying results between them. A chain joins the steps into a pipeline: the output of each step becomes the input of the next, and you only feed the first step. LangChain is named after this idea.

Interview · LCEL

The | pipe syntax (prompt | model | parser) is the LangChain Expression Language (LCEL), a declarative way to build chains. chain.get_graph().print_ascii() prints the pipeline.

Gotcha

print_ascii() needs the grandalf package: pip install grandalf, otherwise it raises an ImportError.

from langchain_core.output_parsers import PydanticOutputParser
from langchain_core.runnables import RunnableBranch, RunnableLambda
from pydantic import BaseModel, Field

    sentiment: Literal["positive", "negative"] = Field(description="Give the sentiment of the feedback")

parser2 = PydanticOutputParser(pydantic_object=Feedback)
prompt1 = PromptTemplate(
    template="Classify the sentiment of the following feedback text into positive or negative\n{feedback}\n{format_instruction}",
    input_variables=["feedback"],

)

prompt3 = PromptTemplate(template="Write an appropriate response to this negative feedback\n{feedback}", input_variables=["feedback"])

)

Gotcha · why the Pydantic parser

A plain StrOutputParser might return "Positive", "positive." or "The sentiment is positive", and the branch conditions would never match. Forcing Literal["positive", "negative"] makes the classifier output consistent. The default branch must be a runnable, so a plain lambda is wrapped in RunnableLambda.

Beyond the video · subtle bug

The branch receives the Feedback object, not the customer's text. A one-variable prompt wraps whatever it gets, so prompt2 becomes "Write an appropriate response to this positive feedback sentiment='positive'" (checked). The reply sounds fine but never sees what the customer wrote. To fix it, carry the original input along with RunnableParallel + RunnablePassthrough (Video 9). Runnables: why they exist

Chains work because every piece in them is a Runnable. This video explains, through LangChain's history, why runnables were invented, then builds the idea from scratch in plain Python.

The story

ComponentOld way to call itAfter runnables
LLMllm.predict(prompt)invoke
Prompt templatetemplate.format(**values)invoke
Retrieverretriever.get_relevant_documents(q)invoke
Output parserparser.parse(text)invoke
Interview · what is a Runnable?
  1. A unit of work: takes an input, processes it, returns an output.
  2. Follows a common interface: every runnable has invoke (one input), batch (many inputs), stream (output as it is produced), plus async versions.
  3. Runnables connect: the output of R1 automatically becomes the input of R2.
  4. A workflow made of runnables is itself a runnable, so chains can be connected to other chains.

Analogy: Lego blocks. Each block has its own shape and purpose, all share the same studs, they snap together, and a built structure still has studs so it snaps onto other structures.

Building it from scratch

Step 1, the problem: a NakliLLM with predict and a NakliPromptTemplate with format. A NakliLLMChain(llm, prompt) class can glue exactly those two, but it cannot do two LLM calls (joke, then explanation). Step 2, the fix: make every component inherit one abstract class.

runnables_from_scratch.pyRan
import random
from abc import ABC, abstractmethod

class Runnable(ABC):
    @abstractmethod
    def invoke(self, input_data):      # every child MUST implement invoke
        ...

class NakliLLM(Runnable):
    def invoke(self, prompt):
        return {"response": random.choice(["Delhi is the capital of India", "IPL is a cricket league"])}

    def predict(self, prompt):         # keep the old method so old code still runs, but warn
        print("predict() is deprecated, use invoke()")
        return self.invoke(prompt)

class NakliPromptTemplate(Runnable):
    def __init__(self, template, input_variables):
        self.template = template
        self.input_variables = input_variables

    def invoke(self, input_dict):
        return self.template.format(**input_dict)

class NakliStrOutputParser(Runnable):
    def invoke(self, input_data):
        return input_data["response"]

class RunnableConnector(Runnable):     # the "chain": connects any number of runnables
    def __init__(self, runnable_list):
        self.runnable_list = runnable_list

    def invoke(self, input_data):
        for runnable in self.runnable_list:
            input_data = runnable.invoke(input_data)   # output of one step = input of the next
        return input_data

llm, parser = NakliLLM(), NakliStrOutputParser()
joke_chain = RunnableConnector([NakliPromptTemplate("Write a joke about {topic}", ["topic"]), llm])
explain_chain = RunnableConnector([NakliPromptTemplate("Explain the following joke {response}", ["response"]), llm, parser])
final_chain = RunnableConnector([joke_chain, explain_chain])     # a chain of chains
print(final_chain.invoke({"topic": "cricket"}))
Gotcha · abstract method

A class that inherits Runnable but does not define invoke cannot even be created: TypeError: Can't instantiate abstract class ... with abstract method invoke. That error is what forces every component into the same shape.

The same thing in real LangChain

Runnable primitives and LCEL

Interview

Task-specific runnables are core components converted to runnables (prompt templates, chat models, parsers, retrievers). Runnable primitives are building blocks that orchestrate them sequentially, in parallel, conditionally, and so on.

RunnableSequence and RunnableParallel

sequence_and_parallel.pyRan · fake model
from langchain_core.runnables import RunnableParallel, RunnableSequence

prompt1 = PromptTemplate(template="Write a joke about {topic}", input_variables=["topic"])
prompt2 = PromptTemplate(template="Explain the following joke - {text}", input_variables=["text"])

# Sequence: 6 runnables, only the last output comes back (the explanation)
chain = RunnableSequence(prompt1, model, parser, prompt2, model, parser)
print(chain.invoke({"topic": "AI"}))

# Parallel: same input to every branch, branches run independently, output is a dict
parallel_chain = RunnableParallel({
    "tweet": RunnableSequence(PromptTemplate.from_template("Generate a tweet about {topic}"), model, parser),
    "linkedin": RunnableSequence(PromptTemplate.from_template("Generate a LinkedIn post about {topic}"), model, parser),
})
result = parallel_chain.invoke({"topic": "AI"})
print(result["tweet"]); print(result["linkedin"])

RunnablePassthrough: keep the joke and its explanation

It returns its input unchanged (RunnablePassthrough().invoke(2) gives 2). Useful when a sequence would otherwise throw away an intermediate result.

passthrough_and_lambda.pyRan · fake model
from langchain_core.runnables import RunnableLambda, RunnablePassthrough

joke_gen_chain = RunnableSequence(prompt1, model, parser)

parallel_chain = RunnableParallel({
    "joke": RunnablePassthrough(),                                  # joke comes out untouched
    "explanation": RunnableSequence(prompt2, model, parser),
})
final_chain = RunnableSequence(joke_gen_chain, parallel_chain)
print(final_chain.invoke({"topic": "cricket"}))                     # {"joke": ..., "explanation": ...}

# RunnableLambda: turn any Python function into a runnable (custom logic, preprocessing)
def word_count(text):
    return len(text.split())                                        # LLMs are bad at counting words

final_chain = joke_gen_chain | RunnableParallel({
    "joke": RunnablePassthrough(),
    "word_count": RunnableLambda(word_count),                       # or RunnableLambda(lambda x: len(x.split()))
})
result = final_chain.invoke({"topic": "AI"})
print(f"{result['joke']}\nword count - {result['word_count']}")
Interview · RunnableLambda use case

Cleaning customer reviews before sentiment analysis: a Python function lower-cases the text and strips HTML tags, emojis and punctuation. Wrapped in RunnableLambda, it becomes a normal step of the chain, right before the model.

RunnableBranch: summarize only long reports

branch.pyRan · fake model
from langchain_core.runnables import RunnableBranch

report_prompt = PromptTemplate(template="Write a detailed report on {topic}", input_variables=["topic"])
summary_prompt = PromptTemplate(template="Summarize the following text\n{text}", input_variables=["text"])

Interview · RunnableBranch syntax

RunnableBranch((cond1, runnable1), (cond2, runnable2), default_runnable). The first condition that returns True wins; the last argument (no tuple) is the else. Real use: route a customer email to a complaint, refund or general-query chain based on the LLM's classification.

LCEL: the pipe is just RunnableSequence

RunnableSequence turned out to be used everywhere, so LangChain gave it a shortcut: RunnableSequence(r1, r2, r3) can be written r1 | r2 | r3. That declarative syntax is the LangChain Expression Language. From here on chains are written with |.

Beyond the video

Nitish guessed that parallel might get its own operator someday. It already has a shortcut: inside a pipe, a plain dict becomes a RunnableParallel and a plain function becomes a RunnableLambda. Checked:

Document loaders (start of RAG)

Memory was skipped on purpose (it is moving to LangGraph). From this video the playlist builds toward RAG, one component per video.

Interview · what is RAG?

Retrieval-Augmented Generation combines information retrieval with language generation: the model retrieves relevant documents from an external knowledge base and uses them as context to generate accurate, grounded answers.

Why: ChatGPT cannot answer about today's news, your emails or your company's docs, because it never saw them. RAG gives up-to-date information, privacy (no uploading confidential files to a chatbot) and no document size limit (a 1 GB file is chunked instead of crammed into the context window).

Interview · the Document object

Document loaders load data from many sources into a standard format: a list of Document objects, each with page_content (the text) and metadata (source, page, author, created date...). Every loader returns a list, even for one file. All loaders live in langchain_community.document_loaders.

custom_loader.pyRan
from typing import Iterator
from langchain_core.document_loaders import BaseLoader
from langchain_core.documents import Document

class LineLoader(BaseLoader):
    """One Document per non-empty line of a file."""
    def __init__(self, path):
        self.path = path

    def lazy_load(self) -> Iterator[Document]:
        with open(self.path, encoding="utf-8") as f:
            for n, line in enumerate(f):
                if line.strip():
                    yield Document(page_content=line.strip(), metadata={"source": self.path, "line": n})

docs = LineLoader("cricket.txt").load()    # load() comes free once lazy_load() exists

Because anyone can write a loader by subclassing BaseLoader, the community built loaders for their own data sources and they were added to LangChain. That is why loaders sit in the langchain_community package.

Text splitters

Interview · what and why

Text splitting breaks large text (articles, PDFs, HTML pages, books) into smaller chunks an LLM can handle well. Why:

  1. Model limits: a model with a 50,000-token context window cannot take a 100,000-word PDF to summarize.
  2. Better downstream results: chunk embeddings capture meaning better than one embedding of a huge text (a paragraph each on CSK, MI and RCB beats one mixed vector); semantic search is more precise; summaries drift and hallucinate less.
  3. Less compute: small chunks need less memory and can be processed in parallel.

1. Length based

Decide a chunk size (in characters or tokens), walk through the text, cut every N characters. Simple and fast, but it ignores grammar, structure and meaning, so it can cut mid-word or mid-sentence and split one idea across two chunks.

length_based.pyRan
from langchain_community.document_loaders import PyPDFLoader
from langchain_text_splitters import CharacterTextSplitter    # was: langchain.text_splitter

splitter = CharacterTextSplitter(chunk_size=100, chunk_overlap=0, separator="")

chunks = splitter.split_text(some_long_string)               # list[str]

docs = PyPDFLoader("dl-curriculum.pdf").load()               # loader + splitter together
chunks = splitter.split_documents(docs)                       # list[Document], page metadata kept
print(chunks[0].page_content)

chunk_overlap

How many characters two neighbouring chunks share. With overlap 20, the last 20 characters of chunk 1 are repeated at the start of chunk 2 (verified), so context cut at a boundary is not lost.

How much overlap?

More overlap keeps more context but creates more chunks, so more compute. Rule of thumb for RAG: 10 to 20% of chunk size (10 to 20 for chunk size 100).

Beyond the video

The colourful chunk visualizer used in the video is ChunkViz, linked from LangChain's text-splitter docs. Paste text, pick a splitter, move the chunk size and overlap sliders.

2. Text-structure based: RecursiveCharacterTextSplitter

Text is naturally organised as paragraphs, then sentences, then words, then characters. This splitter tries the separators in that order: "\n\n" (paragraph), "\n" (line), " " (word), "" (character). It splits with the biggest separator first and only goes finer for pieces still larger than chunk_size; then it merges neighbouring small pieces back together while they fit.

The video's worked example. Text: "My name is Nitish\nI am 35 years old\n\nI live in Gurgaon\nHow are you" (paragraph 1 is 34 characters, paragraph 2 is 28).

Interview · why it is the default

Bigger chunk sizes make it split at paragraphs, smaller ones at sentences, then words, and only at characters as a last resort. Splitting along the text's own structure keeps related context together, which is why it is the most used splitter.

3. Document-structure based: code and markdown

Code is not organised in paragraphs; it is organised in classes, functions and loops. Same recursive algorithm, different separators: for Python it first tries "\nclass ", "\ndef ", "\n\tdef ", then the usual paragraph, line and word separators. Supported languages include Python, JavaScript, Java, PHP, HTML and Markdown.

code_and_markdown_splitting.pyRan
from langchain_text_splitters import Language, RecursiveCharacterTextSplitter

chunks = py_splitter.split_text(python_code)    # chunk 0: the class, chunk 1: the code that uses it

md_splitter = RecursiveCharacterTextSplitter.from_language(language=Language.MARKDOWN, chunk_size=200, chunk_overlap=0)
chunks = md_splitter.split_text(readme_text)    # splits at headings first

4. Semantic meaning based

Some text defeats structure: one paragraph about farmers that switches to the IPL halfway, then a paragraph about terrorism. Ideal result: three chunks, but structure-based splitting gives two. The semantic chunker splits where the meaning changes.

semantic_meaning_based.pyNeeds OPENAI_API_KEY + langchain-experimental · not run

Revision32 questions

Interview Q&A

Click an answer to reveal it.

What is LangChain and why use it instead of calling the OpenAI API directly?

An open-source framework for building LLM-powered apps. A real app has many steps (load, split, embed, store, retrieve, prompt, call, parse). LangChain gives a component for each step, one interface across providers so you can switch models in 1 to 2 lines, and chains that wire the steps together.

Videos 1, 2

Name the six LangChain components and the problem each solves.

Models (different provider APIs), Prompts (output sensitive to input), Chains (manual wiring between steps), Indexes (LLM does not know your data), Memory (API calls are stateless), Agents (chatbots cannot act).

Video 2

LLM vs chat model?

LLMs take a string and return a string; general purpose, no roles, no history; legacy (BaseLLM). Chat models take a list of messages and return an AIMessage; fine-tuned on conversations, understand system/user/assistant roles; recommended (BaseChatModel).

Video 3

What does temperature do?

Controls randomness. Near 0 the same input gives the same output (factual tasks, code). Higher values give more varied output on each run (creative writing, brainstorming).

Videos 3, 4

Language model vs embedding model?

A language model returns text; an embedding model returns a vector of numbers that captures the text's meaning. Embeddings power semantic search and RAG.

Video 3

embed_query vs embed_documents?

embed_query embeds one string and returns one vector. embed_documents embeds a list of strings and returns a 2D list, one vector per document.

Video 3

Pros and cons of open-source models?

Pros: no API cost, full control, data privacy, fine-tuning, deploy anywhere. Cons: need strong hardware, harder setup, less RLHF refinement, limited multimodal support.

Video 3

How do you find the most relevant document for a query with embeddings?

Embed all documents and the query, compute cosine similarity between the query vector and every document vector, return the highest-scoring document. In production, store document vectors in a vector database instead of recomputing them.

Video 3

Static vs dynamic prompts?

Static: the user writes the whole prompt, so quality is inconsistent and hallucination is more likely. Dynamic: you write a template and the user only fills placeholders, so every request follows your rules.

Video 4

Why use PromptTemplate instead of an f-string?

Built-in validation of placeholders, saving and reusing templates, and it is a runnable that plugs into chains.

Video 4

What are SystemMessage, HumanMessage and AIMessage for?

They label each message in a chat history with who said it, so the model understands a long conversation. System sets behaviour, Human is the user, AI is the model's reply.

Video 4

ChatPromptTemplate vs PromptTemplate, and what is MessagesPlaceholder?

PromptTemplate builds one dynamic prompt; ChatPromptTemplate builds a dynamic list of role messages. MessagesPlaceholder is a slot inside a ChatPromptTemplate where stored chat history is inserted at runtime.

Video 4

What is structured output and why does it matter?

Making the LLM return data in a defined format (JSON following a schema). It lets the LLM talk to databases, APIs and tools: data extraction, API building, agents.

Video 5

TypedDict vs Pydantic vs JSON Schema?

TypedDict: type hints only, returns a dict. Pydantic: validation, defaults, type coercion, returns an object; the default choice in Python. JSON Schema: cross-language, returns a dict.

Video 5

What does with_structured_output do behind the scenes?

Converts the schema into instructions for the model (JSON mode, a function/tool definition, or native JSON schema) and parses the reply into the schema's type.

Video 5

json_mode vs function_calling?

json_mode asks the model for JSON output. function_calling sends the schema as a tool definition, natural for agents. Current ChatOpenAI defaults to json_schema (native structured outputs).

Video 5

When do you need output parsers instead of with_structured_output?

When the model cannot produce structured output natively (many open-source models). Parsers work with any model: they inject format instructions into the prompt and parse the text reply.

Video 6

Compare the four main output parsers.

StrOutputParser: plain text. JsonOutputParser: any JSON, no schema. StructuredOutputParser: fixed keys via ResponseSchema, no validation. PydanticOutputParser: schema plus validation.

Video 6

Why is StrOutputParser useful if result.content gives the same text?

Inside a chain there is no place to write .content. The parser turns the AIMessage into a string so it can flow into the next prompt.

Video 6

What are partial_variables?

Template placeholders filled when the template is created rather than at invoke time, typically the parser's format instructions.

Video 6

What is a chain and what types exist?

A pipeline where each step's output is the next step's input, so you only feed the first step. Sequential, parallel (RunnableParallel) and conditional (RunnableBranch).

Video 7

How do you make a conditional chain reliable?

Make the classifier's output consistent with a PydanticOutputParser and a Literal type, so the branch conditions always match. Give RunnableBranch a default branch wrapped in RunnableLambda.

Video 7

Why were runnables introduced?

Early components had different methods (predict, format, get_relevant_documents, parse), so every combination needed a custom chain class. Too many chains made the codebase heavy and the library hard to learn. Runnables give every component the same interface, so anything connects to anything.

Video 8

What are the properties of a Runnable?

A unit of work with input and output; a common interface (invoke, batch, stream); runnables connect so outputs flow into inputs; a connected workflow is itself a runnable. Like Lego blocks.

Video 8

Task-specific runnables vs runnable primitives?

Task-specific: components that do a job (ChatOpenAI, PromptTemplate, retrievers, parsers). Primitives: orchestrate other runnables (Sequence, Parallel, Passthrough, Lambda, Branch).

Video 9

When would you use RunnablePassthrough and RunnableLambda?

Passthrough returns its input unchanged, used to keep an intermediate result (the joke) next to a derived one (its explanation). Lambda turns any Python function into a runnable, for custom logic such as preprocessing or counting words.

Video 9

What is LCEL?

LangChain Expression Language: the declarative pipe syntax. r1 | r2 | r3 builds a RunnableSequence. Inside a pipe a dict becomes a RunnableParallel and a function becomes a RunnableLambda.

Video 9

What is RAG and why use it?

Retrieval-Augmented Generation: retrieve relevant chunks from an external knowledge base and give them to the LLM as context. Gives current information, works with private data, keeps it private, and handles documents bigger than the context window.

Video 10

What does a document loader return?

A list of Document objects, each with page_content and metadata. PyPDFLoader gives one per page, CSVLoader one per row, TextLoader one per file, WebBaseLoader one per URL.

Video 10

load() vs lazy_load()?

load() reads everything into memory and returns a list. lazy_load() returns a generator that yields one Document at a time; use it for many or large files.

Video 10

Why split text, and how does RecursiveCharacterTextSplitter work?

Context limits, better embeddings and search, better summaries, less compute. The recursive splitter tries paragraph, line, word, then character separators, going finer only for pieces still too big, and merges small neighbours back up to chunk_size.

Video 11

What is chunk_overlap and what value would you pick?

Characters shared between neighbouring chunks so context cut at a boundary is kept. More overlap means more chunks and compute; 10 to 20% of chunk size is typical for RAG.
