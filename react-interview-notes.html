1. What is React and why is it popular? 1:20

React is a JavaScript library for building user interfaces (the part of an app the user sees and clicks). It was made by Jordan Walke at Facebook (now Meta) and released in 2013. The video quotes it as the 2nd most-used web framework in 2024, used by about 39% of developers.

Why people like it, in two ideas:

  • Components — you build the UI from small, reusable Lego blocks (a Button, a Navbar, a ProductCard) and snap them together. Write once, use everywhere.
  • Virtual DOM — React keeps a cheap copy of the page in memory and only touches the real page where something actually changed. Touching the real page is slow, so this makes apps fast. (Full detail in Q11.)

2. What is a Single Page Application (SPA)? 1:50

An SPA loads one HTML page once. After that, when you click around, the page is not reloaded from the server. JavaScript just swaps out the parts that need to change (e.g. a box turning from light blue to pink) and fetches only the data it needs.

Simple picture: a traditional website is like a book where every click gives you a whole new printed page. An SPA is like a whiteboard: you keep the same board and just erase and redraw one corner.

ProsCons
Faster after first load, feels like an app, smooth transitionsSEO is harder: search engines see one URL / an almost empty HTML page, so crawling and indexing content is tougher. First load can be heavier.
Interview add-on: the SEO problem is usually solved with server-side rendering (SSR) frameworks like Next.js, which send ready-made HTML first.

3. What is JSX and how is it different from HTML? 2:35

JSX = JavaScript XML. It lets you write HTML-looking tags inside JavaScript. It's not real HTML — a tool (Babel) converts it into plain JavaScript function calls before the browser sees it.

// You write JSX:
const name = "Anshul";
const element = <h1 className="title">Hello, {name}!</h1>;

// Babel turns it into plain JS:
const element = React.createElement("h1", { className: "title" }, "Hello, ", name, "!");
JSXHTML
Can embed JavaScript with { } — {user.name}, {2+2}, {isLoggedIn ? "Hi" : "Login"}Static; needs separate <script> for logic
Every tag must close: <img />, <br />, <input /> (same rule as XHTML)<img>, <br> are fine unclosed
className, htmlFor, onClick (camelCase)class, for, onclick
Must return one parent element (or a Fragment)Any number of siblings

4. Functional vs class components 3:14

Simple version: class components are the old, bulky machine; functional components are the modern, simple one. Since React Hooks arrived (React 16.8, 2019), functional components can do everything classes could, with less code. New code is almost always functional.

// Class component (old way)
import React from "react";

class Counter extends React.Component {
  constructor(props) {
    super(props);
    this.state = { count: 0 };          // state lives in this.state
  }
  render() {                            // must have render() that returns JSX
    return (
      <button onClick={() => this.setState({ count: this.state.count + 1 })}>
        Clicked {this.state.count} times
      </button>
    );
  }
}
// Functional component (modern way) — same thing
import { useState } from "react";

function Counter() {
  const [count, setCount] = useState(0);   // state via a hook
  return <button onClick={() => setCount(count + 1)}>Clicked {count} times</button>;
}

5. Stateless vs stateful components 4:09

Stateless = has no memory of its own. It just receives data (props) and shows it. Like a TV screen: it displays whatever signal it gets.

Stateful = keeps its own data that can change over time (e.g. after a click). Like a scoreboard: it remembers and updates the score.

// Stateless: just displays what it is given
function Greeting({ name }) {
  return <h2>Hello, {name}</h2>;
}

// Stateful: remembers and changes its own data
function LikeButton() {
  const [likes, setLikes] = useState(0);
  return <button onClick={() => setLikes(likes + 1)}>👍 {likes}</button>;
}

With hooks, any functional component can be either one — you just decide whether to use useState.

Good practice: keep most components stateless and put state in a few parent components. Stateless ones are easier to test and reuse.

6. What are props? 4:50

Props (properties) are how a parent passes data down to a child, like arguments to a function. They are read-only: the child can use them but must never change them.

function UserCard(props) {
  return <p>{props.name} is {props.age} years old</p>;
}

// Destructured version (more common):
function UserCard({ name, age }) {
  return <p>{name} is {age} years old</p>;
}

function App() {
  return <UserCard name="John" age={30} />;   // passing props
}

Output: John is 30 years old

How does a child "talk back" to the parent then? The parent passes a function as a prop (e.g. onDelete), and the child calls it. The parent then updates its own state.

function Parent() {

  return <Display value={count} />;               // ...is a prop here

  return <h1>{value}</h1>;
}

8. Controlled vs uncontrolled components 5:58

This is about form inputs. The question is: who holds the value the user typed — React or the browser?

  • Controlled — React holds it in state. Every keystroke updates state, and the input shows whatever state says. Use when you need to check input live, e.g. validating a username/password, disabling a button until the form is valid.
  • Uncontrolled — the browser (DOM) holds it. React only reads it when needed, using a ref. Use for simple cases: newsletter email box, file upload.
// Controlled
function LoginForm() {
  const [username, setUsername] = useState("");
  return (
    <>
      <input value={username} onChange={(e) => setUsername(e.target.value)} />
      {username.length < 3 && <p>Username too short</p>}   {/* live validation */}
    </>
  );
}

// Uncontrolled
import { useRef } from "react";

function NewsletterForm() {
  const emailRef = useRef();
  const handleSubmit = (e) => {
    e.preventDefault();
    alert("Subscribed: " + emailRef.current.value);   // read only on submit
  };
  return (
    <form onSubmit={handleSubmit}>
      <input ref={emailRef} defaultValue="" />
      <button>Subscribe</button>
    </form>
  );
}

9. What is the key attribute in lists for? 6:47

When you render a list, React needs a way to tell items apart. A key is a unique ID for each item — like a name tag. If you rename "orange" in a list of apple / banana / orange, React uses the keys to see that only that one item changed, and updates only it instead of redrawing the whole list.

const fruits = [
  { id: 1, name: "Apple" },
  { id: 2, name: "Banana" },
  { id: 3, name: "Orange" },
];

function FruitList() {
  return (
    <ul>
      {fruits.map((fruit) => (
        <li key={fruit.id}>{fruit.name}</li>     // key goes on the outermost element in map
      ))}
    </ul>
  );
}
Common follow-up: don't use the array index as a key if items can be added, removed or reordered — the index of an item changes, so React matches the wrong items and you get bugs (e.g. text typed in the wrong input). Use a stable ID from your data. Keys only need to be unique among siblings.

10. What are Fragments? 7:25

A component must return one parent element. If you want to return an <h1> and a <p> side by side, you'd normally wrap them in a <div> — but that adds a useless extra box to the page. A Fragment groups them without adding anything to the DOM. Think of it as an invisible wrapper.

// With a div: adds an extra <div> to the page
return (
  <div>
    <h1>Title</h1>
    <p>Text</p>
  </div>
);

// With a Fragment: no extra node
import { Fragment } from "react";
return (
  <Fragment>
    <h1>Title</h1>
    <p>Text</p>
  </Fragment>
);

// Short syntax (most common)
return (
  <>
    <h1>Title</h1>
    <p>Text</p>
  </>
);

Resulting DOM: <h1>Title</h1><p>Text</p> — no wrapper

Why it matters: extra divs can break CSS layouts (flex/grid children, tables — a <div> inside <tr> is invalid). Need a key on a fragment inside a list? Use the long form: <Fragment key={id}>.

11. What is the Virtual DOM and how does it improve performance? 7:50

The DOM is the browser's tree of everything on the page. Changing it is slow because the browser has to recalculate layout and repaint.

The Virtual DOM is a lightweight copy of the DOM kept in memory as plain JavaScript objects. Changing objects in memory is very fast.

The video's example: a page with a "Click me" button and a <span> showing a click count. On each click only the number changes. Should React redraw the button, the paragraph and the whole page? No — that wastes time, especially on a huge page. With the virtual DOM, React figures out that only the span's text changed and updates just that.

// The video's demo idea
function ClickCounter() {
  const [clicks, setClicks] = useState(0);
  return (
    <div>
      <p>You clicked: <span>{clicks}</span></p>   {/* only this text node changes in the real DOM */}
      <button onClick={() => setClicks(clicks + 1)}>Click me</button>
    </div>
  );
}
Correction: the video describes React comparing the virtual DOM against the real DOM. More precisely, React compares the new virtual DOM with the previous virtual DOM (both in memory), then applies the minimal changes to the real DOM. Open DevTools → Elements while clicking and you'll see only the number flash.

12. React lifecycle methods 10:10

Definition: lifecycle methods are special functions (in class components) that let you run your code at specific moments in a component's life.

Simple version: a component is born (appears on screen), grows (updates when data changes) and dies (is removed). Lifecycle methods are hooks into those moments: "when you appear, fetch data"; "when you're removed, stop the timer".

The video explains them with a video game analogy. Here it is, with the accurate meaning next to it:

constructorNew player: score and ID set to starting valuesSet initial this.state, bind methods. Runs once.
getDerivedStateFromPropsReturning player: load saved statsStatic method that updates state from incoming props before render. Rarely needed.

class GameScore extends React.Component {
  constructor(props) {
    super(props);
    this.state = { score: 0 };
  }
  componentDidMount() {
    // fetch saved score, start a timer
    this.timer = setInterval(() => this.setState((s) => ({ score: s.score + 10 })), 1000);
  }
  shouldComponentUpdate(nextProps, nextState) {
    return nextState.score !== this.state.score;   // only re-render if score changed
  }
  componentDidUpdate(prevProps, prevState) {
    console.log(`Score went from ${prevState.score} to ${this.state.score}`);
  }
  componentWillUnmount() {
    clearInterval(this.timer);                     // cleanup
  }
  render() {
    return <h2>Score: {this.state.score}</h2>;
  }
}
Correction: the video's analogy for getDerivedStateFromProps ("fetch the player's saved stats") is misleading — it can't fetch anything; it only copies props into state, synchronously. Data fetching belongs in componentDidMount (or useEffect).
Hooks equivalent (say this in interviews):
componentDidMount → useEffect(() => {...}, [])
componentDidUpdate → useEffect(() => {...}, [dep])
componentWillUnmount → the function you return from useEffect
shouldComponentUpdate → React.memo

13. useState and useEffect hooks 14:45

useState

Simple version: useState is a container (a box) that remembers a value between renders. You get the current value and a function to change it. When you call that function, React re-renders the component with the new value.

const [count, setCount] = useState(0);
//     ↑ value  ↑ setter          ↑ initial value

Video demo: a counter 16:00

// components/Counter.js
import { useState } from "react";

function Counter() {
  const [count, setCount] = useState(0);

  const increment = () => setCount(count + 1);
  const decrement = () => setCount(count - 1);

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={increment}>Increment</button>
      <button onClick={decrement}>Decrement</button>
    </div>
  );
}

export default Counter;
// App.js
import Counter from "./components/Counter";

function App() {
  return <Counter />;
}
export default App;

Run with: npm start → clicking the buttons changes the number (no limit set, so it can go negative)

useEffect

Simple version: useEffect runs code after the component appears on screen — for "side effects": things that reach outside React, like API calls, timers, subscriptions, changing the page title. Think of a clock ticking in the corner: it must keep running, but shouldn't block the main page from loading.

useEffect(() => {
  // effect: runs after render
  return () => {
    // cleanup: runs before the next effect and when the component is removed
  };
}, [dependencies]);
Dependency arrayWhen the effect runs
none: useEffect(fn)After every render
empty: useEffect(fn, [])Once, after the first render (like componentDidMount)
useEffect(fn, [userId])First render + whenever userId changes

Video demo: a timer 18:38

// components/Timer.js
import { useState, useEffect } from "react";

function Timer() {
  const [seconds, setSeconds] = useState(0);

  useEffect(() => {
    const interval = setInterval(() => {
      setSeconds((prev) => prev + 1);   // use previous value, not `seconds`
    }, 1000);

    return () => clearInterval(interval); // cleanup when component is removed
  }, []);                                // [] = start the timer only once

  return <h3>Timer: {seconds} seconds</h3>;
}

export default Timer;

The timer keeps ticking in the background while you keep using the counter — that's useEffect.

Why prev => prev + 1? The effect runs only once, so the seconds variable it "sees" is stuck at 0 forever (a stale closure). The function form always gets the latest value. Why cleanup? Without clearInterval, the timer keeps running after the component is gone → memory leak and warnings.

Classic data-fetch pattern (the video mentions "fetch data when the component mounts"):

function Users() {
  const [users, setUsers] = useState([]);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    fetch("https://jsonplaceholder.typicode.com/users")
      .then((res) => res.json())
      .then((data) => { setUsers(data); setLoading(false); });
  }, []);

  if (loading) return <p>Loading...</p>;
  return <ul>{users.map((u) => <li key={u.id}>{u.name}</li>)}</ul>;
}
Rules of Hooks: call hooks only at the top level of a component (not inside if, loops or nested functions), and only in React function components or custom hooks.

14. What is props drilling? 21:17

Simple version: you want to give a note to your great-grandchild, but you can only hand it to your child, who hands it to the grandchild, who finally hands it to the great-grandchild. The middle people don't care about the note — they're just couriers. That's props drilling.

Technical: props drilling is when data has to be passed through many layers of components that don't use it, just so a deeply nested component can get it. With many levels it becomes hard to track where a prop is going, and every middle component has to change if the data changes.

// App.js — the data lives here
import Parent from "./components/Parent";

function App() {
  const user = { name: "John", age: 30 };
  return <Parent user={user} />;
}

// components/Parent.js — doesn't use user, only forwards it
import Child from "./Child";
function Parent({ user }) {
  return <Child user={user} />;
}

// components/Child.js — also doesn't use it, forwards again
import GrandChild from "./GrandChild";
function Child({ user }) {
  return <GrandChild user={user} />;
}

// components/GrandChild.js — finally uses it
function GrandChild({ user }) {
  return <h2>Hello, {user.name}</h2>;
}

Output: Hello, John

Fixes: Context API (next question), state libraries (Redux, Zustand), or component composition (pass the finished <GrandChild/> as children).

15. What is the Context API and how is it used for state management? 26:33

Simple version: instead of handing the note down person by person, you pin it on a family notice board. Anyone in the family can walk up and read it directly. Context is that notice board — a shared, "global" space for a part of the component tree.

Technical: the Context API lets you share state/data across a component tree without passing props manually at every level.

Three steps: 1) create the context, 2) provide it around the tree, 3) consume it where needed.

// context/UserContext.js — step 1: create + a Provider component
import { createContext, useState } from "react";

export const UserContext = createContext();

export function UserProvider({ children }) {
  const [user, setUser] = useState({ name: "John", age: 30 });
  return (
    <UserContext.Provider value={user}>
      {children}                          {/* everything inside can read `user` */}
    </UserContext.Provider>
  );
}
// App.js — step 2: wrap the tree in the provider
import { UserProvider } from "./context/UserContext";
import Parent from "./components/Parent";

function App() {
  return (
    <UserProvider>
      <Parent />                           {/* no props passed! */}
    </UserProvider>
  );
}

// Parent.js and Child.js — just render the next component, no user prop
function Parent() { return <Child />; }
function Child()  { return <GrandChild />; }
// components/GrandChild.js — step 3: consume
import { useContext } from "react";
import { UserContext } from "../context/UserContext";

function GrandChild() {
  const user = useContext(UserContext);
  return <h2>Hello, {user.name}</h2>;
}

Output: Hello, John — read directly by GrandChild

The bug hit in the video 31:49: it first didn't work because the components weren't wrapped in <UserProvider>. A component only sees context if it is inside the Provider; outside, useContext returns the default value (here undefined).
To let children also change the value, pass the setter too: value={{ user, setUser }} and read it with const { user, setUser } = useContext(UserContext).
Context vs Redux: Context is built-in and great for things that change rarely (logged-in user, theme, language). Every consumer re-renders when the value changes, so for large, frequently changing app state, people use Redux Toolkit or Zustand.

16. What are Higher-Order Components (HOCs)? 32:36

Technical: a HOC is a function that takes a component and returns a new component with extra functionality or modified behaviour.

It's the same idea as a higher-order function in JavaScript (like map, which takes a function as input). Simple version: a HOC is like a gift-wrapping station: you hand in any component, it comes back wrapped with something extra (a login check, logging, a loading spinner).

Video's use case: on a website, some pages are only for premium users. Instead of copying the "is this user premium?" check into every page, write it once as a HOC and wrap each premium page with it.

Video demo 33:54 — a HOC that logs every time the wrapped component renders:

// components/withLogger.js — the HOC (video called it "HOC")
function withLogger(WrappedComponent) {
  return function EnhancedComponent(props) {
    console.log("Modifying this component with new props:", props);
    return <WrappedComponent {...props} />;    // render the original, pass all props through
  };
}
export default withLogger;
// components/Greet.js
import withLogger from "./withLogger";

function Greet({ name }) {
  return <h2>Hello, {name}!</h2>;
}

const EnhancedGreet = withLogger(Greet);    // wrap it
export default EnhancedGreet;
// App.js
import EnhancedGreet from "./components/Greet";

function App() {
  return <EnhancedGreet name="John" />;
}

Screen: Hello, John! Console: Modifying this component with new props: {name: "John"}

Correction: on screen the video types something like return WrappedComponent + props. That's not valid — you must render it as JSX: <WrappedComponent {...props} />. The {...props} spreads all incoming props onto the original component.

The premium-page example from the video, written out:

function withPremium(WrappedComponent) {
  return function (props) {
    const user = useContext(UserContext);
    if (!user?.isPremium) return <p>Upgrade to premium to see this page.</p>;
    return <WrappedComponent {...props} />;
  };
}

const PremiumReports = withPremium(Reports);
const PremiumDownloads = withPremium(Downloads);   // one check, reused everywhere
Real-world HOCs: React.memo(Component), Redux's old connect(). Today custom hooks (e.g. usePremium()) are often preferred for sharing logic, but HOCs are still a common interview question.

17. Explain reconciliation 41:01

Reconciliation is the whole process React follows when something changes: how the virtual DOM and real DOM work together to update the screen efficiently. The Virtual DOM (Q11) is the tool; reconciliation is the algorithm that uses it.

  1. Initial render — React builds the first virtual DOM and creates the real DOM from it.
  2. State or props change — React builds a brand-new virtual DOM. This is cheap because it's just JS objects.
  3. Diffing — compare the new virtual tree with the old one to find what's different.
  4. Updating the DOM — work out the minimum list of real-DOM changes.
  5. Commit phase — React applies those changes to the actual DOM in one go. Then useEffect / componentDidMount/DidUpdate run.
Diffing rules worth naming in an interview: (1) if an element's type changes (e.g. <div> → <span>), React throws away that whole subtree and builds a new one; (2) same type → keep the node, update only changed attributes; (3) in lists, React matches children by key. These shortcuts make diffing O(n) instead of very slow. The modern engine that does this is called React Fiber.

18. How do React Portals work and when should you use them? 42:44

Technical: a portal renders a component's children into a different part of the DOM, outside the parent's DOM hierarchy, while it still behaves like a normal child in the React tree (props, state, context and events still work).

Simple version: a component normally draws inside its parent's box. A portal lets it teleport its output somewhere else — usually straight into document.body. Used for modals, popups, tooltips, dropdowns, toasts — things that must float on top of everything and not get clipped by a parent's overflow: hidden or z-index.

Video demo 43:24:

// components/Modal.js
import ReactDOM from "react-dom";

function Modal({ isOpen, children }) {
  if (!isOpen) return null;                 // hidden → render nothing

  return ReactDOM.createPortal(
    <div
      style={{
        position: "fixed",
        top: "50%",
        left: "50%",
        transform: "translate(-50%, -50%)",  // center on screen
        color: "white",
        backgroundColor: "purple",
        padding: "20px",
      }}
    >
      {children}
    </div>,
    document.body                            // ← where to render (outside #root)
  );
}
export default Modal;
// App.js
import { useState } from "react";
import Modal from "./components/Modal";

function App() {
  const [isModalOpen, setIsModalOpen] = useState(false);

  return (
    <div>
      <h1>Welcome to React Portal</h1>
      <button onClick={() => setIsModalOpen(true)}>Open Modal</button>

      <Modal isOpen={isModalOpen}>
        <p>This is a modal</p>
        <button onClick={() => setIsModalOpen(false)}>Close Modal</button>
      </Modal>
    </div>
  );
}
Bugs hit in the video, worth remembering: (1) createPortal comes from react-dom, not react — importing from react gives "createPortal is not a function"; (2) the Modal must actually be rendered in App with isOpen passed; (3) the Close button goes inside the modal. Also, to center it use translate(-50%, -50%) with position: fixed.
Event bubbling: a click inside a portal still bubbles up to its React parent (App), even though in the DOM it lives under body.

19. How does React Router handle navigation in an SPA? 48:23

In an SPA there's only one HTML page, yet users expect /about and /contact URLs, back/forward buttons and bookmarks to work. React Router watches the URL and shows the matching component without reloading the page.

Install first:

npm install react-router-dom

The four pieces the video stresses: Router (BrowserRouter), Routes, Route, Link.

// App.js  (React Router v6+)
import { BrowserRouter as Router, Routes, Route, Link } from "react-router-dom";

function Home()    { return <h2>Home Page</h2>; }
function About()   { return <h2>About Page</h2>; }
function Contact() { return <h2>Contact Page</h2>; }

function App() {
  return (
    <Router>
      <div>
        <nav>
          <ul>
            <li><Link to="/">Home</Link></li>
            <li><Link to="/about">About</Link></li>
            <li><Link to="/contact">Contact</Link></li>
          </ul>
        </nav>

        <Routes>
          <Route path="/" element={<Home />} />
          <Route path="/about" element={<About />} />
          <Route path="/contact" element={<Contact />} />
        </Routes>
      </div>
    </Router>
  );
}
export default App;
Correction: the video writes routes with a component= prop. That's the old v5 style. Current React Router (v6+) uses element={<Home />} inside <Routes> (which replaced <Switch>).
Why <Link> and not <a href>? A normal <a> makes the browser reload the whole page, throwing away all React state. <Link> changes the URL using the browser's History API and lets React swap components. Other handy pieces: useNavigate() to navigate in code (e.g. after login), useParams() for URLs like /user/:id, and path="*" for a 404 page.

20. What is React Strict Mode? 52:35

Like JavaScript's "use strict", React Strict Mode is a safety net for development. It deliberately triggers extra checks and warnings so you catch bad patterns early, before they become real bugs later.

// index.js (created for you by most React templates)
import React from "react";
import ReactDOM from "react-dom/client";
import App from "./App";

ReactDOM.createRoot(document.getElementById("root")).render(
  <React.StrictMode>
    <App />
  </React.StrictMode>
);

What it does (in development only — it has zero effect in production):

  • Renders components twice and runs effects mount → cleanup → mount to expose impure code and missing cleanups.
  • Warns about deprecated / unsafe APIs (old lifecycle methods like componentWillMount, string refs, findDOMNode).
  • Like a Fragment, it renders nothing visible to the DOM.
Classic interview trap: "Why does my console.log / API call in useEffect run twice?" → Strict Mode in development. It's intentional; don't remove Strict Mode — make sure your effect has proper cleanup instead.
