FinVeritas Interview Guide

A plain-language walkthrough of how FinVeritas works: the architecture, each of the five agents, the credibility score and the login system. Every section has the real code and the questions an interviewer is likely to ask.

Based on the code at commit 3d8626da (11 Apr 2026), app folder mayankPbl/ocr/. Click any question to reveal a model answer, or use Show all answers to revise.

01

The big idea

FinVeritas reads a company's financial statements and explains how healthy the company is. The interesting part is who does what.

Python does all the maths. The LLM only explains the answers. The AI never sees the raw numbers and is told it may not create new ones.

Why? Language models are bad at arithmetic, can invent figures, and may answer differently each time. In finance, every number must be traceable and give the same result every time. So pandas and numpy calculate everything, and the LLM is handed a small dictionary of finished results to put into words.

You can see this rule in every agent. The revenue agent even removes one metric before calling the LLM, because small models tend to turn 0.875 into "87.5%", which is a new number.

Why not just ask the LLM to analyse the financial statements?

LLMs make arithmetic mistakes, can make up figures, and are not fully repeatable. A bank or auditor needs every number to be traceable to a formula. So the maths is done in Python, which is deterministic (same input, same output every time), and the LLM only turns finished numbers into readable text, at temperature 0.

What does temperature 0 do? Does it guarantee the same answer?

Temperature controls randomness. At 0 the model always picks its most likely next word, so the wording is as stable as possible. It does not fully guarantee identical output (servers can still differ slightly), which is exactly why no numbers are left to the model.

02

Architecture

Think of it as a factory line. Data comes in from one of three sources, gets converted into one standard format, is checked for trustworthiness, then five agents analyse it. The results go to the dashboard. A login wall sits in front of everything.

The common format

Every source ends up as this shape. Each financial field is a list of {period, value} pairs, and periods are always written YYYY-FY (a full year) or YYYY-Q1 to Q4.

How would you add a new data source, such as XBRL filings?

Write one converter that outputs the common JSON format above. Nothing else changes: the credibility checks and all five agents already read that format. That is the benefit of having one shared contract between ingestion and analysis.

Why Streamlit instead of React with a backend API?

It is a data-heavy prototype written by a Python team. Streamlit gives tables, charts, file upload and widgets in pure Python, so we could iterate fast. The cost is weaker control over routing and sessions, which is why the login wall and page guarding had to be built by hand.

03

Getting the data in

Ingestion has one job: whatever the user gives us, turn it into the common JSON format and save it to disk, so the rest of the app never has to care where the data came from. There are three ways in, and all three end in the same place.

The big picture: three doors, one room

This is the Upload page code for the PDF tab. The ticker and CSV tabs follow exactly the same shape with a different converter.

Streamlit re-runs the whole script on every click. How do you avoid re-parsing the PDF each time?

With a cache key. For PDFs it is the sorted list of file names; for a ticker it is the symbol. The parsed payload is stored in st.session_state with that key, and parsing only runs again if the key changes. Switching tabs clears all caches so data from one source never mixes with another.

Path 1 · Bloomberg PDF, step by step

This is the most complex path, and the one interviewers will dig into. It runs four stages, and each stage hands a specific object to the next one.

Stage 0 · The entry point

parse_pdf_to_json() runs the whole PDF path. pdfplumber needs a real file, so each upload is written into a temporary folder that is deleted automatically afterwards. The user's PDF is never kept on disk.

Stage 1 · extract_pdf(): read the raw page content

For every page it saves two things: the plain text, and any tables pdfplumber can find. Bloomberg PDFs are inconsistent: some draw lines around cells, others only line text up with spaces. So it tries a strict line-based reading first and falls back to a spacing-based one. The result is a PDFContent object: a list of pages, each with text and tables.

Stage 2 · parse_statement(): turn text and tables into data

First it reads the header, then it tries the tables, and only falls back to reading text line by line if the tables gave nothing.

2a · Reading the header. It looks only at the first 15 non-empty lines. The statement type comes from regex patterns (“income statement”, “profit and loss”, “balance sheet”), the currency from a list of codes (defaulting to INR), and the company name from a Company: field or the first line.

2b · Reading a table. The first row is the header with the periods. The first column is the label. For every other row: map the label to a key, then read each number under its period. Rows with labels the mapper does not know are skipped.

Worked example · what one table becomes
Row in the PDFFY 2023FY 2024What the parser does
(header row)FY 2023FY 2024periods → 2023-FY, 2024-FY
Revenue from Operations1,53,6701,62,990→ revenue: 153670, 162990

Note the brackets: in accounting, (284) means −284.

2c · The text fallback. When no table is found, it reads lines of text. It finds the first line with two or more period labels (the header), then for each line after it, it walks backwards from the end collecting numbers. Whatever is left at the front is the label. Reading from the right works because Bloomberg labels can contain spaces, but the numbers are always at the end.

Worked example

Line: Total Current Assets 6,71,850 7,08,810 8,94,320 → numbers taken from the right: 894320, 708810, 671850 → reversed to left-to-right order → label left over: "Total Current Assets" → key current_assets. If a line has fewer numbers than there are periods, they are matched to the latest periods.

The three helpers every value passes through

normalise_period() turns any period style into YYYY-FY or YYYY-QN using one big regular expression.

In the PDFBecomesRule

resolve_field() maps a row label to a key. Each key has a list of regex patterns; the dictionary is checked top to bottom and the first match wins. That makes the order of the dictionary important.

_parse_number() turns a cell into a float: it strips commas, treats (1,234) as −1234, treats dashes and “N/A” as “no value”, and returns None for anything that does not look like a number.

Stage 3 · build_company_json(): merge the statements

You usually upload two PDFs: the income statement and the balance sheet. Each becomes its own ParsedStatement. The builder pours all their values into one dictionary, removes duplicate periods (the last value seen wins), sorts them, and makes sure a few key fields always exist, even as an empty list, so the agents never hit a missing key.

Stage 4 · split one file per agent

Besides the full JSON, three smaller files are written, each holding only the fields one agent needs. Each agent is then run with a file path, which is also how you run it alone from the command line.

Real bug, visible in the project's own output. The pattern ^total\s+liabilities also matches the row “Total Liabilities & Equity”, which on every balance sheet equals total assets. That row comes later in the table, and the builder keeps the last value, so it overwrites the real liabilities. In output/Infosys_Ltd.json, total_liabilities is identical to total_assets for all ten years (e.g. 2025: 14,89,030 both). Everything downstream then breaks: the leverage ratio and the accounting identity check (the latter does at least flag the mismatch). Fix: anchor the pattern so it rejects “& equity”, e.g. ^total\s+liabilities\s*$, or check the more specific labels first.
Second issue in the same file: Infosys revenue includes 2026-FY and 2027-FY. Those are Bloomberg analyst estimates, read as if they were actual results, and 2019 is about 4× smaller than 2020, which suggests a different row or unit. The yearly-jump check only flags changes above 500%, so this 338% jump passes. Fix: drop columns later than the latest reported year, and tighten the jump threshold.

Path 2 · Stock ticker

Much simpler, because Yahoo Finance already gives structured tables. fetch_by_ticker() gets the company name and currency from t.info, the yearly income statement from t.financials and the balance sheet from t.balance_sheet. Each is a pandas table where rows are labels like “Total Revenue” and columns are dates. Two lookup tables map the labels to our keys and the dates become YYYY-FY.

The project's own output/Apple_Inc_.json came from this path: four years (2022–2025), and liabilities plus equity add up to assets exactly, which shows why structured data is more reliable than reading PDFs.

Path 3 · CSV or Excel for private companies

The user types the company name, picks a currency and uploads a sheet. load_private_company_data() is mostly validation, and every error message tells the user exactly what to fix.

  • Read .xlsx/.xls with openpyxl, .csv with pandas.
  • Lower-case and trim the column names, so “Revenue ” works.
  • A period column must exist; empty periods are dropped.
  • Every period must match YYYY-FY or YYYY-QN.
  • No period may appear twice.
  • At least one known financial column must be present.
  • Blank or non-numeric cells are skipped.

Four years, all seven fields present, and assets = liabilities + equity in every row, so every agent can run. Writing FY2023 instead of 2023-FY is rejected with a message showing the expected format.

After ingestion · filling missing fields

Once the payload is cached, the Upload page checks it against what the Liquidity and Balance Sheet agents need. If anything is missing, the user chooses Proceed anyway (those agents are skipped) or Fix missing data.

  • Auto-fetch (ticker source only): auto_fetch_missing_fields() tries FMP first, then Alpha Vantage for anything still missing, and only fills fields that are actually missing.
  • Manual entry: the user types values per period; _patch_payload_field() merges them in, and the four files are rewritten.
Worth knowing: in app.py the sidebar sets av_api_key = "", so the Alpha Vantage fallback can never actually run. Only FMP works. If asked, say that Alpha Vantage is implemented but not wired to a key yet.

Questions on ingestion

The folder is called "ocr". Is this really OCR?

No. pdfplumber reads the text that is already stored inside a digital PDF. It cannot read a scanned image, and the code warns when a page has no text: "PDF may be scanned/image-based". To support scans you would add an OCR step such as Tesseract before parsing.

Why try tables first and text second?

Tables keep columns aligned, so each number is reliably tied to its period. Text reading has to guess which number belongs to which column. So the more reliable method goes first, and the fallback only runs when it finds nothing.

Why does the text parser read numbers from the end of the line?

Labels can contain spaces and even digits, like "Total Current Assets", so splitting from the left is unreliable. Numbers are always the last tokens, so walking backwards until something is not a number cleanly separates the values from the label.

What happens to a row whose label the mapper doesn't recognise?

It is silently skipped. That keeps the output clean, but you cannot see what was missed. A good improvement would be to log every unmapped label so new patterns can be added to mapper.py.

Why does "Mar-24" become Q4 and not Q1?

The mapping follows the Indian financial year, which runs April to March, so January to March is Q4. That is correct for Indian companies but wrong for companies whose year follows the calendar, like most US firms. A better design would read the fiscal year end from the company's metadata.

Why write a separate JSON file for each agent?

Each agent gets only the fields it needs, and agents take a file path, which means they can also be run alone from the command line on any saved file. The files on disk also act as an audit trail of exactly what each agent saw.

Why save the upload to a temporary folder?

pdfplumber opens files by path, not raw bytes. TemporaryDirectory is deleted automatically when the block ends, so the user's PDF is never left on the server.

Did you find any bugs in your ingestion?

Yes, and saying so is a strong answer. "Total Liabilities & Equity" matches the total-liabilities pattern and overwrites the real value, which shows up in the Infosys sample output, where liabilities equal assets. Bloomberg's estimate columns (2026–2027) were also read as actual revenue. Both have simple fixes: a stricter regex, and dropping columns after the latest reported year.

Why is ticker data more reliable than PDF data?

Yahoo already returns labelled, structured tables, so there is no layout guessing. In the project's own outputs, the Apple file from yfinance balances perfectly, while the Infosys file from a PDF has the liabilities mapping problem. The trade-off is that yfinance only gives about four years and is an unofficial source.

04

Credibility score

Why we do it

Every agent trusts its input completely. If the data is wrong, the agents calculate wrong ratios with perfect precision, and then the LLM explains those wrong ratios in confident, professional English. Bad data does not look bad by the time it reaches the dashboard.

And bad data is likely here. PDFs are read by pattern matching, Yahoo is an unofficial source, and CSVs are typed by hand. So before any analysis runs, src/data_verifier.py inspects the data and gives it a score from 0 to 100, with a list of every check and its result. A bank does the same thing: it checks that the documents are genuine and add up before it reads what they say.

The checks answer four plain questions:

QuestionChecks
Is the source genuine?Bloomberg signature (PDF), active listing and dual-source cross-check (ticker), source type (CSV)
Is there enough data?Field completeness, temporal coverage
Does the data agree with itself?Accounting identity, internal consistency, year-on-year plausibility
Is it current?Data freshness

Where it runs

Step 1 · The two data structures

Each check produces one CredibilityCheck: a name, a status, a sentence explaining the result, and a weight (how many points it is worth). A CredibilityReport is just the list of checks plus the company and source.

Step 2 · Choosing which checks to run

run_verification() first adds the checks that only make sense for this source, then the six that apply to everything.

Step 3 · Turning checks into a score

  • PASS earns its full weight.
  • WARN earns half its weight, rounded down (15 // 2 = 7).
  • FAIL earns nothing.
  • SKIP is removed from the total. If a check could not run (for example, no FMP key), the data is not punished for it.

Score = points earned ÷ points possible × 100. 80 or more is HIGH, 55 or more is MEDIUM, below 55 is LOW. If every check was skipped, the score is a neutral 50.

The score is a @property, so it is recalculated from the checks every time it is read. There is no stored number that could fall out of step with the checks.

Worked example · the Acme CSV from section 03 (real output of the code)

Source type WARN 2/5 · completeness WARN 7/15 (6 of 10 key fields) · coverage PASS 10/10 · identity PASS 20/20 · freshness WARN 5/10 (2024 is two years old) · plausibility PASS 10/10 · consistency PASS 15/15.

69 ÷ 85 × 100 = 81.2 → 81, HIGH.

Step 4 · Each check, how and why

Accounting identity (20 points), the most important check. In every balance sheet, assets = liabilities + equity. This is a rule of double-entry bookkeeping, not an estimate. If it fails, the extraction or the label mapping almost certainly went wrong. A 5% tolerance allows for rounding and items like minority interest. Fewer than half the periods off is a warning; more than half is a failure.

Internal consistency (15 points). Some numbers must always be smaller than others: gross profit cannot exceed revenue, current assets cannot exceed total assets, current liabilities cannot exceed total liabilities. If they do, two labels were probably swapped. A 5% margin allows for rounding. Any problem at all is a failure.

Year-on-year plausibility (10 points). It walks every field in date order and flags any jump of more than 500%. Real companies rarely grow five-fold in a year, but a value in thousands next to one in millions looks exactly like that. This is a warning, never a failure, because big swings can be real.

Field completeness (15 points). Counts how many of ten key fields have data: revenue, gross profit, net income, operating income, EBITDA, total assets, total liabilities, equity, current assets, current liabilities. 80% or more passes, 50% or more warns, less fails. Fewer fields means fewer agents can run.

Temporal coverage (10 points). Counts the periods of revenue (or total assets if there is no revenue). 4 or more passes, 2–3 warns, 1 fails. The agents need at least 4 periods to calculate a trend.

Data freshness (10 points). Takes the newest period across all fields and compares its year with today's. At most 1 year old passes, 2 years warns, older fails. Analysing a company on five-year-old figures is misleading.

Source checks. These ask whether the data really came from where it claims to.

CheckPointsHowWhy
Bloomberg signature25Searches the PDF text for "Bloomberg Finance L.P.", "© Bloomberg" and similar (pass), or just "Bloomberg"/"BBG" (warn)Real Bloomberg exports carry a legal notice; a random PDF does not

Other things to know

  • The score never blocks anything. A LOW score is shown in red, but Run Analysis still works. It is a warning to the user, not a gate.
  • Future periods count as fresh. Infosys has Bloomberg estimates for 2027, so freshness says "2027-FY — current". The check should ignore periods later than the current year.
  • The 500% jump limit is loose. The Infosys revenue jump from 2019 to 2020 is 338% and is not flagged, while Apple's real retained-earnings swing is.
  • The history score is calculated differently. After the agents run, the score is calculated again for MongoDB without the ticker or FMP key, so the listing and cross-check are left out. For Apple both happen to give 94, but they can differ.

Questions on credibility

Why check the data at all? The agents already validate their inputs.

The agents check format: enough periods, no negatives, the right order. They cannot tell whether a correctly formatted number is the right number. The credibility checks look at meaning: do the figures add up, do they agree with another source, are they current. Without it, wrong data produces confident, well-written wrong analysis.

Why is the accounting identity worth so many points?

It is the one rule every balance sheet must satisfy. If it fails, something went wrong in extraction or mapping, which is exactly what this check is meant to catch. Our own Infosys sample shows it working: it caught the liabilities bug that every other check missed.

Why does a warning give half the points instead of zero?

A warning means "suspicious, not proven wrong", like 2-year-old data or a big but possibly real jump. Half credit lets a few warnings lower the score without making it look as bad as a real failure.

Why are skipped checks removed from the total instead of scoring zero?

A skip means we could not check, not that the data failed. For example, without an FMP key the cross-check cannot run. Scoring that as zero would punish the data for a missing API key.

Why a weighted average? What is wrong with it?

It is simple to explain, and each check's weight reflects how much it matters. The weakness is that strong passes can hide a critical failure: our Infosys file fails the identity check in every year and still scores 75. The fix is to combine the average with hard gates, so a critical failure caps the result at LOW.

Where do the weights and thresholds come from?

They are judgement calls, not learned from data: more weight for checks that catch more serious problems (identity 20, signature 25), less for softer ones (freshness 10). Thresholds like 80 for HIGH and 5% for tolerance are common rules of thumb. To improve them you would test against labelled examples of good and bad data.

Can the Bloomberg signature check be fooled?

Yes. Anyone can type "© Bloomberg" into a PDF. It is a quick heuristic, not proof. Also, in this version the app never passes the PDF text to it, so it is always skipped. Real verification would need a digital signature or cross-checking figures with a trusted source.

Should a LOW score stop the analysis?

Today it does not. A good middle ground is to let it run but require the user to confirm, and to carry the credibility score into the agent results so nobody reads the analysis without seeing it.

Why is the score a @property and not a stored number?

So it is always calculated from the current list of checks. If a check is added or changed, the score cannot be stale.

05

How every agent works

All five agents follow the same recipe, which makes them easy to explain. Each agent is two files: the real logic in src/, and a tiny wrapper in agents/ that the dashboard calls. That split also lets every agent run on its own from the command line.

Are these really "agents"?

Be honest: they are specialised analysis modules, each with an LLM step, run in a fixed order. They do not plan or choose their own tools the way autonomous agents do. The word fits in the sense of "one expert per area": each owns one part of the analysis, can fail on its own without breaking the others, and can be tested alone.

06

Revenue agent

src/revenue_agent.py

Question it answers: is revenue growing, how fast, and how steadily?

Validation first. It needs at least 4 periods, no empty or negative values, no repeated periods, and the periods must already be in date order. If not, it stops with an error rather than quietly re-sorting.

MetricPlain meaningHow
avg_growthAverage growth per period, in %mean of pct_change() × 100
cagrThe steady yearly rate that gets you from first to last value((last ÷ first)^(1 ÷ years) − 1) × 100
volatilityHow bumpy the growth isstandard deviation of the growth rates
positive_growth_ratioShare of periods that grewmean of growth > 0
trend_directionUp, down or flat overallslope of a straight line through revenue, divided by average revenue
Worked example

Revenue over four years: 100 → 110 → 121 → 133.1. Growth is 10%, 10%, 10%, so avg_growth = 10% and volatility = 0. CAGR = (133.1 ÷ 100)1/3 − 1 = 10%. The best-fit slope is about 11 per year; average revenue is about 116, and 11 ÷ 116 ≈ 9.5%, well above 1%, so the trend is increasing.

Why divide the slope by average revenue?

To make the trend fair across company sizes. A rise of ₹1,000 crore a year is huge for a small firm and tiny for a giant. Dividing by average revenue turns it into a percentage, so the same 1% rule works for every company.

Why report both CAGR and average growth?

CAGR only looks at the first and last values and hides what happened in between. Average growth plus volatility shows the path. Two companies with the same CAGR can have very different volatility: one grew steadily, the other swung up and down.

Is there a bug in the CAGR calculation?

Yes, a subtle one worth raising yourself. years = n_periods - 1 assumes one period is one year. With quarterly data, four quarters would be counted as three "years", so the answer is a per-quarter rate wrongly labelled annual. The fix is to work out the real number of years from the period labels.

Why is positive_growth_ratio not sent to the LLM?

Small local models tend to "helpfully" rewrite 0.875 as 87.5%. That is a new number the code never produced, which breaks the core rule. Leaving the ratio out of the prompt removes the temptation.

07

Balance sheet agent

src/balance_sheet_agent.py

Question it answers: how much does the company rely on borrowed money, and is that getting better or worse?

It lines up total assets, total liabilities and equity on the periods where all three exist (at least 4). Negative assets or liabilities are rejected as bad data. Negative equity is allowed with a warning, because a company that owes more than it owns is a real and serious signal, not a data error.

It then calculates the average growth of assets, liabilities and equity, and the leverage ratio = total liabilities ÷ equity, averaged over the periods. Finally, fixed rules decide the risk level.

Worked example

Leverage 2.5, assets growing 6% a year, liabilities 4%, equity 3%. Not above 3, and liabilities are not outgrowing assets, so not high. Leverage is not below 2, so not low. Result: moderate.

Is the leverage ratio the same as debt-to-equity?

Not exactly. It uses total liabilities, which includes things like money owed to suppliers. True debt-to-equity uses only interest-bearing debt. The README calls it D/E, so be precise in the interview.

Where do the 2 and 3 thresholds come from? Do they suit every company?

They are common rules of thumb for ordinary (non-financial) companies. They do not suit banks, which normally run at 10× or more, so this agent would flag every bank as high risk. A better version would use thresholds per industry.

Why fixed rules instead of a machine-learning model?

Every label can be traced to a rule a person can read, which regulators and auditors expect. We also had no labelled data on which companies later got into trouble, which a model would need for training.

08

Liquidity agent

src/liquidity_agent.py

Question it answers: can the company pay the bills that are due in the next year?

It needs current assets, current liabilities, total assets, total liabilities and equity for at least 4 shared periods. "Current" means due or usable within a year.

  • Current ratio = current assets ÷ current liabilities. Above 1 means short-term assets cover short-term bills.
  • Working capital = current assets − current liabilities, and whether it is trending up or down.
  • How much working capital moves around, plus asset, liability and equity growth.

The risk level comes from a points system. More points means more risk.

SignalPoints
Average current ratio below 1.0+3
Average current ratio between 1.0 and 1.5+1
Current ratio trending down+1
Working capital trending down+1
Liabilities growing more than 2 points faster than assets+2
Liabilities growing faster than assets (by less)+1
Working capital swings more than half its average size+1
Total: 4 or more is high, 2–3 moderate, 0–1 low
Worked example

Current ratio 1.2 (+1), current ratio trending down (+1), working capital flat (0), liabilities growing 8% vs assets 5% (8 is more than 5 + 2, so +2), working capital fairly steady (0). Total 4 → high.

The strongest guardrails in the project

This agent does not just trust the LLM to follow instructions. It checks the answer, retries once, and keeps the risk label out of the LLM's hands completely.

Why ban the words "cash flow" in a liquidity agent?

Because no cash-flow data is given to it. If the LLM talks about cash flow, it is inventing information. The rule is simple: only talk about what you were given.

Why keep the risk flag away from the LLM?

If the LLM saw "high" it might soften it to "moderate", or contradict it later in the text. By hiding the flag and adding it in code, the label always matches the calculation exactly.

What is a weakness of this agent?

The displayed liquidity_volatility is in raw currency, so you cannot compare it across companies. Internally the risk score divides it by average working capital, which fixes this, but the number on screen is not normalised.

09

Sentiment agent

src/sentiment_agent.py

Question it answers: what is the news saying about the company right now?

  • Asks NewsAPI for up to 20 recent English articles about the company (free tier: 100 requests a day, last 30 days).
  • For each article, it takes the title and description, splits them into distinct words, and counts how many appear in a list of about 90 positive words and about 120 negative words.
  • Score = (positive − negative) ÷ (positive + negative), giving a number from −1 to +1.
  • 0.15 or more is positive, −0.15 or less is negative, anything between is neutral.
  • It totals the labels, picks 5 representative headlines, and sends those with the counts to the LLM.
  • If there is no NewsAPI key, the agent is simply skipped.
Worked example

Headline: "Infosys shares rise after record deal, but layoffs concern investors". Positive words: rise, record, deal = 3. Negative words: layoffs, concern = 2. Score = (3 − 2) ÷ 5 = 0.2, which is at least 0.15, so the article is labelled positive.

Why keyword counting instead of a model like FinBERT?

It is deterministic and you can show exactly which words drove the score, which fits the project's rule of no unexplained numbers. It also needs no GPU and runs instantly.

What are the weaknesses of keyword sentiment?

It misses negation ("not a loss" counts as negative) and context ("debt reduced" counts as negative). Searching "Apple" also finds articles about the fruit. Each word counts once however often it appears. Improvements: FinBERT, VADER with a financial word list, or matching news by ticker instead of name.

Why the ±0.15 neutral band?

So that one stray word does not flip an otherwise balanced article to positive or negative. Mixed or weak signals land in neutral.

10

Cross-reference agent

agents/cross_reference_agent.py

Question it answers: taken together, what is the overall picture, and do the signals agree or clash?

It receives only the finished metrics from the other agents, never raw data. It builds a "must include" list from whichever agents succeeded, so it never asks the LLM to summarise something that is missing. The LLM is asked to point out agreement or tension, for example "revenue is growing, but leverage is rising and the news is negative".

It only runs when at least 3 of the 4 other agents succeeded. That check lives in app.py.

Why require 3 of 4?

With only one or two inputs there is nothing real to compare, and the LLM would be tempted to fill gaps by guessing. Three gives enough signals to cross-check.

This agent does no maths. Doesn't that break your rule?

No. Its job is to combine results, not calculate. All numbers it sees were already calculated in Python and it is told not to create new ones. A good next step would be an automatic check that every number in its output also appears in its input.

How the agents prompt the LLM

Every agent ends the same way: it has finished its maths, and now it asks an LLM to put the results into words. This section shows exactly how that request is built and sent, with the real prompt code from all five agents.

The shape of every prompt

Each request is a list of two chat messages, sent through LangChain:

  • SystemMessage: the rules. Who the model is, and what it must never do. Models treat the system message as the highest-priority instruction.
  • HumanMessage: the data and the task. A Python dict turned into JSON with json.dumps(): what to explain, the company name, what each metric means, the metric values, and extra output limits.

Where the model settings come from

No agent hard-codes which LLM to use. app.py reads three values from .env once and passes the same three to every agent.

The defaults point at LM Studio running on your own machine (port 1234), which is why the API key defaults to "local". Your .env overrides them with Gemini's OpenAI-compatible endpoint.

Questions on prompting

Why split the prompt into a system message and a human message?

The system message holds rules that never change, and models give it the most weight. The human message holds the data for this one request. Keeping them apart means the rules cannot be confused with the data, and the data can change without touching the rules.

Why send the data as JSON instead of a sentence?

JSON keeps each value next to its exact name, so the model cannot mix them up, and it is built straight from the Python dict with json.dumps(), so there is no hand formatting. It also makes it easy to log exactly what the model was given.

Why include metric definitions?

A name like volatility is ambiguous: volatility of what, in which unit? Without a definition the model guesses, and a wrong guess appears as a confident sentence. The definitions tell it the meaning and the unit, for example "standard deviation of YoY revenue growth, in percentage points".

Why use temperature 0?

Temperature controls randomness. At 0 the model always takes its most likely next word, so the same metrics give nearly the same text every time, which matters for an auditable tool. It does not fully guarantee identical output, which is one more reason no numbers are left to the model.

What do you do when the model ignores the rules?

Rules in the prompt are not enough on their own, especially with small local models. The liquidity agent checks the reply for banned words and risk labels, retries once with a correction, and raises an error if it still fails, so a non-compliant answer is never shown. It also keeps the risk label out of the model's hands entirely and adds it in code.

Why LangChain's ChatOpenAI instead of calling one provider's SDK?

ChatOpenAI speaks the OpenAI API format, which LM Studio, Ollama, OpenRouter and Gemini all offer. So the same code runs against a free local model on a laptop or a hosted model, and switching is a .env change. LangChain also gives a standard message format.

What is prompt injection, and is this project exposed to it?

It is when text inside the data tries to act as instructions to the model. Four agents only send numbers the code calculated, so they are safe. The sentiment agent sends real news headlines, which are written by outsiders, so in principle a crafted headline could try to steer the summary. The impact is limited to display text, and the fix is to clearly mark headlines as quoted data and check the reply.

How would you test a prompt change?

Keep a fixed set of metric inputs (good, borderline and odd cases), run each prompt version against them, and check the replies automatically: no numbers that are not in the input, no banned words, label matches, length within limits. Because temperature is 0, results are stable enough to compare versions.

Running the pipeline

When you click Run Analysis, _run_agent_pipeline() in app.py runs the agents one after another. Before each one it checks whether the required fields exist; if not, the agent is skipped with a clear reason. Every agent is wrapped in _safe_run(), so if one crashes, its error is stored and the next agent still runs. This is called graceful degradation.

Readiness check and gap filling

Before running, the app shows which agents can run with the fields available. The user can proceed anyway (agents that cannot run are skipped) or fix missing data, either by fetching it from FMP or Alpha Vantage (supplemental_fetchers.py) or by typing it in. The JSON is updated and the agent files are rewritten.

Why run the agents one after another instead of in parallel?

It was simpler and fits Streamlit's loading spinners. The first four agents do not depend on each other and mostly wait on the LLM, so running them in a thread pool would cut total time to roughly the slowest one. Cross-reference must still wait for the rest.

What happens if the LLM server is down?

Each agent's LLM call fails, _safe_run stores the error, and the dashboard shows it. A good improvement would be to still show the calculated metrics when only the explanation fails, since the numbers do not depend on the LLM.

Isn't mixing data from different sources risky?

Yes, units and currencies can differ. That is why the credibility engine flags implausible jumps (likely unit mix-ups) and cross-checks Yahoo figures against FMP.

Login and security

Nothing renders until you are logged in. Passwords are stored as bcrypt hashes, never as plain text. A correct login returns a JWT, a signed token that proves who you are for 24 hours. Every time the page reloads, the token is checked, and if you have been idle for over 15 minutes you are sent back to the login page.

Forgot password: one-time code

A 6-digit code is emailed through Gmail SMTP (encrypted with STARTTLS). It is valid for 2 minutes and is deleted as soon as it is used, so it cannot be reused. MongoDB has a unique index on email, so the database itself refuses a second account with the same address.

Heads-up: the README says the OTP is sent when you register. In the code it is only used for forgot password. Describe it that way.
Why bcrypt and not SHA-256 for passwords?

bcrypt is slow on purpose and adds a random salt to every password. Slow means an attacker can try far fewer guesses per second; the salt means two users with the same password get different hashes, so precomputed lookup tables are useless. SHA-256 is designed to be fast, which helps attackers.

Why use a JWT?

The token carries the user's id and an expiry time and is signed with a secret key. The server can verify it without storing sessions in a database, and any change to the token breaks the signature.

What would you improve in the security?

Raising these yourself shows maturity:

  • The token sits in the URL, where it can leak through browser history and logs. Use a secure, HTTP-only cookie.
  • The OTP uses Python's random; it should use secrets, which is built for security.
  • There is no limit on OTP attempts, so it could be guessed. Add rate limiting.
  • JWT_SECRET has a hard-coded fallback. The app should refuse to start without a real secret.
  • Login messages reveal whether an email is registered. Use one generic message.
  • A token cannot be cancelled before it expires. Use short-lived tokens with refresh, or a block list.

The later main branch fixed several of these (field encryption, MFA, security CI), which you can mention as how the project grew.

General questions

What was your own contribution?

Prepare this yourself: name the specific modules you wrote, one problem you solved, and one decision you made and why. Concrete beats general.

What was the hardest problem?

Good answers: making small local LLMs obey the rules (which led to hiding ratios, hiding the risk flag and adding the check-and-retry loop), and handling the many different label and period formats in Bloomberg exports.

How did you test it?

At this commit, manually, with sample outputs for Apple and Infosys in the output/ folder. There were no automated tests yet; the later main branch added a pytest suite. Say this honestly.

Why at least 4 periods?

Four values give three growth rates, the minimum where an average, a spread and a trend line mean anything. With fewer points the trend and volatility would be noise.

How would it scale to many users?

Streamlit keeps each user's state separately and MongoDB Atlas scales on its own. The slow part is the LLM calls: run independent agents in parallel and cache results for identical inputs.

Is FinVeritas Basel III compliant?

No, and do not overclaim. It does not calculate capital ratios such as CET1, LCR or NSFR. It supports the spirit of Pillar 2 (supervisors reviewing risk) through risk trend monitoring, and Pillar 3 (disclosure) through an explainable audit trail.

How do you know the LLM did not add numbers?

Three layers: it only receives the metrics, the prompt forbids new numbers, and the liquidity agent checks its output and retries. The next step would be an automatic check that every number in any output appears in its input.
