What is data engineering?

In one line: data engineering means taking raw, messy data, cleaning and shaping it, and handing it to the people who need it, as a clean data model.

There are thousands of definitions online. Don't memorise one. Understand the journey:

Raw data → Transformations → Serve to stakeholders

Simple analogy

A data engineer is a chef. The raw vegetables (potato, onion, carrot) are the raw data. The chef cooks them (transformations) and serves a nice dish (a clean data model) to the customers (analysts, data scientists, managers). Nobody wants to eat a raw potato. Nobody wants to report on raw data either.

Why do companies need data engineers?

  • The amount of data is growing very fast, and that pushes up demand for data engineers too.
  • Businesses want to make data-driven decisions. Someone has to prepare that data well. That's the data engineer.
  • Tools come and go, but fundamentals stay the same. The video says about 50% of DE interview questions come from these basics.
028:26

The workflow: three pillars

1. Data production

Any activity that creates data: a CSV file, a database row, a Google search, a phone call, an Amazon click.

2. Data transformation

Turning raw data into curated data. A data engineer spends most of their time (about 70–80%) here.

3. Data serving

You can't hand over one giant pot of food. You serve plates: half plate, full plate. In the same way, you build data models that fit each consumer.

Interview

"What are the three pillars of data engineering?" Data production, data transformation and data serving.

Data production & where data is stored

Data is generated all the time. On Amazon, clicking an item, picking a quantity, choosing an address, paying, and getting the confirmation each create data. On Prime Video, searching for a movie, watching it and rating it also create data.

  • API: a connector that lets one application pull information from another. Data you fetch through an API also counts as data production.
  • All of this data lands in a storage (a database). The data engineer reads from that storage, not from the clicks themselves. A chef only needs the ingredients in the kitchen and doesn't care who brought them.

Upstream & downstream

Picture a river. Water flows from upstream to downstream, and you are standing in the middle. Data flows the same way.

  • Upstream = whoever sends you data: DBAs, and in small companies sometimes software or web developers.
  • Downstream = whoever you serve data to: analysts, data scientists, managers.
  • You get requirements from downstream and data from upstream. Keep a good working relationship with both sides. Sometimes you have to ask upstream to change something in the source for a project.
Gotcha

"Downstream" says nothing about rank. Analysts are not "below" engineers. The word only describes which way the data flows.

OLTP vs OLAP

Both are called "databases", which is why people mix them up. The easy way to remember: OLTP is built for writing. OLAP is built for reading.

OLTPOLAP
Full formOnline Transactional ProcessingOnline Analytical Processing
Also calledTransactional DB, source systemData warehouse
Optimised forWrites & updates (small, frequent)Reads (large analytical queries)
ModelingNormalization (1NF, 2NF, 3NF)Dimensional modeling (facts & dims)
Who owns itDBA / software engineersData engineer
ExamplesPostgreSQL, MySQL, SQL Server, OracleSnowflake, Azure Synapse, Redshift, BigQuery, WhereScape RED

What normalization looks like (the OLTP side)

Normalization splits data into many small tables so that each fact is stored only once. That makes writes safe and quick. In practice people normalize up to 3NF. Going further gets hard to manage.

oltp_normalized.sqlNot run
-- OLTP: normalized (3NF). Many small tables, each fact stored once.
CREATE TABLE customers (
  customer_id INT PRIMARY KEY,
  name        VARCHAR(100),
  city_id     INT REFERENCES cities(city_id)   -- city stored once, in its own table
);
CREATE TABLE orders (
  order_id    INT PRIMARY KEY,
  customer_id INT REFERENCES customers(customer_id),
  order_ts    TIMESTAMP
);
CREATE TABLE order_items (
  order_id    INT REFERENCES orders(order_id),
  product_id  INT REFERENCES products(product_id),
  quantity    INT,
  price       DECIMAL(10,2)
);
-- Each click / purchase = one small INSERT. Very fast.
INSERT INTO orders VALUES (1001, 7, CURRENT_TIMESTAMP);
Interview

"Why not run reports straight on the OLTP DB?" It holds a huge amount of row-by-row transactional data and it's tuned for writes. Heavy report queries would be slow, and they would also slow down the live application. So we copy the data into an OLAP warehouse that is modeled for reads.

ETL & data pipelines

ETL = Extract → Transform → Load. It's how data moves from OLTP into OLAP.

  • Extract: pull data from the source.
  • Transform: clean it and reshape it.
  • Load: write it into the warehouse.

The source keeps changing, maybe every hour, and you don't want to repeat this by hand every day. So you build an ETL pipeline that runs on its own.

Simple analogy

A water pipeline brings water from the dam to your tap. You don't walk to the dam with buckets. A data pipeline brings data from the source to the warehouse in the same automatic way.

etl_pipeline.pyNot run
import pandas as pd
from sqlalchemy import create_engine

src = create_engine("postgresql://user:pass@oltp-host/shop")      # OLTP source
dw  = create_engine("postgresql://user:pass@dw-host/warehouse")   # OLAP target

def extract():
    return pd.read_sql("SELECT * FROM orders", src)

def transform(df):
    df = df.dropna(subset=["customer_id"])          # drop junk rows
    df["order_date"] = pd.to_datetime(df["order_ts"]).dt.date
    df["amount"] = df["quantity"] * df["price"]
    return df[["order_id", "customer_id", "order_date", "amount"]]

def load(df):
    df.to_sql("fact_orders", dw, if_exists="append", index=False)

# A scheduler (cron / Airflow / Azure Data Factory) runs this every hour = a "pipeline"
load(transform(extract()))
Extra

ETL vs ELT: in ELT you load the raw data first and transform it later, inside the warehouse or lake. That's common on the cloud because storage and compute are cheap. The medallion architecture (section 18) is basically ELT.

0755:00

Data warehouse layers: staging & core

Data doesn't jump straight from the source into the final model. It passes through layers. For now, think of a layer as a folder.

  • Staging layer: dump the extracted data here first.
  • Core layer: transform the staged data into facts and dimensions.
  • Transient staging: temporary. After the core is built, staging is truncated and refilled with the next batch. About 99% of projects use this.
  • Persistent staging: keeps every batch so you have the full history. Rare, and only when the project needs it.
Interview

"Why have a staging layer at all?" If the transformations queried the source directly, they would slow down the live source system. So you copy the data once into staging, then do all the heavy work from there.

transient_staging.sqlNot run
-- Each run: empty staging, reload it, then build core from it.
TRUNCATE TABLE stg_orders;                       -- "transient" = wipe old batch

INSERT INTO stg_orders                           -- Extract
SELECT * FROM oltp.orders WHERE order_ts >= :batch_start;

INSERT INTO core.fact_orders (order_id, customer_key, date_key, amount)   -- Transform + Load
SELECT s.order_id, c.customer_key, CAST(FORMAT(s.order_ts,'yyyyMMdd') AS INT), s.quantity * s.price
FROM stg_orders s
JOIN core.dim_customer c ON c.customer_id = s.customer_id;

Incremental loading

People call this an "advanced" topic, but the idea is simple: only load the data that is new since the last run.

This is a working version using Python's built-in sqlite3. It keeps a watermark table that remembers how far it has loaded:

incremental_load.pyRan
import sqlite3
db = sqlite3.connect(":memory:")
db.executescript("""
CREATE TABLE src_orders(order_id INT PRIMARY KEY, amount REAL, order_date TEXT);   -- source
INSERT INTO src_orders VALUES (1,100,'2024-01-01'),(2,250,'2024-01-01');
CREATE TABLE dw_orders(order_id INT PRIMARY KEY, amount REAL, order_date TEXT);    -- warehouse
CREATE TABLE watermark(tbl TEXT PRIMARY KEY, last_date TEXT);                      -- bookmark
INSERT INTO watermark VALUES ('orders','1900-01-01');
""")

def incremental_load():
    last = db.execute("SELECT last_date FROM watermark WHERE tbl='orders'").fetchone()[0]
    new = db.execute("SELECT * FROM src_orders WHERE order_date > ?", (last,)).fetchall()
    db.executemany("INSERT INTO dw_orders VALUES (?,?,?)", new)
    if new:   # move the bookmark forward
        db.execute("UPDATE watermark SET last_date=? WHERE tbl='orders'", (max(r[2] for r in new),))
    return len(new)

assert incremental_load() == 2     # day 1: loads all history
db.execute("INSERT INTO src_orders VALUES (3,75,'2024-01-02')")
assert incremental_load() == 1     # day 2: loads ONLY the new row
assert incremental_load() == 0     # nothing new, nothing loaded
Gotcha

A plain date > last_date filter misses rows that arrive late or get updated after you loaded them. In real projects you use an updated_at column, or change data capture (CDC), and you upsert (MERGE) instead of a plain INSERT. Extra

Interview

"What is incremental loading and how would you implement it?" It means loading only new or changed data since the last successful run. You track a watermark (max date or ID) and filter the source by it. Then you append or merge into the target and move the watermark forward.

Dimensional modeling: facts & dimensions

This is how we model the warehouse. Split the data into two kinds of tables:

Fact table

Holds the numbers (measures): price, bill, quantity, weight. It also holds the keys that link to the dimensions. It's the centre of the model.

Dimension table

Holds the context, the descriptive text. dim_customer has name and address. dim_product has name and category. It's grouped by business entity.

Dimensions are denormalized: everything about a customer sits in one table, even if some values repeat. That means fewer joins, so reads are faster.

star_schema.sqlNot run
-- Dimensions: descriptive context
CREATE TABLE dim_product (
  product_key  INT PRIMARY KEY,      -- surrogate key (warehouse-owned)
  product_id   INT,                  -- business key from source
  product_name VARCHAR(100),
  category     VARCHAR(50)           -- denormalized: no separate category table
);
CREATE TABLE dim_customer (
  customer_key INT PRIMARY KEY,
  customer_id  INT,
  name VARCHAR(100), city VARCHAR(50), country VARCHAR(50)
);
CREATE TABLE dim_date (date_key INT PRIMARY KEY, full_date DATE, month INT, year INT);

-- Fact: numbers + foreign keys
CREATE TABLE fact_sales (
  product_key  INT REFERENCES dim_product(product_key),
  customer_key INT REFERENCES dim_customer(customer_key),
  date_key     INT REFERENCES dim_date(date_key),
  quantity     INT,
  amount       DECIMAL(10,2)
);

-- A typical report query: one hop from fact to each dimension
SELECT p.category, d.year, SUM(f.amount) AS revenue
FROM fact_sales f
JOIN dim_product p ON p.product_key = f.product_key
JOIN dim_date    d ON d.date_key    = f.date_key
GROUP BY p.category, d.year;
Interview

"Star vs snowflake?" In a star schema, denormalized dimensions connect directly to the fact. It has fewer joins and faster queries, and it's the industry default. A snowflake schema normalizes the dimensions into hierarchies. That saves a bit of storage, but you pay with more joins and more complexity.

Slowly Changing Dimensions (SCD)

The video ranks this among the top 3 most important topics. Dimension data sometimes changes in the source. The question is how your dimension handles that change.

Scenario used throughout: product 3 "Comb" was in category Clothing. The source changes it to Hair.

TypeNicknameWhat happensKeeps history?
SCD 0FixedDimension never changes. Ignore updates.n/a
SCD 1Upsert / overwriteUpdate the row in place. Insert new rows.No. Used about 70–80% of the time.
SCD 2Full historyClose the old row (end date, flag=0) and insert a new row.Yes, full history with dates
SCD 3Previous valueKeep a previous_* column next to current_*.Only the one previous value

SCD Type 1: upsert (update + insert)

scd1_upsert.pyRan
db.executescript("""
CREATE TABLE dim_product(product_id INT PRIMARY KEY, name TEXT, category TEXT);
INSERT INTO dim_product VALUES (1,'Honey','Food'),(2,'Shirt','Clothing'),(3,'Comb','Clothing');
""")
incoming = [(3,'Comb','Hair'), (4,'Shoes','Footwear')]
# UPSERT: insert, and if the key already exists, update instead
db.executemany("""INSERT INTO dim_product VALUES (?,?,?)
  ON CONFLICT(product_id) DO UPDATE SET name=excluded.name, category=excluded.category""", incoming)

assert db.execute("SELECT category FROM dim_product WHERE product_id=3").fetchone()[0] == 'Hair'
assert db.execute("SELECT COUNT(*) FROM dim_product").fetchone()[0] == 4

In a warehouse (SQL Server, Synapse, Databricks) you write the same thing with MERGE:

scd1_merge.sqlNot run
MERGE INTO dim_product AS tgt
USING stg_product      AS src
  ON tgt.product_id = src.product_id
WHEN MATCHED THEN
  UPDATE SET tgt.name = src.name, tgt.category = src.category      -- overwrite
WHEN NOT MATCHED THEN
  INSERT (product_id, name, category) VALUES (src.product_id, src.name, src.category);
Interview

Interviewers often say "we need an upsert" instead of "SCD Type 1". When you hear upsert, think SCD 1.

SCD Type 2: keep the full history

Add three columns: start_date, end_date (or expiry date) and an is_current flag. When a value changes, you don't overwrite it. You close the old row and insert a new one. For rows that are still active, set the end date far in the future, like 3000-12-31.

scd2_history.pyRan
db.executescript("""
CREATE TABLE dim_product_h(sk INTEGER PRIMARY KEY AUTOINCREMENT, product_id INT, name TEXT,
  category TEXT, start_date TEXT, end_date TEXT, is_current INT);
INSERT INTO dim_product_h(product_id,name,category,start_date,end_date,is_current) VALUES
 (1,'Honey','Food','2024-01-01','3000-12-31',1),
 (2,'Shirt','Clothing','2024-01-01','3000-12-31',1),
 (3,'Comb','Clothing','2024-01-01','3000-12-31',1);
""")

def scd2(pid, name, cat, day):
    cur = db.execute("SELECT category FROM dim_product_h WHERE product_id=? AND is_current=1",
                     (pid,)).fetchone()
    if cur and cur[0] == cat:
        return                                     # nothing changed
    # 1) expire the current row
    db.execute("UPDATE dim_product_h SET end_date=?, is_current=0 "
               "WHERE product_id=? AND is_current=1", (day, pid))
    # 2) insert the new version
    db.execute("INSERT INTO dim_product_h(product_id,name,category,start_date,end_date,is_current) "
               "VALUES (?,?,?,?,'3000-12-31',1)", (pid, name, cat, day))

scd2(3, 'Comb', 'Hair', '2024-01-02')
rows = db.execute("SELECT category,start_date,end_date,is_current FROM dim_product_h "
                  "WHERE product_id=3 ORDER BY sk").fetchall()
assert rows == [('Clothing','2024-01-01','2024-01-02',0), ('Hair','2024-01-02','3000-12-31',1)]
Extra

Because SCD 2 creates several rows per product, the fact table must link to the surrogate key (sk), not to product_id. That way, a sale from last year still points to "Clothing".

SCD Type 3: keep only the previous value

Cheaper than Type 2. There are no date columns, just one extra column.

scd3_previous.sqlRan
CREATE TABLE dim_product3(product_id INT PRIMARY KEY, name TEXT,
                          current_category TEXT, previous_category TEXT);
INSERT INTO dim_product3 VALUES (3,'Comb','Clothing','Clothing');

-- on change: shift current into previous, then set the new current
UPDATE dim_product3
SET previous_category = current_category,
    current_category  = 'Hair'
WHERE product_id = 3;
-- result: current_category = 'Hair', previous_category = 'Clothing'
Remember

0 = no change · 1 = overwrite (upsert) · 2 = new row + dates (full history) · 3 = previous-value column

Data lake

A data warehouse only handles structured data (tables). Data started growing very fast and arriving in every shape: JSON, CSV, images, logs. Forcing all of it into tables became too hard. A data lake stores data of any format, cheaply, in files.

The three shapes of data

TypeWhat it meansFormats / examplesStored in
StructuredFixed rows and columns, and the schema is defined firstSQL tables (MySQL, Postgres), Excel sheetsWarehouse and lake
Semi-structuredHas some structure (keys, tags, headers), but no fixed table schema. Fields can vary from record to record.JSON, CSV, XML, Avro, Parquet/ORC (self-describing files), YAML, log filesLake
UnstructuredNo predefined structure at allImages, videos, audio, PDFs, emails, free textLake
semi_structured.jsonExample
[
  {"order_id": 1, "customer": "Asha", "items": [{"sku": "A1", "qty": 2}]},
  {"order_id": 2, "customer": "Ravi", "coupon": "DIWALI10"}
]

Both records are orders, but the second one has a coupon field and no items list. A rigid SQL table can't hold that easily. A data lake stores it as it is. That's what "semi-structured" means.

Gotcha

The video calls CSV semi-structured. Some books call CSV "structured", because it's really rows and columns. In interviews, the safe answer is "JSON, XML and CSV are semi-structured formats", and if asked, you can mention that CSV is a borderline case.

Data warehouseData lake
Data formatStructured onlyStructured + semi-structured (CSV, JSON) + unstructured
SchemaSchema-on-write: define the table first (DDL), then insertSchema-on-read: store raw files first, define the schema later
CostExpensive storageVery cheap storage. This is the main reason businesses moved.
Used forBI reportingBig data processing, ML, reporting, IoT

# Schema-on-WRITE (warehouse): the table must exist before data goes in
#   CREATE TABLE orders(order_id INT, amount DECIMAL);  then INSERT ...

Lakehouse = data lake + data warehouse

So should you throw away everything you learned about warehouses? No. A lakehouse takes the best part of each:

  • From the lake: cheap storage for any file format.
  • From the warehouse: tables, dimensional models and fast SQL reporting.

The trick is a metadata layer (also called the abstraction or logical layer). It sits on top of the files in the lake and makes them look and behave like tables.

lakehouse_sql.sqlNot run
-- Databricks / Spark SQL: a "table" whose data is really files in the lake
CREATE TABLE gold.dim_product
USING DELTA
LOCATION 'abfss://gold@mylake.dfs.core.windows.net/dim_product';

-- Analysts query it with normal SQL, unaware it's files underneath
SELECT category, COUNT(*) FROM gold.dim_product GROUP BY category;

File formats: row-based vs column-based

The difference is how the data is laid out on disk.

  • Row-based (CSV, Avro): writes record by record, so adding or updating a row is easy. Use it on the OLTP side.
  • Column-based (Parquet, ORC): writes column by column. SELECT product_id FROM dim_product reads one block and doesn't jump over every row. Use it for OLAP and big data.
row_vs_column.pyRan
rows = [(1,'Honey','Food'), (2,'Shirt','Clothing'), (3,'Comb','Clothing')]

row_layout = [v for r in rows for v in r]             # how CSV lays it on disk
col_layout = [v for col in zip(*rows) for v in col]   # how Parquet lays it on disk

print(row_layout)  # [1, 'Honey', 'Food', 2, 'Shirt', 'Clothing', 3, 'Comb', 'Clothing']
print(col_layout)  # [1, 2, 3, 'Honey', 'Shirt', 'Comb', 'Food', 'Clothing', 'Clothing']
# Reading just "product_id": the column layout gives it as ONE contiguous chunk [1,2,3]
csv_to_parquet.pyNot run
import pandas as pd                        # needs: pip install pandas pyarrow
df = pd.read_csv("products.csv")
df.to_parquet("products.parquet")          # columnar + compressed, usually much smaller
pd.read_parquet("products.parquet", columns=["product_id"])   # reads only that column
Extra

Columnar files also compress much better, because the values in one column look alike (Clothing, Clothing, …). That's another reason Parquet is the default in big data.

Delta format (Delta Lake)

Delta is an open table format built on top of Parquet. The data itself is still stored as Parquet files. Delta adds a transaction log folder (_delta_log/) full of JSON files, and each JSON file records one change made to the table.

1. Time travel / versioning

Every write creates a new version. Deleted something by mistake? Go back to an older version.

2. Schema evolution

The source adds a 6th column? Delta can add it to the table instead of failing.

3. ACID transactions

Atomicity, Consistency, Isolation, Durability. These are database-grade guarantees on cheap lake storage.

delta_demo.py (PySpark + Delta)Not run
# Works out of the box on Databricks. Locally: pip install delta-spark
path = "/tmp/delta/products"

df = spark.createDataFrame([(1,"Honey","Food"), (2,"Shirt","Clothing"), (3,"Comb","Clothing")],
                           ["product_id", "name", "category"])
df.write.format("delta").mode("overwrite").save(path)                 # version 0

spark.sql(f"UPDATE delta.`{path}` SET category='Hair' WHERE product_id=3")   # version 1
spark.sql(f"DELETE FROM delta.`{path}` WHERE product_id=1")                  # version 2 (mistake!)

# See every version recorded in _delta_log
spark.sql(f"DESCRIBE HISTORY delta.`{path}`").select("version", "operation").show()

# TIME TRAVEL: read the table as it was at version 1
spark.read.format("delta").option("versionAsOf", 1).load(path).show()

# Restore it
spark.sql(f"RESTORE TABLE delta.`{path}` TO VERSION AS OF 1")

# SCHEMA EVOLUTION: append data that has a new column
new = spark.createDataFrame([(4,"Shoes","Footwear",999.0)], ["product_id","name","category","price"])
new.write.format("delta").mode("append").option("mergeSchema", "true").save(path)
Interview

"Delta vs Parquet?" Delta is Parquet files plus a JSON transaction log. The log adds ACID transactions, time travel and schema evolution, and it supports MERGE, UPDATE and DELETE on lake data.

Distributed computing with Apache Spark

Simple analogy

Picture the 20 computers in your college lab joined into one super-computer. Or picture a professor giving you an assignment: you split it into pieces, hand them to 10 friends, and they finish it far faster than you would alone. That's distributed computing. A group of machines working together is called a cluster.

spark_basics.pyNot run
from pyspark.sql import SparkSession, functions as F   # pip install pyspark

spark = SparkSession.builder.appName("sales").getOrCreate()   # this program is the DRIVER

df = spark.read.parquet("data/sales/")      # the data is split into partitions
print(df.rdd.getNumPartitions())            # each partition can go to a different worker

result = (df.filter(F.col("amount") > 0)    # transformations are LAZY: just a plan
            .groupBy("category")
            .agg(F.sum("amount").alias("revenue")))

result.show()   # ACTION: now the driver sends tasks to workers, they compute in parallel
Extra

Spark is lazy. filter and groupBy only build a plan. Nothing runs until an action such as show(), count() or write. This comes up in interviews as "transformations vs actions".

Medallion architecture (bronze → silver → gold)

This is the modern cloud version of staging → core. The layers are named after medals, and the data gets cleaner at each step.

medallion.py (Databricks / PySpark)Not run
from pyspark.sql import functions as F
lake = "abfss://{layer}@mylake.dfs.core.windows.net/orders"

# BRONZE: land raw data exactly as received (rule #1: no changes)
raw = spark.read.json("abfss://landing@mylake.dfs.core.windows.net/orders/")
raw.write.format("delta").mode("append").save(lake.format(layer="bronze"))

# SILVER: clean + fix types + dedupe
bronze = spark.read.format("delta").load(lake.format(layer="bronze"))
silver = (bronze.dropDuplicates(["order_id"])
                .filter(F.col("customer_id").isNotNull())
                .withColumn("order_date", F.to_date("order_ts"))
                .withColumn("amount", F.col("quantity") * F.col("price")))
silver.write.format("delta").mode("overwrite").option("mergeSchema", "true") \

Interview Q&A

Click an answer to reveal it.

What are the three pillars of data engineering?

Data production (generation and storage), data transformation, and data serving (data models for stakeholders).

Who are your upstream and downstream teams?

Upstream sends you data: DBAs and software developers. Downstream consumes your data and gives you requirements: data analysts, data scientists, analytics managers.

OLTP vs OLAP?

OLTP is transactional, tuned for writes and updates, normalized (up to 3NF), and owned by the DBA. OLAP is the data warehouse, tuned for reads, dimensionally modeled, and owned by the data engineer.

Why do we need a staging layer? Transient vs persistent?

Staging stops heavy transformations from querying (and slowing down) the source. Transient staging is truncated every run (about 99% of cases). Persistent staging keeps history.

What is incremental loading?

Loading only the data that is new or changed since the last run. You track a watermark (last date or ID), filter the source by it, then append or merge into the target. This saves compute and time.

Fact vs dimension table?

A fact table holds numeric measures (price, quantity) and foreign keys. A dimension table holds descriptive context (customer, product, date), grouped by entity and denormalized.

Star vs snowflake schema, and which is used more?

Star: dimensions link directly to the fact. Snowflake: dimensions are normalized into hierarchies. Star is used most of the time because it's faster, has fewer joins, and is easier to manage.

Interviewer says "we need an upsert". Which SCD?

SCD Type 1: update the row if it exists, insert it if it doesn't. No history is kept.

How do you design SCD Type 2?

Add start_date, end_date and an is_current flag. On a change, expire the old row (set end_date, flag = 0) and insert a new row (end_date far in the future, flag = 1). Use surrogate keys.

SCD 2 vs SCD 3?

SCD 2 keeps the full history with dates, one row per version. SCD 3 keeps only the previous value in an extra column. It's cheaper but has limited history.

Data lake vs data warehouse?

A lake stores any format (structured, semi-structured, unstructured) using schema-on-read, and storage is very cheap. A warehouse stores structured data only, with schema-on-write, and costs more.

What is a lakehouse?

Data lake storage plus a metadata/table layer (such as Delta) on top. You get warehouse features (tables, SQL, dimensional models, ACID) on cheap lake files.

Row-based vs column-based file formats?

Row-based (CSV, Avro) stores record by record. It's good for writes, so it suits OLTP. Column-based (Parquet, ORC) stores column by column. It's good for analytical reads and compression, so it suits OLAP and big data.

What does Delta Lake add on top of Parquet?

A transaction log (_delta_log JSON files) that adds ACID transactions, versioning and time travel, schema evolution, and UPDATE, DELETE and MERGE support.

Explain Spark architecture.

A cluster has one driver node (the brain: it plans and assigns tasks) and many worker nodes (they run the tasks on data partitions in parallel). Databricks manages these clusters for you.

Explain medallion architecture.

Bronze holds raw data with no changes. Silver holds cleaned, transformed data with the schema enforced. Gold holds business-ready facts, dimensions and aggregates for BI and data science.

Which Azure service stores streaming data? Which is the ETL tool? Which is the warehouse?

Streaming: Event Hubs. ETL: Azure Data Factory. Warehouse: Azure Synapse Analytics. Lake: ADLS Gen2. Processing: Databricks. Secrets: Key Vault.
