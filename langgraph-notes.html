What is Agentic AI?

Interview · definition

Agentic AI is AI that takes a goal from a user and works toward it mostly on its own. It plans, takes actions, adapts when things change, and asks a human only when it needs to.

A GenAI chatbot is reactive: it answers exactly the question you asked, one turn at a time. An agentic system is proactive. Say "I want to go to Goa between these dates" and it works out transport, hotels and an itinerary without being prompted for each step.

Running example: the AI recruiter

The goal given to the agent is "hire a remote backend engineer with 2 to 4 years of experience". The agent turns this into a plan and carries it out, pausing for approval at the risky steps.

The six characteristics of an agentic system

Interview

"How do you tell if a system is agentic?" Ask these six questions. If all six are yes, it is agentic.

Autonomy

  • It shows up everywhere: in execution (runs the steps itself), in decisions (how many candidates to shortlist and on what basis) and in tool use (which tool, when).
  • Autonomy also makes it proactive: it noticed the low application count by itself. With ChatGPT you would have had to notice and ask.
Interview · controlling autonomy
  • Permission scope: limit which tools and actions it can use alone (it may screen resumes but must ask before rejecting anyone).
  • Human-in-the-loop: checkpoints that need human approval before continuing (approve the JD before posting).
  • Override controls: the user can pause, stop or redirect at any time ("pause hiring").
  • Guardrails and policies: hard rules it must follow (no interviews on weekends, formal language only).

Why it matters: an unchecked agent could send offers with the wrong salary, shortlist with bias (age, nationality, which is illegal in some countries) or spend unlimited money on ads.

Goal-oriented

  • The goal is the compass for autonomy. Autonomy says the agent can act alone; the goal says what to act toward.
  • Goals can be plain ("hire a backend engineer") or carry constraints (India only, remote only, a fixed budget).
  • Goals sit in the agent's core memory, roughly like the JSON below (each library stores this differently).
  • Goals can change midway, for example "hire a freelancer instead". The plan then changes with it.

Planning

Every agentic system works in two stages, planning and execution, and runs them in a loop. If a step turns out to be impossible midway, it goes back and re-plans.

Interview · how an agent plans
  1. Generate candidate plans. Planning is a search from an initial state (we need an engineer) to a goal state (we hired one), and there are many paths. Plan A: post on job portals. Plan B: internal referrals or a hiring agency.
  2. Evaluate them on efficiency (speed), tool availability (a plan that needs Google Search is out if there is no search tool), cost, risk of failure, and fit with constraints (which plan finds remote candidates?).
  3. Select one, either by asking the human (HITL) or by a pre-programmed policy. Then execute it.

Reasoning

Reasoning means interpreting information, drawing a conclusion and making a decision. Human example: your phone is stolen (information), the thief could misuse your number (conclusion), so you call your carrier to block the SIM (decision).

During planning

  • Goal decomposition into steps
  • Tool selection per step ("salary for 2-4 yrs" needs a search tool)
  • Estimating time, dependencies and risk

During execution

  • Decisions between options (interview 2 or 3 candidates?)
  • When to ask a human versus act alone
  • Error handling: LinkedIn is down, so retry later, notify the human, or post elsewhere

Adaptability

Adaptability means changing plans, strategies or actions when something unexpected happens, while staying aligned with the goal. Three triggers:

  • Failures: the calendar API is down, so the agent asks the human for availability directly.
  • External feedback from the environment: only 2 applications came in. The environment is everything the agent acts in: the board for a chess agent, the road for a driving agent, LinkedIn plus applicants plus the human for the recruiter.
  • Goal changes: the human switches to hiring a freelancer.

Context awareness and memory

An agent keeps: the original goal, progress and the conversation so far, the state of the environment (job posted, 8 applicants, ad budget ends in 2 days), tool responses (candidate B has 3 years of Django and AWS), user preferences (send questions as a Google Doc) and guardrails (never send an offer without approval). This is implemented with memory.

Interview · short-term vs long-term memory

Short-term: the current session: messages, tool results, immediate decisions. Long-term: things that persist across sessions: high-level goals, past interactions, user preferences, guardrails. Human analogy: "finish the video before the 4 pm meeting" is short-term; "I live in Gurgaon" is long-term.

The five components of an agentic system

Interview
  • Brain (LLM): interprets the goal, plans, reasons, picks tools, reads and writes natural language. It does most of the heavy lifting.
  • Orchestrator: executes the plan: task order, conditional routing, retry logic, loops, and delegating to the LLM or a human. Like the nervous system or a project manager. Frameworks such as LangGraph, CrewAI and AutoGen give you classes to build it.
  • Tools: the hands and legs. Every external action (API call, DB write, email) goes through a tool. A RAG knowledge base is also a tool.
  • Memory: short-term, long-term and state tracking (what is done, what is left).
  • Supervisor: implements human-in-the-loop. It gets approval for high-risk actions, enforces guardrails and escalates edge cases (a great resume from outside the allowed colleges).

If you go deeper, the brain can itself split into a planner (makes plans) and an evaluator (scores them).

LangChain vs LangGraph

Quick LangChain recap

LangChain is an open-source library for building LLM-based applications from modular blocks:

  • Models: one interface for any provider (OpenAI, Anthropic, Hugging Face, Ollama), so swapping LLMs needs few code changes.
  • Prompts: prompt templates and prompt engineering.
  • Retrievers: fetch relevant documents from a vector store or knowledge base (the basis of RAG).
  • Chains: join components so each output becomes the next input automatically, for example prompt, then model, then output parser.

With these you can build chatbots and summarizers, multi-step chains (topic, then report, then summary), RAG apps and simple tool-calling agents (such as a weather tool).

Interview · workflow vs agent

This follows Anthropic's "Building effective agents" blog. A workflow is a system where LLMs and tools are orchestrated through predefined code paths: the developer draws the flowchart, and it runs the same path every time. An agent is a system where the LLM dynamically decides its own process and tool use. Both use LLMs; the agent has more autonomy. The hiring flowchart below is a workflow.

Subgraph use cases

  • Multi-agent systems: a self-driving car might have a sensor agent, a driving agent, an entertainment agent and a "CEO" agent coordinating them, each its own graph.
  • Reusability: build one small approval workflow and reuse it for JD approval, posting approval and interview approval, the way you reuse a function.
  • "Conduct interview" in the hiring flow is itself a workflow (per-candidate questions, rounds, evaluations), so it fits as a subgraph. The tricky part is how the parent and child states talk to each other (covered later in the playlist).
Interview · definition

LangGraph is an orchestration framework for building stateful, multi-step, event-driven workflows with LLMs. It suits both single-agent and multi-agent applications. Think of it as a flowchart engine for LLMs: you define steps as nodes, connect them with edges, and LangGraph handles state, branching, looping, pausing and resuming, and fault recovery.

Interview · when to use which
  • LangChain for simple linear flows: a prompt chain, a summarizer, a basic RAG pipeline.
  • LangGraph for complex non-linear flows: conditional paths, loops, human-in-the-loop, multi-agent coordination, asynchronous or event-driven runs.
  • Does LangGraph replace LangChain? No. LangGraph is built on top of LangChain. Inside nodes you still use LangChain components: ChatOpenAI, prompt templates, retrievers, document loaders, text splitters, tools. LangChain gives the components; LangGraph orchestrates them.

LangGraph core concepts

LLM workflows

A workflow is a series of tasks executed in the right order to reach a goal. An LLM workflow is one where some of those tasks depend on an LLM: prompting, reasoning, tool calling, memory access, decision making. Workflows can be linear, parallel, branched or looped.

Five common LLM workflow patterns

Interview

Parallelization vs orchestrator-workers: both run sub-tasks in parallel and aggregate. In parallelization the sub-tasks are fixed in advance. In orchestrator-workers an LLM decides them dynamically from the input.

Graphs, nodes and edges

Example: a UPSC essay practice site. It gives a topic, the student writes an essay, it is evaluated on three aspects, and if the score is too low the student gets feedback and can retry.

Interview
  • Every node is one task, and behind the scenes it is just a Python function. Nodes say what to do.
  • Edges say when: which node runs after which. Edge types: sequential, parallel, conditional (branching) and loops.
  • So a LangGraph graph is a set of Python functions wired together by edges.

State

Interview

State is the shared memory that flows through the workflow. It holds every piece of data the workflow needs to run (essay text, topic, the three scores, the overall score), and those values change as execution moves forward.

  • Defined before the graph, as key-value pairs, usually a TypedDict (Pydantic also works).
  • Shared: every node gets the full state as input.
  • Mutable: every node can update it, and the updated state flows to the next node.

Reducers

By default an update replaces the old value. For "add two numbers, then double the result", that is fine: 11 becomes 22. It breaks a chatbot:

Interview

A reducer defines how a node's update is applied to the shared state: replace, add, or merge. Each key can have its own reducer. Examples: chat messages should be appended; essay drafts can be kept as history so a student sees how they improved. Reducers matter most in parallel workflows, where several nodes write to the same key in the same step.

Execution model

Interview
  • The model is inspired by Google Pregel, a system for large-scale graph processing.
  • compile() checks the graph is logically valid, for example that there is no orphaned node connected to nothing.
  • Message passing: sending the updated state along edges to the next node.
  • Superstep: one round of execution. It is called a superstep because one round can hold several nodes running in parallel (three evaluators fire together, so that is one superstep with three steps).
  • You never call nodes yourself: invoke the graph and LangGraph runs everything.

The recipe for any LangGraph workflow

  1. Define the state: a class inheriting TypedDict.
  2. Create the graph: StateGraph(State).
  3. Add nodes: add_node("name", function). The node name and function name may differ.
  4. Add edges, using the dummy START and END nodes.
  5. compile(), which returns a runnable workflow.
  6. invoke(initial_state) returns the final state. State goes in, state comes out.
bmi_workflow.pyRan · LangGraph 1.2.11
from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class BMIState(TypedDict):
    weight_kg: float
    height_m: float
    bmi: float
    category: str

def calculate_bmi(state: BMIState) -> dict:
    bmi = state["weight_kg"] / state["height_m"] ** 2
    return {"bmi": round(bmi, 2)}            # return only what changed

def label_bmi(state: BMIState) -> dict:
    bmi = state["bmi"]
    if bmi < 18.5:
        category = "Underweight"
    elif bmi < 25:
        category = "Normal"
    elif bmi < 30:
        category = "Overweight"
    else:
        category = "Obese"
    return {"category": category}

builder = StateGraph(BMIState)
builder.add_node("calculate_bmi", calculate_bmi)
builder.add_node("label_bmi", label_bmi)
builder.add_edge(START, "calculate_bmi")
builder.add_edge("calculate_bmi", "label_bmi")
builder.add_edge("label_bmi", END)
workflow = builder.compile()

print(workflow.invoke({"weight_kg": 80, "height_m": 1.73}))
# {'weight_kg': 80, 'height_m': 1.73, 'bmi': 26.73, 'category': 'Overweight'}

LLM workflows: Q&A and prompt chaining

The simplest LLM workflow is one node that sends a question to the LLM and writes the answer into state. It shows LangChain (the model) and LangGraph (the flow) working together. Prompt chaining uses two LLM calls in a row: topic to outline, then outline to blog.

prompt_chaining.pyNeeds OPENAI_API_KEY · not run
from typing import TypedDict
from dotenv import load_dotenv
from langchain_openai import ChatOpenAI
from langgraph.graph import StateGraph, START, END

load_dotenv()                                 # reads OPENAI_API_KEY from .env
llm = ChatOpenAI(model="gpt-4o-mini")        # any LangChain chat model works

class BlogState(TypedDict):
    title: str
    outline: str
    content: str

def create_outline(state: BlogState) -> dict:
    prompt = f"Write a detailed outline for a blog titled: {state['title']}"
    return {"outline": llm.invoke(prompt).content}   # .content = the text of the AIMessage

def create_blog(state: BlogState) -> dict:
    prompt = (f"Write a detailed blog titled '{state['title']}' "
              f"that follows this outline:\n{state['outline']}")
    return {"content": llm.invoke(prompt).content}

builder = StateGraph(BlogState)
builder.add_node("create_outline", create_outline)
builder.add_node("create_blog", create_blog)
builder.add_edge(START, "create_outline")
builder.add_edge("create_outline", "create_blog")
builder.add_edge("create_blog", END)
blog_writer = builder.compile()

final = blog_writer.invoke({"title": "Rise of AI in India"})
print(final["outline"])    # the intermediate result is still here
print(final["content"])
Interview

"Isn't LangGraph overkill for a linear flow?" Yes. One llm.invoke() or a LangChain chain does the same job. One concrete benefit, though: the state keeps every intermediate value. The final state has the title, the outline and the blog, while a chain only hands you the last output.

from pydantic import BaseModel, Field

class BlogState(TypedDict):          # 1. add the new key to the state
    title: str
    outline: str
    content: str
    score: int

builder.add_edge("create_blog", "evaluate_blog")
builder.add_edge("evaluate_blog", END)

Parallel workflows

Several tasks run at the same time and their results are combined. Fan out by adding several edges from one node; fan in by pointing several edges at one node.

Example 1: batsman stats (no LLM)

Input: runs, balls, fours, sixes from one innings. Three independent metrics, so they can run in parallel:

  • Strike rate = runs ÷ balls × 100
  • Balls per boundary = balls ÷ (fours + sixes)
  • Boundary % = (fours × 4 + sixes × 6) ÷ runs × 100
batsman_workflow.pyRan · LangGraph 1.2.11
from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class BatsmanState(TypedDict):
    runs: int
    balls: int
    fours: int
    sixes: int
    strike_rate: float
    balls_per_boundary: float
    boundary_pct: float
    summary: str

def calc_sr(s: BatsmanState):
    return {"strike_rate": s["runs"] / s["balls"] * 100}

def calc_bpb(s: BatsmanState):
    return {"balls_per_boundary": s["balls"] / (s["fours"] + s["sixes"])}

def calc_boundary_pct(s: BatsmanState):
    return {"boundary_pct": (s["fours"] * 4 + s["sixes"] * 6) / s["runs"] * 100}

def summary_node(s: BatsmanState):
    return {"summary": f"SR {s['strike_rate']:.1f} | balls/boundary "
                       f"{s['balls_per_boundary']:.1f} | boundary% {s['boundary_pct']:.1f}"}

builder = StateGraph(BatsmanState)
for fn in (calc_sr, calc_bpb, calc_boundary_pct, summary_node):
    builder.add_node(fn.__name__, fn)
for name in ("calc_sr", "calc_bpb", "calc_boundary_pct"):
    builder.add_edge(START, name)            # fan-out
    builder.add_edge(name, "summary_node")   # fan-in
builder.add_edge("summary_node", END)
workflow = builder.compile()

print(workflow.invoke({"runs": 100, "balls": 50, "fours": 6, "sixes": 4})["summary"])
# SR 200.0 | balls/boundary 5.0 | boundary% 48.0
Gotcha · InvalidUpdateError

If each parallel node does state["x"] = ...; return state, the run fails with:

InvalidUpdateError: At key 'runs': Can receive only one value per step. Use an Annotated key to handle multiple values.

Why: returning the full state counts as writing every key, including runs, even though you only read it. Three nodes writing the same key in the same superstep is a conflict, because LangGraph cannot tell whose value is right.

Fix: return a partial update containing only the keys the node computed. The video's advice is to do this everywhere, sequential graphs included.

Example 2: UPSC essay evaluator (LLM)

This example combines three ideas: parallel nodes, structured output and a reducer.

Interview · why structured output

If you only ask in the prompt for "feedback and a score", most replies come back right, but some won't: the model may write "seven" instead of 7, and you can't average that. Define a Pydantic schema with field descriptions (descriptive fields help the LLM) and constraints (ge=0, le=10), then call llm.with_structured_output(Schema). Every call now returns a Schema object (.feedback, .score). It needs a model that supports structured output, such as gpt-4o-mini.

Interview · reducer for parallel writes

All three nodes write a score to the same key in the same superstep. With the default replace behavior they would conflict. The fix is scores: Annotated[list[int], operator.add], where each node returns [score], a one-item list. operator.add is the function form of +, and [8] + [7] + [6] gives [8, 7, 6]. Other reducers are possible, such as max, min or your own function.

upsc_essay_workflow.pyNeeds OPENAI_API_KEY · not run
import operator
from typing import Annotated, TypedDict
from dotenv import load_dotenv
from pydantic import BaseModel, Field
from langchain_openai import ChatOpenAI
from langgraph.graph import StateGraph, START, END

load_dotenv()
llm = ChatOpenAI(model="gpt-4o-mini")

class Evaluation(BaseModel):
    feedback: str = Field(description="Detailed feedback on the essay")
    score: int = Field(description="Score out of 10", ge=0, le=10)

grader = llm.with_structured_output(Evaluation)      # returns an Evaluation object

class EssayState(TypedDict):
    essay: str
    language_feedback: str
    analysis_feedback: str
    clarity_feedback: str
    overall_feedback: str
    scores: Annotated[list[int], operator.add]        # reducer: concatenate lists
    avg_score: float

def grade(aspect: str, essay: str) -> Evaluation:
    return grader.invoke(f"Evaluate the {aspect} of this essay. "
                         f"Give detailed feedback and a score out of 10.\n\n{essay}")

def evaluate_language(state: EssayState):
    out = grade("language quality", state["essay"])
    return {"language_feedback": out.feedback, "scores": [out.score]}   # a list, so it merges

def evaluate_analysis(state: EssayState):
    out = grade("depth of analysis", state["essay"])
    return {"analysis_feedback": out.feedback, "scores": [out.score]}

def evaluate_clarity(state: EssayState):
    out = grade("clarity of thought", state["essay"])
    return {"clarity_feedback": out.feedback, "scores": [out.score]}

def final_evaluation(state: EssayState):
    summary = llm.invoke(            # plain model: we want prose, not another score
        "Combine these into one short feedback paragraph:\n"
        f"Language: {state['language_feedback']}\n"
        f"Analysis: {state['analysis_feedback']}\n"
        f"Clarity: {state['clarity_feedback']}"
    ).content
    return {"overall_feedback": summary,
            "avg_score": sum(state["scores"]) / len(state["scores"])}

builder = StateGraph(EssayState)
for fn in (evaluate_language, evaluate_analysis, evaluate_clarity, final_evaluation):
    builder.add_node(fn.__name__, fn)
for name in ("evaluate_language", "evaluate_analysis", "evaluate_clarity"):
    builder.add_edge(START, name)
    builder.add_edge(name, "final_evaluation")
builder.add_edge("final_evaluation", END)
essay_grader = builder.compile()

result = essay_grader.invoke({"essay": "India in the Age of AI ..."})
print(result["scores"], result["avg_score"])
print(result["overall_feedback"])

Conditional workflows

Interview · parallel vs conditional

Both have branches. A parallel workflow runs all branches together. A conditional workflow runs exactly one branch, chosen by a condition. It is if/else for workflows, and more than two branches are allowed. Almost every complex workflow needs it.

Example 1: solving a quadratic equation

For ax² + bx + c = 0, the discriminant D = b² − 4ac decides the roots. If D > 0, there are two real roots (−b ± √D) ÷ 2a. If D = 0, there is one repeated root −b ÷ 2a. If D is negative, there are no real roots.

Interview · how routing works
  1. Write a router function that reads the state and returns the name of the next node. It is not a node itself. Type its return value with Literal[...] so the graph knows the possible targets.
  2. Use add_conditional_edges(source_node, router) instead of add_edge. LangGraph calls the router after the source node and follows the returned name.

from typing import Literal, TypedDict
from langgraph.graph import StateGraph, START, END

class QuadState(TypedDict):
    a: int
    b: int
    c: int
    equation: str
    discriminant: float
    result: str

def show_equation(s: QuadState):
    # :+ prints the sign, which fixes the "4x2 4x 4" display bug from the video
    return {"equation": f"{s['a']}x² {s['b']:+}x {s['c']:+} = 0"}

def calc_discriminant(s: QuadState):
    return {"discriminant": s["b"] ** 2 - 4 * s["a"] * s["c"]}

def real_roots(s: QuadState):
    d = s["discriminant"] ** 0.5
    r1 = (-s["b"] + d) / (2 * s["a"])
    r2 = (-s["b"] - d) / (2 * s["a"])
    return {"result": f"Two real roots: {r1:g} and {r2:g}"}

def repeated_root(s: QuadState):
    return {"result": f"One repeated root: {-s['b'] / (2 * s['a']):g}"}

def no_real_roots(s: QuadState):
    return {"result": "No real roots"}

def route_roots(s: QuadState) -> Literal["real_roots", "repeated_root", "no_real_roots"]:
    if s["discriminant"] > 0:
        return "real_roots"
    if s["discriminant"] == 0:
        return "repeated_root"
    return "no_real_roots"

builder = StateGraph(QuadState)
for fn in (show_equation, calc_discriminant, real_roots, repeated_root, no_real_roots):
    builder.add_node(fn.__name__, fn)
builder.add_edge(START, "show_equation")
builder.add_edge("show_equation", "calc_discriminant")
builder.add_conditional_edges("calc_discriminant", route_roots)
for name in ("real_roots", "repeated_root", "no_real_roots"):
    builder.add_edge(name, END)
quadratic = builder.compile()

quadratic.invoke({"a": 1, "b": -3, "c": 2})["result"]   # 'Two real roots: 2 and 1'
quadratic.invoke({"a": 2, "b": 4, "c": 2})["result"]    # 'One repeated root: -1'
quadratic.invoke({"a": 2, "b": 4, "c": 4})["result"]    # 'No real roots'

Iterative (looping) workflows

Loop between nodes to improve something until it is good enough. This is the evaluator-optimizer pattern from Video 4.

Use case: automatically post funny, original tweets on a topic. First drafts from an LLM are usually mediocre, so we loop a generator, a strict evaluator and an optimizer. In real life, an approved tweet would also go to a human for approval and then be posted through the X API.

Interview · loops
  • A loop is nothing special: you just add an edge that points back to an earlier node.
  • add_conditional_edges(source, router, path_map): the dict maps router outputs to nodes, and END is allowed as a target.
  • Always add a stop condition. An evaluator that is too strict, or a model that is too weak, can loop forever. Track iteration and stop at max_iteration.
  • Model choice: ideally a strong writer for generate and optimize, and a model that follows a rubric reliably for evaluate. The evaluator prompt should spell out the criteria clearly, because the final quality depends on it.
Beyond the video

LangGraph also stops runaway graphs by itself. Every run has a recursion_limit on supersteps (25 by default in LangGraph 1.2.11), and going past it raises GraphRecursionError. Raise it with invoke(inputs, {"recursion_limit": 50}). Your own max_iteration is still better, because it ends the run cleanly with a result.

import operator
from typing import Annotated, Literal, TypedDict
from dotenv import load_dotenv
from pydantic import BaseModel, Field
from langchain_core.messages import HumanMessage, SystemMessage
from langchain_openai import ChatOpenAI
from langgraph.graph import StateGraph, START, END

load_dotenv()
writer = ChatOpenAI(model="gpt-4o")         # generate + optimize
judge = ChatOpenAI(model="gpt-4o-mini")     # evaluate

class Verdict(BaseModel):
    evaluation: Literal["approved", "needs_improvement"]
    feedback: str = Field(description="One paragraph on strengths and weaknesses")

strict_judge = judge.with_structured_output(Verdict)

class TweetState(TypedDict):
    topic: str
    tweet: str
    evaluation: Literal["approved", "needs_improvement"]
    feedback: str
    iteration: int
    max_iteration: int
    tweet_history: Annotated[list[str], operator.add]     # keep every draft
    feedback_history: Annotated[list[str], operator.add]

def generate(state: TweetState):
    tweet = writer.invoke([
        SystemMessage("You are a witty X/Twitter writer."),
        HumanMessage(f"Write one original, funny tweet about {state['topic']}. "
                     "No question-answer jokes. Max 280 characters. Simple English."),
    ]).content
    return {"tweet": tweet, "tweet_history": [tweet]}

def evaluate(state: TweetState):
    v = strict_judge.invoke([
        SystemMessage("You are a harsh tweet critic. Judge originality, humour, punch, "
                      "virality and format. Reject Q&A jokes, setup-punchline jokes and "
                      "anything over 280 characters."),
        HumanMessage(f"Tweet: {state['tweet']}"),
    ])
    return {"evaluation": v.evaluation, "feedback": v.feedback,
            "feedback_history": [v.feedback]}

def optimize(state: TweetState):
    tweet = writer.invoke([
        SystemMessage("You improve tweets using a critic's feedback."),
        HumanMessage(f"Topic: {state['topic']}\nTweet: {state['tweet']}\n"
                     f"Feedback: {state['feedback']}\nRewrite it. Max 280 characters."),
    ]).content
    return {"tweet": tweet, "iteration": state["iteration"] + 1, "tweet_history": [tweet]}

def route_evaluation(state: TweetState) -> str:
    if state["evaluation"] == "approved" or state["iteration"] >= state["max_iteration"]:
        return "approved"
    return "needs_improvement"

builder = StateGraph(TweetState)
builder.add_node("generate", generate)
builder.add_node("evaluate", evaluate)
builder.add_node("optimize", optimize)
builder.add_edge(START, "generate")
builder.add_edge("generate", "evaluate")
builder.add_conditional_edges("evaluate", route_evaluation,
                              {"approved": END, "needs_improvement": "optimize"})
builder.add_edge("optimize", "evaluate")            # the back-edge makes the loop
tweet_bot = builder.compile()

result = tweet_bot.invoke({"topic": "Indian Railways", "iteration": 1, "max_iteration": 5})
for draft in result["tweet_history"]:
    print(draft)

Building a chatbot

This video starts a chatbot that later videos extend with persistence, a UI, streaming, human-in-the-loop, retries and tools. The graph itself is tiny: START, then one chat_node that calls the LLM, then END. It runs inside a while loop.

Interview · chat state
  • State: messages: Annotated[list[BaseMessage], add_messages].
  • BaseMessage is the parent of HumanMessage, AIMessage, SystemMessage and ToolMessage, so the list can hold any of them.
  • add_messages is LangGraph's built-in reducer for message lists. It appends like operator.add but is optimized for messages, and it is the recommended choice for them.
Beyond the video

What makes add_messages better, checked on 1.2.11: a new message whose ID matches an existing one replaces it instead of being appended, and plain tuples like ("ai", "hello") or dicts like {"role": "user", "content": "x"} are converted into message objects.

Gotcha · the chatbot forgets

Asking "Hi, I'm Nitish" and then "What is my name?" fails, and "add 10 to 100, then add 15" gives 25. Why: every invoke() starts with a fresh state. When a run reaches END its state is thrown away, so the second call only contains the second message.

Fix: persistence. Compile with a checkpointer and pass a thread_id. LangGraph then loads the saved state for that thread before each run, and add_messages appends the new turn to it.

from langchain_core.messages import BaseMessage, HumanMessage

Persistence and time travel

Interview · definition

Persistence is the ability to save and restore the state of a workflow over time. Normally, once a run finishes, its state is erased and cannot be recovered. With persistence the state is saved, and not just the final values: every intermediate state is saved too. This is the foundation for memory, fault tolerance, human-in-the-loop and time travel.

Checkpointer and checkpoints

LangGraph implements persistence with a checkpointer. It splits a run into checkpoints, one at each superstep, and saves a snapshot of the state at each one to storage.

Interview · threads

Every run is given a thread_id, and its checkpoints are stored against it. Ask for a thread_id and you get exactly that run's states, even though the database holds many runs. A new chat gets a new thread_id; resuming an old chat reuses its id.

Each snapshot carries .values (the state), .next (which node runs next) and .config (thread_id plus checkpoint_id).

The four benefits of persistence

Interview

1. Short-term memory for chatbots (resume a past conversation, as in Video 9). 2. Fault tolerance. 3. Human-in-the-loop. 4. Time travel.

Fault tolerance: resume where it crashed

Because the state is saved after every superstep, a crashed run can continue from the failed node instead of starting over. The video simulated a crash with a 30-second sleep in step 2 and a manual keyboard interrupt in Colab. I used an exception instead:

fault_tolerance.pyRan · LangGraph 1.2.11
from typing import TypedDict
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import StateGraph, START, END

class JobState(TypedDict):
    step1: str
    step2: str
    step3: str

attempts = 0

def step_1(state):
    return {"step1": "done"}

def step_2(state):
    global attempts
    attempts += 1
    if attempts == 1:
        raise RuntimeError("server went down")    # simulated crash
    return {"step2": "done"}

def step_3(state):
    return {"step3": "done"}

builder = StateGraph(JobState)
for fn in (step_1, step_2, step_3):
    builder.add_node(fn.__name__, fn)
builder.add_edge(START, "step_1")
builder.add_edge("step_1", "step_2")
builder.add_edge("step_2", "step_3")
builder.add_edge("step_3", END)
job = builder.compile(checkpointer=InMemorySaver())

cfg = {"configurable": {"thread_id": "job-42"}}
try:
    job.invoke({}, cfg)
except RuntimeError:
    pass

job.get_state(cfg).next     # ('step_2',)  where it stopped
job.invoke(None, cfg)       # None means "resume this thread"; step_1 is not run again
# {'step1': 'done', 'step2': 'done', 'step3': 'done'}
Interview

To resume a thread, call invoke(None, config) with the same thread_id. Passing None instead of an input tells LangGraph to continue from the last checkpoint rather than start a new run.

Human-in-the-loop

Example: generate a LinkedIn post, ask a human for approval, then post it through the API. The human might reply in a minute or in two days, and keeping the process alive for two days makes no sense. So LangGraph interrupts the run (suspends it), and when the human replies it resumes from the same point. It knows where to resume because of the checkpoints. It is like fault tolerance, except the pause is intentional. The code comes in a later video.

Time travel: replay and edit the past

Go back to any checkpoint and re-run everything after it. It is mainly a debugging tool for complex workflows. You can also change the state at that checkpoint and run from there, which creates a fork.

In the video, after update_state the run still produced a pizza joke. The run had been started from the old checkpoint_id, which still says pizza. update_state creates a new checkpoint and returns its config, so run from that returned config.

Interview · which checkpointer

InMemorySaver keeps everything in RAM. It is for demos and learning, and the data is lost when the process stops. In production use a database-backed checkpointer such as Postgres or Redis. SQLite comes later in this playlist.

Chatbot UI with Streamlit

The Video 9 chatbot gets a ChatGPT-like web UI. The code splits into a backend (the LangGraph graph, nearly unchanged) and a frontend (Streamlit).

Two Streamlit components

  • st.chat_message(role): a message bubble. Use "user" or "assistant"; the role sets the icon, and the avatar parameter can change it.
  • st.chat_input(placeholder): the input box at the bottom. It returns the text when the user presses Enter.
Gotcha · Streamlit reruns everything

On every interaction, such as pressing Enter, Streamlit re-runs the whole script from top to bottom. A plain Python list holding the chat history is recreated empty each time, so old messages vanish. The fix is st.session_state, a dict that survives reruns and resets only when the page is refreshed.

The video builds it in three steps: an echo bot that repeats the user, then history in session_state, then the echo replaced with chatbot.invoke.

Streaming

Until now the chatbot called invoke() and showed the reply only after the LLM had finished. Streaming shows the reply token by token while it is being generated, the way ChatGPT does.

Interview · why streaming matters
  • Perceived latency: the user sees the first words within a second instead of waiting for the whole answer (time to first token).
  • Long answers become readable while they are still being written, and the user can stop early.
  • The UI can show progress, for example which tool is running (Video 17).
  • Replace chatbot.invoke(...) with chatbot.stream(..., stream_mode="messages"). It yields (message_chunk, metadata) pairs. chunk.content is the new piece of text, and metadata["langgraph_node"] says which node produced it.
  • In Streamlit, st.write_stream(generator) renders the chunks as they arrive and returns the complete text, which you then append to the history.

Resume chat: multiple conversations

This video adds ChatGPT's sidebar: a New Chat button and a list of past conversations that you can click to continue. The trick is that every conversation is its own LangGraph thread.

  • Three keys live in st.session_state: message_history (what is on screen), thread_id (the current chat) and chat_threads (all chat ids, for the sidebar).
  • Every invoke/stream call uses the current thread: {"configurable": {"thread_id": st.session_state["thread_id"]}}.
  • Loading an old chat does not need any storage of your own: the checkpointer already holds its messages.
frontend.py, thread helpersStreamlit · not run
import uuid
import streamlit as st
from langchain_core.messages import HumanMessage

def new_chat():
    st.session_state["thread_id"] = str(uuid.uuid4())
    st.session_state["chat_threads"].append(st.session_state["thread_id"])
    st.session_state["message_history"] = []

def load_chat(thread_id):
    state = chatbot.get_state({"configurable": {"thread_id": thread_id}})
    return [
        {"role": "user" if isinstance(m, HumanMessage) else "assistant", "content": m.content}
        for m in state.values.get("messages", [])
    ]

for key, default in [("message_history", []), ("chat_threads", [])]:
    st.session_state.setdefault(key, default)
if "thread_id" not in st.session_state:
    new_chat()

if st.sidebar.button("New Chat"):
    new_chat()
st.sidebar.header("My Conversations")
for tid in reversed(st.session_state["chat_threads"]):
    if st.sidebar.button(tid, key=tid):
        st.session_state["thread_id"] = tid
        st.session_state["message_history"] = load_chat(tid)

Interview · why observability for LLM apps

Tools in LangGraph

The chatbot gets three tools: web search (DuckDuckGo), a live stock price API and a calculator. It can now answer "What is Apple's share price, and how much do 50 shares cost?" by calling two tools in a row.

Interview · the four pieces
  • Tool: a function with a name, a description and typed arguments. With @tool, the docstring becomes the description and the type hints become the argument schema the LLM sees.
  • llm.bind_tools(tools): tells the LLM which tools exist. When it wants one, it returns an AIMessage with tool_calls (tool name plus arguments) instead of text. The LLM never runs the tool itself.
  • ToolNode(tools): a prebuilt node that runs every tool call in the last AI message and appends a ToolMessage with each result.
  • tools_condition: a prebuilt router. It goes to the node named "tools" if the last AI message has tool calls, otherwise to END.
tool_backend.pyGraph ran · fake LLM making a tool call

from typing import Literal
from langchain_core.tools import tool
from langchain_community.tools import DuckDuckGoSearchRun
from langgraph.graph import StateGraph, START, MessagesState
from langgraph.prebuilt import ToolNode, tools_condition

@tool
def calculator(a: float, b: float, operation: Literal["add", "sub", "mul", "div"]) -> float:
    """Do basic arithmetic on two numbers."""
    if operation == "div" and b == 0:
        return "Error: division by zero"
    return {"add": a + b, "sub": a - b, "mul": a * b, "div": a / b if b else 0}[operation]

@tool
def get_stock_price(symbol: str) -> dict:
    """Get the latest price for a stock symbol such as AAPL or TSLA."""

           f"&symbol={symbol}&apikey={os.environ['ALPHAVANTAGE_API_KEY']}")

    return {"messages": [llm_with_tools.invoke(state["messages"])]}

builder.add_edge(START, "chat_node")
builder.add_conditional_edges("chat_node", tools_condition)
builder.add_edge("tools", "chat_node")

MCP client in LangGraph

The problem with hand-written tools

Every tool in Video 17 is code inside the chatbot. Add GitHub, Slack and a database, and the client grows with each integration. When a provider changes its API version, every app that wrote its own integration breaks and must be updated. The tool approach is brittle.

The MCP idea: separate who owns the tools

Interview · what MCP solves

Model Context Protocol is a standard way for AI apps to talk to tool servers. The tool's owner runs an MCP server that exposes its tools; your app is an MCP client that connects, lists the tools and calls them. When the provider changes something, they update their server and every client keeps working. In the demo, adding a remote expense-tracker server needed only a new config entry; the agent could add, list and summarise expenses without any new client code.

Why the code had to become async

The MCP client libraries are async-only, so the graph must be async too: nodes become async def, LLM calls become await llm.ainvoke(...), the graph runs with await graph.ainvoke(...), and the entry point is asyncio.run(main()). Async lets one thread juggle many I/O waits (network calls to servers and LLMs): await hands control back to the event loop while waiting.

mcp_chatbot.pyNot run · needs langchain-mcp-adapters and servers

    builder.add_edge("tools", "chat_node")

    result = await graph.ainvoke({"messages": [HumanMessage("List my expenses for November")]})
    print(result["messages"][-1].content)

asyncio.run(main())

RAG using LangGraph

The chatbot becomes a RAG chatbot: upload a PDF, ask questions answered from it, and the other tools keep working.

Interview · why RAG
  • Outdated knowledge: an LLM only knows its training data.
  • Privacy: your private documents were never in that data, and you don't want to train a model on them.
  • Hallucination: grounding answers in retrieved text reduces made-up answers.

The principle is in-context learning: give the LLM the relevant information in the prompt instead of retraining it. You can't paste a whole book (token limits), so you split it and send only the chunks related to the question.

RAG as a tool (agentic RAG)

Instead of always retrieving, the retriever is wrapped as a rag_tool and added to the tool list. The LLM decides when a question needs the document, and the same chat_node / ToolNode loop from Video 17 runs it. The LangSmith trace shows chat_node, then tools, then the retriever, then chat_node again. A document-grounded answer took about 8 to 9 seconds in the demo.

Human-in-the-loop (HITL)

HITL means the agent pauses at chosen points so a human can approve, edit or answer before it continues.

Interview · why agents need human oversight
  • Accuracy: LLMs make mistakes, and a human can catch them before they cause harm.
  • Accountability: for high-stakes actions (spending money, sending emails, deleting data, buying stock) a person should own the decision.
  • Benefits: safer actions, more user trust, compliance, and human feedback you can learn from.
Interview · common HITL patterns
  • Approve or reject an action before it runs.
  • Edit the state or a draft (fix the email before it is sent).
  • Review tool calls: check or change a tool's arguments before execution.
  • Ask for input: the agent asks the human for missing information.

How LangGraph does it: interrupt and Command

Interview
  • Call interrupt(payload) inside a node (or a tool). Execution stops and the payload comes back to the caller under result["__interrupt__"].
  • It needs a checkpointer and a thread_id: the paused state has to be saved somewhere (this is the persistence feature from Video 10).
  • Resume with graph.invoke(Command(resume=value), config) using the same thread. Inside the node, interrupt() returns value.
Gotcha · the node runs twice

On resume, LangGraph re-runs the paused node from its first line; it does not continue from the middle. I confirmed it: a counter at the top of the node reached 2. So code before interrupt() runs again. Keep side effects (API calls, DB writes) after the interrupt, or make them safe to repeat.

LLMs don't have memory. So how do they remember?

This is a theory video with no repository. These notes follow its chapter list, with the concepts explained in my own words.

LLMs are stateless by design

At inference an LLM takes the input tokens and predicts the next token, over and over. Its weights are frozen, and nothing is kept between two API calls. Each call is independent, so the model cannot remember your name from the previous message unless you send it again.

Building memory around the LLM

The only thing the model can use is what is in its context window. Anything placed in the prompt can be used for that answer: this is in-context learning. So memory is something the application builds around the model by choosing what to put in the prompt.

Interview · short-term memory and its limits

Short-term memory = resending the conversation history every turn. That is exactly what the checkpointer plus add_messages did in Video 9. Its limits:

  • The context window fills up, and old messages must be dropped.
  • Cost and latency grow with every turn, because every token is resent.
  • Quality drops in very long contexts: the model can miss details in the middle.
  • It is session-bound: a new chat starts with nothing.
Interview · three types of long-term memory
TypeWhat it storesExample
EpisodicSpecific past events and interactions"Last week we debugged your Docker setup"
SemanticFacts about the user or the world"User is a Python developer based in India"
ProceduralHow to behave or do tasks: rules and preferences"Always answer with short bullet points"

How long-term memory works

  • Challenges: deciding what is worth storing, duplicate and contradictory memories, stale facts, retrieving the right memory at the right time, privacy and user control, and extra cost and latency.
  • Tools: the video's chapter covers tools for memory systems. LangGraph's own option is the Store (Video 24); dedicated memory layers such as Mem0, Zep and Letta also exist. That list is mine, not taken from the video.
  • Future: bigger context windows and models and products with memory built in.

Long-term memory in LangGraph

Interview · checkpointer vs store

A checkpointer saves state per thread: short-term memory, one conversation. A store saves data across threads, usually per user: long-term memory. A new chat (new thread) starts empty, but it can still read what the store knows about the user.

Store basics

  • Data is organised by namespace (a tuple such as ("user", user_id, "details")), then a key, then a value dict.
  • put(ns, key, value), get(ns, key), and search(ns) to list everything in a namespace.
  • Give the store an embedding model and search(ns, query=..., limit=...) becomes semantic search: "what is the user learning?" finds "User is learning machine learning".

Using memory in a graph

  • Compile with builder.compile(store=store). Nodes that declare config and store parameters get them injected.
  • Pass the user in the config: {"configurable": {"user_id": "u1"}}, alongside a thread id if you also use a checkpointer.
  • Read path: search the user's namespace and put the facts into the system prompt so replies are personal ("Sure, Nitish…").
  • Write path: an extractor LLM with structured output (should_write plus a list of short facts) decides what is worth keeping: stable identity, preferences, ongoing projects, but not one-off details.
  • No duplicates: give the extractor the existing memories and have it mark each fact is_new; only new ones are stored.
  • PostgresStore makes the memories persistent (call store.setup() once).

Project: blog-writing agent

An agent that plans, researches and writes a technical blog with generated images. Code: blog-writing-agent.

Interview · planning agent vs direct execution

Asking one LLM call to "write a blog on X" gives shallow, uneven text. A planning agent first produces a structured plan (sections, goals, bullet points, word targets), then writes each section separately, then assembles them. This is the orchestrator-worker pattern from Video 4.

Built in stages

  1. Basic: a Plan schema via structured output, one worker per task, merge the sections.
  2. Better prompting: richer plan fields (audience, tone, blog kind, whether a section needs code or citations).
  3. Research: a router decides the mode. closed_book for evergreen topics; hybrid for evergreen topics that need current examples; open_book for news and "latest" topics. If research is needed it writes search queries, runs Tavily, and turns the results into evidence items (title, URL, date). Workers may only cite those URLs, and open_book drops evidence older than the recency window.
  4. Images: the reducer becomes a three-node subgraph. It merges the sections in order, asks an LLM where up to 3 diagrams would really help (inserting [[IMAGE_1]] placeholders plus image prompts), generates them with an image model (Gemini), and swaps the placeholders for markdown images. If generation fails, it leaves the prompt in place instead of crashing.
  5. UI: a Streamlit front end. The video ends with advice to build end-to-end projects like this for your portfolio.
Interview · dynamic fan-out with Send

With normal edges, the number of parallel branches is fixed when you build the graph. Here the number of sections is only known at runtime. A function given to add_conditional_edges returns a list of Send("worker", payload), one per task, and LangGraph runs that many workers in parallel. Each worker receives its own payload rather than the whole state. Because parallel workers finish in any order, each returns (task_id, markdown) into a list reducer, and the merge step sorts by task_id.

import operator
from typing import Annotated, TypedDict
from pydantic import BaseModel, Field
from langgraph.graph import StateGraph, START, END
from langgraph.types import Send

class Task(BaseModel):
    id: int
    title: str
    goal: str
    bullets: list[str] = Field(min_length=3, max_length=6)
    target_words: int

class Plan(BaseModel):
    blog_title: str
    tasks: list[Task]

class BlogState(TypedDict):
    topic: str
    plan: Plan
    sections: Annotated[list[tuple[int, str]], operator.add]   # (task_id, markdown)
    final: str

def orchestrator(state: BlogState):
    return {"plan": llm.with_structured_output(Plan).invoke(f"Plan a technical blog on {state['topic']}")}

def fanout(state: BlogState):
    return [Send("worker", {"task": t, "topic": state["topic"]}) for t in state["plan"].tasks]

def worker(payload: dict):                      # gets its own payload, not the full state
    t = payload["task"]
    md = llm.invoke(f"Write the section '{t.title}' ({t.target_words} words) covering: {t.bullets}").content
    return {"sections": [(t.id, md)]}

def merge(state: BlogState):
    body = "\n\n".join(md for _, md in sorted(state["sections"]))   # restore plan order
    return {"final": f"# {state['plan'].blog_title}\n\n{body}"}

builder = StateGraph(BlogState)
builder.add_node("orchestrator", orchestrator)
builder.add_node("worker", worker)
builder.add_node("merge", merge)
builder.add_edge(START, "orchestrator")
builder.add_conditional_edges("orchestrator", fanout, ["worker"])
builder.add_edge("worker", "merge")
builder.add_edge("merge", END)
blog_agent = builder.compile()

Corrective RAG (CRAG)

Interview · the problem with traditional RAG

Traditional RAG blindly trusts whatever the retriever returns. The retriever always returns the top-k chunks, even when none of them is relevant. Ask a question outside the knowledge base (the demo uses ML textbooks, then asks about recent AI news), and the LLM receives irrelevant context and hallucinates.

The CRAG idea (Yan et al., 2024)

Add a retrieval evaluator that judges the retrieved documents, then act on its verdict:

VerdictRule used in the videoAction
CorrectAt least one chunk scores above 0.7Refine the retrieved docs and answer
IncorrectEvery chunk scores below 0.3Discard them; rewrite the query, search the web, answer from the web results
AmbiguousAnything in betweenCombine the weakly relevant docs with web results
  • Knowledge refinement: split the context into sentence-level "strips", have an LLM keep only strips that help answer the question, and join what's left. This removes noise even from good documents.
  • Query rewriting: turn the user's question into a short keyword search query (adding a recency hint such as "last 30 days" when needed) before calling the web search tool (Tavily).
  • Compared with the paper: the paper trains a small model (T5) as the evaluator; the video uses an LLM judge with a Pydantic score schema.

import re
from pydantic import BaseModel

UPPER, LOWER = 0.7, 0.3

class DocScore(BaseModel):
    score: float          # 0.0 irrelevant ... 1.0 enough to answer alone
    reason: str

class KeepOrDrop(BaseModel):
    keep: bool

scorer = llm.with_structured_output(DocScore)
strip_filter = llm.with_structured_output(KeepOrDrop)

def evaluate_docs(state):
    scores = [scorer.invoke(f"Question: {state['question']}\nChunk: {d.page_content}\n"
                            "Score relevance from 0 to 1. Be strict.").score
              for d in state["docs"]]
    good = [d for d, s in zip(state["docs"], scores) if s > LOWER]
    if any(s > UPPER for s in scores):
        verdict = "CORRECT"
    elif scores and all(s < LOWER for s in scores):
        verdict, good = "INCORRECT", []
    else:
        verdict = "AMBIGUOUS"
    return {"verdict": verdict, "good_docs": good}

def refine(state):
    docs = {"CORRECT": state["good_docs"],
            "INCORRECT": state["web_docs"]}.get(state["verdict"], state["good_docs"] + state["web_docs"])
    text = re.sub(r"\s+", " ", " ".join(d.page_content for d in docs))
    strips = [s for s in re.split(r"(?<=[.!?])\s+", text) if len(s) > 20]
    kept = [s for s in strips
            if strip_filter.invoke(f"Question: {state['question']}\nSentence: {s}\nKeep it?").keep]
    return {"refined_context": "\n".join(kept)}

def route_after_eval(state) -> str:
    return "refine" if state["verdict"] == "CORRECT" else "rewrite_query"

Self-RAG: an AI that fact-checks itself

Interview · three problems with traditional RAG
  1. Unnecessary retrieval: it retrieves for every question, even "what is machine learning?", which needs no documents.
  2. Blind trust in documents: it uses whatever comes back, relevant or not.
  3. No answer verification: nobody checks whether the answer is supported by the documents, or whether it answers the question.

Self-RAG (Asai et al., 2023)

The model reflects on its own process at four points. In the paper the model is trained to emit special reflection tokens; the video gets the same behaviour from LLM judges with structured outputs.

CheckQuestion it answersIf it fails
RetrieveDo I need documents for this question?Answer directly from general knowledge
IsRelIs each retrieved document relevant to the topic?Drop it; if none are left, say "No answer found"
IsSupIs my answer fully, partially or not supported by the context?Revise the answer, then check again (up to a retry limit)
IsUseDoes the answer actually address the question?Rewrite the retrieval query and retrieve again (up to a limit)
  • The relevance check is deliberately loose (topic level), because answer support is checked later by IsSup.
  • IsSup is strict: any interpretive words not present in the context ("generous leave", "great culture") count as only partially supported. It also returns short evidence quotes.
  • The revise step rewrites the answer using only direct quotes from the context.
  • Loops need limits (max revisions, max rewrites), and the run raises LangGraph's recursion_limit to 80 so legitimate loops are not cut off.

from typing import Literal
from pydantic import BaseModel, Field

class RetrieveDecision(BaseModel):
    should_retrieve: bool = Field(description="True if company documents are needed")

class IsSup(BaseModel):
    issup: Literal["fully_supported", "partially_supported", "no_support"]
    evidence: list[str] = Field(default_factory=list, description="Up to 3 direct quotes")

class IsUse(BaseModel):
    isuse: Literal["useful", "not_useful"]
    reason: str

MAX_REVISIONS, MAX_REWRITES = 3, 3

def is_sup(state):
    v = llm.with_structured_output(IsSup).invoke(
        f"Is every claim in the ANSWER supported by the CONTEXT?\n"
        f"ANSWER:\n{state['answer']}\nCONTEXT:\n{state['context']}")
    return {"issup": v.issup, "evidence": v.evidence}

def route_after_issup(state) -> str:
    if state["issup"] == "fully_supported" or state.get("retries", 0) >= MAX_REVISIONS:
        return "is_use"
    return "revise_answer"

def route_after_isuse(state) -> str:
    if state["isuse"] == "useful":
        return "END"
    if state.get("rewrite_tries", 0) >= MAX_REWRITES:
        return "no_answer_found"
    return "rewrite_question"

Interview · CRAG vs Self-RAG

CRAG fixes the retrieval side: grade the retrieved documents, refine them, and fall back to web search when the knowledge base can't help. Self-RAG adds self-checks around generation: whether to retrieve at all, whether the answer is grounded, and whether it is useful, looping to revise or re-retrieve. They can be combined.

Interview Q&A

How is agentic AI different from generative AI?

GenAI creates content and is reactive: you guide every step. Agentic AI is given a goal, plans and executes the steps itself, adapts, and brings in a human mainly for approvals. GenAI (the LLM) is a building block inside agentic AI.

Videos 1, 2

Define agentic AI.

AI that takes a task or goal from a user and works toward completing it on its own with minimal human guidance: it plans, takes actions, adapts to changes, and asks for help only when needed.

Video 2

What are the six characteristics of an agentic system?

Autonomy, goal orientation, planning, reasoning, adaptability, context awareness.

Video 2

How do you control an agent's autonomy, and why?

Limit its permission scope (which tools and actions it can use alone), add human-in-the-loop checkpoints, give users override controls (pause, stop), and enforce guardrails and policies. Without these it could send wrong offers, act on bias or overspend.

Video 2

How does an agent plan?

It generates several candidate plans (planning is a search from the initial state to the goal state), evaluates them on efficiency, tool availability, cost, risk and constraints, then selects one through a human or a policy. Planning and execution repeat in a loop, with re-planning when steps fail.

Video 2

Where is reasoning used in an agent?

In planning: goal decomposition, tool selection, estimating resources and risk. In execution: choosing between options, deciding when to ask a human, and handling errors.

Video 2

Short-term vs long-term memory in agents?

Short-term holds the current session: messages, tool results, recent decisions. Long-term persists across sessions: goals, past interactions, user preferences, guardrails.

Video 2

Name the five components of an agentic AI system.

Brain (the LLM), orchestrator (runs the plan: order, routing, retries, loops), tools (external actions, including RAG), memory (short-term, long-term, state) and supervisor (human-in-the-loop, guardrails, escalation).

Video 2

Workflow vs agent?

A workflow orchestrates LLMs and tools through predefined code paths that a developer designs, so it follows the same path each time. An agent's LLM decides its own process and tool use dynamically.

Video 3

Why do we need LangGraph if we have LangChain?

For complex workflows LangChain falls short on control flow (branches and loops need glue code), state (it is stateless), event-driven pause and resume, fault tolerance, long human-in-the-loop waits, nested workflows and full observability. LangGraph handles all of these natively.

Video 3

What is glue code and why is it a problem?

Custom Python written outside the library to stitch steps together (while loops, if/else, manual state passing). The more of it you have, the harder the code is to maintain, debug, observe with LangSmith and share across a team.

Video 3

Does LangGraph replace LangChain?

No. It is built on top of LangChain. LangChain provides components (models, prompts, retrievers, loaders, tools); LangGraph orchestrates them. Use LangChain alone for simple linear flows, and LangGraph for non-linear, stateful or long-running ones.

Video 3

Define LangGraph.

An orchestration framework for building stateful, multi-step, event-driven LLM workflows, both single-agent and multi-agent. It represents a workflow as a graph and handles state, branching, looping, pausing, resuming and fault recovery.

Videos 3, 4

Name five common LLM workflow patterns.

Prompt chaining, routing, parallelization, orchestrator-workers, evaluator-optimizer.

Video 4

Parallelization vs orchestrator-workers?

Both run sub-tasks in parallel and aggregate the results. In parallelization the sub-tasks are fixed in advance; in orchestrator-workers an LLM decides them at runtime based on the input.

Video 4

What are nodes and edges in LangGraph?

Nodes are tasks, implemented as Python functions that take the state and return updates (the what). Edges decide the execution order (the when). Edges can be sequential, parallel, conditional or loops.

Video 4

What is state in LangGraph?

The shared, mutable memory that flows through the graph: every piece of data the workflow needs, as key-value pairs. It is usually a TypedDict (Pydantic also works). Every node can read it and update it.

Video 4

What is a reducer? Give examples.

It defines how an update is applied to a state key: replace (the default), add or merge. Examples: Annotated[list[int], operator.add] to collect parallel scores, and Annotated[list[BaseMessage], add_messages] for chat history.

Videos 4, 6, 9

Explain LangGraph's execution model.

It is inspired by Google Pregel. You define and compile the graph, then invoke it. A node activates, runs, and returns a partial update that is merged through the reducers. Message passing along edges activates the next nodes. Each round is a superstep, and parallel nodes share one. Execution halts when no node is active and no message is in transit.

Video 4

What does compile() do?

It checks that the graph structure is valid (for example, no orphaned nodes) and returns a runnable you can invoke. It is also where you attach a checkpointer.

Videos 4, 5

What causes InvalidUpdateError in a parallel graph?

Several nodes writing the same key in one superstep without a reducer, which typically happens when parallel nodes return the full state. Fix it by returning only the changed keys, or by giving that key a reducer if several nodes really need to write it.

Video 6

Why use structured output with LLM nodes?

Free text is unreliable to parse (a score might come back as "seven"). A Pydantic schema passed to with_structured_output guarantees typed fields that later nodes and routers can trust.

Videos 6, 7

How do you implement branching?

Write a router function that reads the state and returns the next node's name (typed with Literal), then wire it up with add_conditional_edges(source, router), optionally with a path_map dict. Exactly one branch runs. The Command object is another way.

Video 7

How do you build a loop, and how do you stop it from running forever?

Use a conditional edge that either exits or goes to a node, plus an edge from that node back to an earlier one. Stop it with an iteration counter and a max_iteration check in the router. LangGraph's recursion_limit (25 supersteps by default) is a last-resort guard that raises GraphRecursionError.

Video 8

Why did the chatbot forget the user's name, and how do you fix it?

Each invoke() starts with a fresh state, and the state is discarded at END. Fix it with persistence: compile with a checkpointer and pass the same thread_id in the config every turn.

Video 9

What is persistence, and how is it implemented?

Saving and restoring workflow state over time, intermediate states included. A checkpointer saves a snapshot at every superstep, stored under a thread_id. You read it back with get_state and get_state_history.

Video 10

What four features does persistence enable?

Short-term memory, fault tolerance, human-in-the-loop and time travel.

Video 10

How do you resume a crashed run?

Call invoke(None, config) with the same thread_id. It continues from the last checkpoint, at the node that failed, without re-running the finished nodes.

Video 10

What is time travel?

Re-running a thread from any past checkpoint by passing its checkpoint_id in the config, which is useful for debugging. With update_state you can change values at that checkpoint; this creates a fork that you run from the returned config.

Video 10

Why does a Streamlit chat lose its history, and how do you fix it?

Streamlit re-runs the whole script on every interaction, so normal variables reset. Store the display history in st.session_state. The LLM's memory still comes from the LangGraph checkpointer.

Video 11

Why stream LLM output, and how do you do it in LangGraph?

Streaming cuts perceived latency: users see the first words immediately and can read long answers as they arrive. Call graph.stream(input, config, stream_mode="messages") to get (chunk, metadata) pairs as tokens are generated. In Streamlit, pass a generator of chunk.content to st.write_stream.

Video 12

How do you build ChatGPT-style multiple conversations with LangGraph?

Give each conversation its own thread_id (a uuid). Keep the list of ids for the sidebar. To reopen a chat, call graph.get_state({"configurable": {"thread_id": id}}) and turn its messages into UI entries. The checkpointer already stores every chat.

Video 13

How do you list all past conversations from a checkpointer?

Iterate checkpointer.list(None), which yields every checkpoint, and collect the unique config["configurable"]["thread_id"] values.

Video 14

Why check_same_thread=False with SqliteSaver in Streamlit?

A Python sqlite3 connection by default may only be used by the thread that created it. Streamlit reruns the script on different threads, so the shared connection must allow cross-thread use.

Video 14

What is observability, and why do LLM apps need it?

Being able to understand what happened inside the system from what it records. LLM apps are non-deterministic and multi-step, so you need the inputs, outputs, latency, tokens, cost and errors of every step to debug wrong answers, slowness and cost spikes.

Video 15

Project vs trace vs run in LangSmith?

A project groups traces (one app or environment). A trace is one end-to-end request. A run is one step inside a trace (LLM call, retriever, tool, node), and runs nest into a tree.

Video 15

How do you trace code that isn't LangChain?

Decorate the function with @traceable (optionally with a name, tags and metadata). LangChain and LangGraph code is traced automatically once LANGSMITH_TRACING=true and the API key are set.

Video 15

How do you group chat turns into one conversation in LangSmith?

Pass the conversation id as metadata={"thread_id": ...} in the config. This is separate from configurable.thread_id, which the checkpointer uses to load state; pass the same value in both places.

Video 16

Walk through how tool calling works in LangGraph.

bind_tools tells the LLM which tools exist. When it wants one, it returns an AIMessage with tool_calls. tools_condition routes to the ToolNode, which runs the calls and appends ToolMessages. The graph loops back to the LLM, which answers or calls more tools.

Video 17

What do ToolNode and tools_condition do?

ToolNode is a prebuilt node that executes every tool call in the last AI message and returns ToolMessages. tools_condition is a prebuilt router that goes to the node named "tools" if there are tool calls, and to END otherwise.

Video 17

What problem does MCP solve?

Hand-written tool integrations live in every client and break when a provider's API changes. With MCP, the provider runs a server that exposes its tools, and clients connect through config and discover the tools at runtime. Providers update their server; clients don't change.

Video 18

Why did the MCP chatbot have to become async, and how did it work with Streamlit?

The MCP client libraries are async-only, so nodes became async def and used ainvoke, astream, AsyncSqliteSaver and aiosqlite. Streamlit is synchronous, so the backend runs one event loop in a background thread and submits coroutines with run_coroutine_threadsafe.

Video 18

Why RAG, and what are its steps?

LLMs have outdated knowledge, have never seen your private documents, and hallucinate. RAG gives them relevant context in the prompt (in-context learning). Index: load, split, embed, store. Query: retrieve top-k chunks, build the prompt, generate.

Video 19

What is agentic RAG?

Wrapping the retriever as a tool so the LLM decides when to search the documents, instead of retrieving for every message. It reuses the normal tool loop.

Video 19

How can a tool know the current thread without the LLM passing it?

Declare a config: RunnableConfig parameter on the tool. ToolNode injects it, it is hidden from the schema the LLM sees, and the tool reads config["configurable"]["thread_id"].

Video 19, beyond the video

Why human-in-the-loop, and what are the common patterns?

For accuracy (catching mistakes) and accountability on high-stakes actions. Patterns: approve or reject, edit the state or a draft, review tool calls before they run, and ask the human for missing information.

Video 20

How do interrupt and Command work?

interrupt(payload) inside a node pauses the run and returns the payload under __interrupt__. It needs a checkpointer and a thread_id. Resume with invoke(Command(resume=value), config), and interrupt then returns value.

Video 20

What happens to a node's code when you resume after an interrupt?

The whole node runs again from its first line, so code before interrupt() executes twice. Put side effects after the interrupt or make them idempotent.

Video 20

What are the two ways to use a subgraph?

Call the compiled subgraph inside a node and map keys in and out, which suits different state schemas. Or add the compiled subgraph directly as a node, so it shares the parent's keys. Subgraphs give modularity, reuse and multi-agent structure.

Video 21

LLMs are stateless, so how do chatbots remember?

The application puts memory into the context window on every call. Short-term memory resends the conversation history; long-term memory retrieves stored facts about the user and adds them to the prompt.

Video 22

What are the limits of short-term memory, and how do you handle a long conversation?

The context window, cost and latency that grow every turn, weaker answers in long contexts, and no memory across sessions. Strategies: trim what is sent, delete old messages with RemoveMessage, or summarize old messages into a running summary.

Videos 22, 23

Episodic vs semantic vs procedural memory?

Episodic: specific past events and interactions. Semantic: facts about the user or world. Procedural: how to behave or do tasks, such as rules and style preferences.

Video 22

Checkpointer vs store?

A checkpointer saves state per thread (short-term memory for one conversation). A store saves data across threads, usually namespaced per user (long-term memory). Nodes get the store injected after compile(store=store).

Video 24

How does the long-term memory chatbot avoid storing duplicates?

The extractor LLM receives the user's existing memories and marks each new fact is_new. Only facts marked new are written to the store.

Video 24

What is the Send API, and when do you need it?

For a fan-out whose size is only known at runtime. A function passed to add_conditional_edges returns a list of Send(node, payload), and LangGraph runs one parallel worker per Send, each with its own payload. It is the basis of the orchestrator-worker pattern.

Video 25

Why does the blog agent sort sections before merging?

Parallel workers finish in any order, so the list reducer collects sections in completion order. Each worker returns (task_id, markdown), and the merge step sorts by task_id to restore the plan's order.

Video 25

What is Corrective RAG?

RAG with a retrieval evaluator that grades the retrieved chunks. Correct (some chunk above the upper threshold): refine and answer. Incorrect (all below the lower threshold): rewrite the query and use web search. Ambiguous: combine both. It fixes RAG's blind trust in retrieval.

Video 26

What is knowledge refinement in CRAG?

Splitting the retrieved context into sentence strips, keeping only the strips an LLM judges relevant to the question, and recombining them, so even good documents lose their noise.

Video 26

What is Self-RAG?

RAG that checks itself at four points: whether to retrieve at all, whether each document is relevant (IsRel), whether the answer is supported by the context (IsSup, with a revise loop), and whether the answer is useful (IsUse, with a query-rewrite loop).

Video 27

CRAG vs Self-RAG?

CRAG improves the retrieval side: grade the documents, refine them, fall back to the web. Self-RAG adds self-reflection around generation: skip unnecessary retrieval, verify grounding and usefulness, and loop to fix. They can be combined.

Videos 26, 27

Why does the Self-RAG run raise recursion_limit?

Its revise and re-retrieve loops can take many supersteps, and the default limit (25) would stop a legitimate run with GraphRecursionError. The graph's own retry counters are still what ends the loops.
