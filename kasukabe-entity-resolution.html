Kasukabe Entity Resolution
Amazon ML Challenge 2026 · Team Kasukabe · 4 members

Matching 10 million messy business records to the businesses they describe

Three data sources describe the same businesses with typos, missing fields, Indian scripts and look-alike decoys, and share no common ID. For every clean Source 1 business, this pipeline finds each Source 2 and Source 3 record that refers to it, using only the provided data.

The task

Source 1 is a deduplicated list of businesses. Sources 2 and 3 are noisy copies of it. Each Source 2/3 record belongs to at most one Source 1 business, and about a quarter of them belong to none: they are decoys, near-copies of a real business with one word or one number changed. The test set adds France, which never appears in the training data.

Training data

2.21M Source 1 · 10.3M Source 2/3 · 7.64M labelled matches · US and India

Test data

1.73M Source 1 · 9.97M Source 2/3 · no labels · US, India and France (15%)

Metric

F0.5 per Source 1 business, averaged. Precision counts twice as much as recall. A business with no match scores 1.0 only if nothing is predicted for it.

Two real businesses from the training data with every record the ground truth links to them. The model has to accept all of these and reject the decoys that differ by a single word or house number.

How the pipeline works

One command trains on the full training data and a second one predicts the test set. Both run the same cleaning, blocking and feature code, so the model sees test pairs exactly as it saw training pairs. The numbers on the left track how much data exists at each step.

Why two models instead of one

Stage 1 judges each pair in isolation, so it cannot tell that five other records already claim the same business with a slightly different house number. Stage 2 sees one row per record and adds that context: how clear the winner was, how many records compete for the same business, and whether the confident siblings agree with this record or with the Source 1 version on the details that differ. Stage 2 is kept only when it beats stage 1 on held-out businesses.

How the training data is split

The split is by business, not by record, so a held-out business is never seen in any form during training. Every Source 2/3 record stays in the candidate pool, so held-out businesses face the same competition from decoys as test businesses do.

The bug validation could not show

For a while the leaderboard sat about 1.3 points below validation. A train-versus-test report of feature values and LightGBM per-feature contributions found the model rejecting obvious test matches such as “SOTECH LLC SERVICE” against “Sotech LLC” at the same address. The cause was word rarity (IDF). It was computed over the whole file, and the test file has a different country mix, so every English word's rarity moved. For “service” the shift was enough to cross the model's split points.

A second test-only pattern was the next-door decoy. Records whose house number differs by 1 to 10 were accepted 2.4 to 2.6 times more often per business on the test than on validation in the US, while every other group matched. The decision step now makes those records clear a much higher bar (0.999 in the US, 0.98 elsewhere).

Engineering

Scale

143M training pairs × 80 features form a 46 GB float32 matrix kept on disk as a memmap and processed in 1M-pair chunks. Candidate search uses sparse matrix products (sparse_dot_topn) with multi-threaded string scoring (RapidFuzz).

Compute

Up to 7 AWS EC2 instances (8 vCPU, 64 GB) in Mumbai, N. Virginia and Singapore ran queued experiments overnight. A cron job powers each machine off after 30 idle minutes.

Reproducibility

Fixed seeds and sorted tokens make blocking identical across runs; before this fix, Python's hash seed moved scores by ±0.0002. Dependencies are pinned. The cleaning cache is stamped with a hash of the code and inputs, and prediction refuses a model trained with different features.

Testing and review

145 pytest tests, including the challenge metric reproducing the problem statement's worked example (0.714). Two written code reviews, each open bug pinned by an expected-failure test.

Diagnostics

A train-versus-test report compares feature distributions and LightGBM per-feature contributions. This report is how the IDF shift was found.

Rules

No external data, APIs or pretrained models. Every library is MIT, BSD, Apache or ISC licensed; the final model is LightGBM (MIT), far below the 8B-parameter cap.

Resume bullets

  • Built a large-scale entity-resolution pipeline (Amazon ML Challenge 2026, team of 4) linking 10M+ noisy business records to 1.7M reference businesses across the US, India and an unseen country (France); reached 0.9875 macro F0.5 on held-out data and 0.9737 on the public leaderboard.

  • Designed multi-pass blocking with IDF-weighted sparse cosine search over word, phonetic-skeleton and character 3-gram tokens plus look-alike candidate borrowing, cutting 17.3 trillion possible pairs to 144M candidates at 98.7% recall.

  • Engineered 80 pairwise features (fuzzy string similarity, IDF-weighted word alignment, house-number distance, competitor margins) and a two-stage LightGBM matcher with a sibling-aware re-scorer, improving held-out F0.5 from 0.968 to 0.988 over 20+ tracked experiments.

  • Built script-aware text normalisation: a phonetic transliterator for 9 Indian scripts and a 521-word dictionary learned from labelled pairs (e.g. “sarvisej” → “services”) to match non-Latin business names.

  • Traced a validation-to-leaderboard gap to word-rarity statistics that shifted between train and test; computing them per country raised test acceptance of a common true-match pattern from 3.5% to 99.4%.

  • Ran parallel experiments on up to 7 AWS EC2 instances with a deterministic, cached, chunked pipeline (46 GB on-disk feature matrix) backed by a 145-test pytest suite.

Talking points for interviews

  1. The metric shaped the design

    F0.5 counts precision twice, and a business with no match scores zero if anything is predicted for it. That led to the one-record-one-business rule and a strict threshold. Threshold 0.69 scored best on validation, but 0.85 scored higher on the leaderboard (0.9665 vs 0.965).

  2. Blocking sets the ceiling

    A true pair that blocking misses can never be recovered. At 98.71% recall the best possible F0.5 is 0.9959, so recall work (transliteration, character 3-grams, look-alike borrowing) paid off directly.

  3. Context beats pairwise scoring

    The stage-2 re-scorer sees competing records and siblings, which a pairwise model cannot. It lifted held-out F0.5 from 0.9831 to 0.9871.

  4. Debugging distribution shift

    Comparing feature contributions between train and test pointed to one IDF feature. Per-country statistics fixed it without touching the model.

  5. What did not work

    “Test-aware” strict thresholds lost 0.0033 on the leaderboard. Ensembles of four models did not beat the best single model. Look-alike vote features were dropped because decoy clusters exist only in the test set. Doubling blocking K to 20 bought 0.5 points of recall for 1.6× the pairs.
